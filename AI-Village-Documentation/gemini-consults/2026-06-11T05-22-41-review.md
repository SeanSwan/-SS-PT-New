### 2. Design Problems

Here are the core issues I've identified in the data architecture that will directly and negatively impact the final user experience.

-   **Finding 1: Unstable Message Keys**
    -   **Severity:** HIGH
    -   **Design Problem:** The use of `Date.now()` for message IDs (`id: \`cmd-user-${Date.now()}\``) is unreliable. If two messages are generated in the same millisecond (possible in fast operations), it can lead to key collisions. More importantly, these IDs are not stable. They are regenerated on every render pass if the component logic is re-run, which will cause React to unmount and remount the entire message component. This completely breaks animations (like `framer-motion` `AnimatePresence`), ruins accessibility focus, and causes unnecessary re-renders.
-   **Finding 2: Monolithic, String-Based Content**
    -   **Severity:** CRITICAL
    -   **Design Problem:** The `content` field is just a `string`. This is the single biggest architectural flaw. A premium assistant doesn't just send text; it sends interactive prompts, data visualizations, and confirmation dialogs. The current approach crams a simple summary string into `content` and hides the rich data in a generic `metadata` blob. This forces the UI component to have complex, brittle logic like `if (message.metadata?.commandConfirmation) { render buttons } else { render text }`. This is poor design. The data structure itself should tell the UI *what* to render, not just *what text* to show.
-   **Finding 3: Lack of Message State for UI Feedback**
    -   **Severity:** MEDIUM
    -   **Design Problem:** The `CoachMessageData` type has no concept of a message's lifecycle state. Is it sending? Has it been delivered? Did it fail? Without this, we can't provide the subtle but crucial feedback users expect. Optimistic updates will just appear instantly, and network failures will be jarring. We can't build the smooth, responsive feel of an app like Apple Fitness+ if our data model is blind to message status.
