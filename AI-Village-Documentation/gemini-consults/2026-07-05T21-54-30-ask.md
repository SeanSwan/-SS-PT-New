### Q1: Fail-Closed vs. Fail-Soft

**Fail-Closed Argument (Correct):** Financial and administrative actions must be atomic and perfectly auditable. A billing change without a corresponding audit log creates a state of financial ambiguity. This violates the integrity of our "luxury vault" principle. An un-audited mutation is not an inconvenience; it is a critical data corruption event. The system must enforce its own consistency.

**Fail-Soft Argument (Incorrect for this context):** This prioritizes operational uptime over data integrity. It argues that a primary business function (billing change) shouldn't be blocked by a secondary system (auditing). This is acceptable for low-risk, non-financial events, but not here.

**Recommendation: Your choice of fail-closed is absolutely correct.** We must never allow a revenue-affecting change to commit without a corresponding, locked-in audit trail. The risk of an untracked financial event far outweighs the operational risk of a failed transaction.

### Q2: Snapshot Correctness & Lost Updates

You've identified a critical race condition. Reading a row via `findOne` without a lock, even inside a transaction, is vulnerable to a lost update anomaly under the default `READ COMMITTED` isolation level.

**Risk:** Another admin transaction (T2) could read the same client data after your transaction (T1) starts but before your `findOne` executes. Both T1 and T2 would then operate on the same stale `previousState`, and the last transaction to commit would overwrite the other's changes.

**Solution:** Use a pessimistic lock. When you fetch the client, explicitly lock the row for the duration of the transaction. This forces any concurrent transactions attempting to modify that same row to wait until yours is complete.

```typescript
// Correct Implementation: Lock the row on read
const client = await Client.findOne({
  where: { id: clientId },
  transaction: t,
  lock: t.LOCK.UPDATE // Acquires a row-level lock in PostgreSQL
});

// Now your snapshot is guaranteed to be correct for the update
const previousState = { /* ... snapshot data from 'client' ... */ };

await client.update({ /* ... new data ... */ }, { transaction: t });
```

### Q3: Other Failure Modes

The primary failure mode introduced by wrapping the audit in the transaction is **performance degradation and lock contention**.

The `AdminAccountAuditLog.create` operation adds overhead. If the `admin_account_audit_logs` table has complex indexes, triggers, or is under heavy write load, it will prolong the duration of your transaction. This holds the `UPDATE` lock on the `clients` row for longer, increasing the likelihood of deadlocks and reducing system throughput. While correct for integrity, we must monitor the performance of this specific transaction closely.

Stick with the fail-closed, locked-row approach. It's the only path that meets our standard for security and precision.
