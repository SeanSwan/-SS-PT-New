### **1. Design Gaps**

The plan is almost exclusively concerned with backend architecture and data models. It correctly identifies the need for UI surfaces but provides no specification for them. This is the primary gap we must fill.

*   **Visual Design & State Communication:** The plan introduces critical new states (Modes A/B/C, readiness levels, stale pain data, blocking gates) with zero visual language. How does a trainer *see* a "hard hold"? How does a client understand a plan is in "Clinician-Coordinated" mode? Without a clear visual system, these states are just database entries.
*   **Interaction & Animation:** The plan mentions "feels-fast engineering" but provides no animation strategy. The experience of encountering a safety gate, providing an override reason, or logging a symptom response is undefined. These are critical moments that can feel either reassuring and professional or clunky and alarming.
*   **Responsive Behavior:** There is no consideration for how these new, complex UI elements—like a clinician protocol view or a trainer override modal—will function across our 10-breakpoint system, especially on a 320px screen.
*   **Accessibility (a11y):** Critical safety alerts, blocking modals, and new data visualizations must be fully accessible. The plan does not specify ARIA roles, focus management strategy for modals, or screen-reader-friendly text for new iconography. A safety gate a screen reader can't understand is not a safety gate.

### **2. Enhancement Opportunities**

This is where we elevate the Cortex from a correct machine to a premium coaching experience, drawing inspiration from the fluidity of Apple Fitness+ and the clarity of Nike Training Club.

*   **Data-Rich, Not Data-Dense:** The new exercise ontology (§7) adds fields like `impactLevel` and `technicalComplexity`. We must not simply display these as a table of numbers. We will visualize them as elegant, minimalist "stat glyphs" or micro-bars directly on exercise cards, using our `Arctic Cyan` data color. This provides at-a-glance intelligence, a hallmark of premium apps.
*   **"Living" Surfaces:** The body map for pain logging (§12) should not be a static diagram. We will use a subtly animated SVG model of the human body. Active pain points will have a soft, persistent pulse effect. Selecting a region will feel fluid and responsive.
*   **Theatrics for Critical Moments:** Encountering a safety gate (§5.3) is a moment of high importance. Instead of a jarring `alert()`, we will use a deliberate, focused modal animation. The background will blur and darken, bringing the modal into sharp focus, reinforcing its gravity and importance.
*   **Haptic Feedback:** On mobile, interactions with critical components like the symptom-response sliders or acknowledging a safety override should provide subtle haptic feedback to confirm the action.
*   **The Coach Persona Embodied:** The "charming no" from §13.5 should manifest visually. When Swan Coach chat denies a request for safety reasons, the chat bubble could have a unique style—perhaps a subtle `Wing Purple` border glow—and be accompanied by a custom "safety shield" icon to visually reinforce the reason.

### **3. Architecture Recommendations**

To build these experiences, we need a consistent frontend architecture.

*   **Component Structure:** We will create a new directory: `src/components/cortex/`. This will house all new UI components related to this initiative (e.g., `StatusIndicator.tsx`, `SafetyGateModal.tsx`, `BodyMap.tsx`). These will be built as primitives that can be composed into larger views.
*   **Styled-Components & Theme Strategy:** All styling will be driven by our theme provider. We will add new tokens to our theme file to represent these new concepts:
    ```typescript
    // in styles/theme.ts
    export const theme = {
      // ...existing colors, fonts, etc.
      colors: {
        // ...
        modes: {
          durability: tokens.colors.iceWing, // #60C0F0
          clinicianCoordinated: tokens.colors.gildedFern, // #C6A84B
          clinicalHold: tokens.colors.wingPurple, // #8B5CF6
        },
        status: {
          stale: tokens.colors.gildedFern, // Warning/attention
          // ... other statuses
        }
      },
      shadows: {
        // ...
        glow: {
          purple: `0 0 12px 2px ${tokens.colors.wingPurple}60`, // Note the alpha
          cyan: `0 0 12px 2px ${tokens.colors.iceWing}60`,
        }
      },
      animations: {
        modalFadeIn: 'cubic-bezier(0.4, 0, 0.2, 1) 300ms',
        // ...
      }
    };
    ```
*   **Animation Approach:**
    *   **CSS Transitions/Transforms:** For simple, performant interactions like hover states, button presses, and focus rings.
    *   **Framer Motion:** For complex, stateful animations like modal entry/exit, layout animations (e.g., a list re-ordering), and sequenced reveals. It provides superior control and handles accessibility (e.g., `prefers-reduced-motion`) out of the box. We will use it for the Safety Gate Modal and any "page-level" transitions.
