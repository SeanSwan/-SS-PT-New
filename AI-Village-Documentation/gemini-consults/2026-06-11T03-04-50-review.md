### **2. Design Problems**

I've identified two primary design problems in the data contracts produced by this engine.

#### **Finding #1: Brittle "Magic String" Attention Flags**

*   **Severity:** HIGH
*   **Design Problem:** The `buildTrainerDayContext` function returns an array of simple strings for `flags`, such as `['active pain', 'credits low (2)']`. This is a significant design flaw for several reasons:
    1.  **Brittleness:** If the backend team changes the string from "active pain" to "pain reported," the frontend breaks.
    2.  **Parsing Overhead:** The frontend has to parse the string "credits low (2)" to extract the number `2`. This is fragile and inefficient.
    3.  **Lack of Semantic Meaning:** A string doesn't carry inherent design information. The frontend must maintain a large, hardcoded mapping to translate "active pain" into a specific icon, a color (`CrimsonFrost`), and a priority level. This logic should not live on the client.
    4.  **Scalability:** Adding new flags requires coordinated changes in both the backend (string generation) and frontend (string parsing and mapping).

#### **Finding #2: Unstructured, Non-Hierarchical Gamification Data**

*   **Severity:** MEDIUM
*   **Design Problem:** The `gamification` object in `buildCoachContext` returns a flat structure: `{ tier: 'some_string', level: 5, points: 1250 }`.
    1.  **No Context:** The frontend receives `tier: 'gold'` but has no information about what `gold` means. Is it the highest tier? What's the next tier? What color is it associated with? We cannot build a dynamic, visually rich progress UI (like the rings in Apple Fitness+) without this context.
    2.  **No Progress Data:** The UI needs to know `pointsToNextLevel` to render a progress bar (an XP bar, in our theme). The current structure doesn't provide this, forcing the frontend to hardcode the entire level progression system. This is a classic violation of separation of concerns.

Here is the specific vision for correcting these issues.

*   **Design Solution:** We will replace the string-based `flags` array with an array of **Flag Objects**. Each object will have a consistent, machine-readable structure that empowers the frontend to render rich, data-driven indicators without any string parsing.

*   **Code Specification:**
    Modify the `sessions.map` block inside `buildTrainerDayContext`.

    **Current (Problematic) Output:**
    ```json
    "flags": ["active pain", "credits low (2)"]
    ```

    **New (Authoritative) Structure:**

    ```javascript
    const flags = [];
    const activePainCount = painByClient.get(clientId) || 0;
    if (activePainCount > 0) {
      flags.push({
        type: 'ACTIVE_PAIN',
        label: `Active Pain Reported`,
        severity: 'high',
        metadata: { count: activePainCount }
      });
    }

    if (credits !== null && credits <= 2) {

        type: 'LOW_CREDITS',
    ```


#### **Solution for Finding #2: Contextual Gamification Object**

*   **Design Solution:** The `gamification` object must be enriched to provide the frontend with all necessary context for rendering tier badges, XP bars, and progress indicators. It should describe not just the user's current state, but their state *within the system*.

*   **Code Specification:**
    This requires a lookup service or a configuration object for your gamification tiers, which should be trivial to implement. The `buildCoachContext` function should then use this to assemble the new object.

    **Current (Problematic) Output:**
    ```json
    "gamification": {
      "points": 1250,
      "level": 5,
      "tier": "silver",
      "streakDays": 14,
      "totalWorkouts": 55
    }
    ```

    **New (Authoritative) Structure:**
    ```json
    "gamification": {
      "level": 5,
      "points": 1250,
      "pointsInLevel": 250, // points accumulated since reaching level 5
      "pointsToNextLevel": 750, // points needed to hit level 6
      "tier": {
        "id": "silver",
        "name": "Icefall Knight", // Thematic name
        "rank": 2, // Ordinal rank for sorting/comparison
        "colorToken": "ArcticCyan" // Direct reference to our design system
      },
      "streak": {
        "days": 14,
        "isActive": true
      },
      "totalWorkouts": 55
    }
    ```
    This new structure is vastly superior. The frontend can now build an XP bar using `pointsInLevel` and `pointsToNextLevel`. It can display the tier badge using the thematic `name` and color it correctly using the `colorToken`, without any hardcoded logic.
