# Hostile Review Archive

**Role:** make a hostile review a *findable artifact* instead of a message in a transcript.

**Canonical root:** `Z:\HostileReviews` (WSL `/mnt/z/HostileReviews`).
**Full contract:** `Z:\HostileReviews\README.md` — read it; this skill is the procedure, that
file is the schema.
**Rule:** Rule 86 (`CLAUDE.md` / `AGENTS.md` / `CODEBUDDY.md`), full text in
`docs/ai-workflow/references/HOSTILE-REVIEW-ARCHIVE.md`.

## Why this exists

A hostile review that lives only in a chat transcript is not findable by the next agent.
Two things then happen, and both have already happened on this repo:

1. **The same defect gets re-found** in new words — restatement, not review, paid for twice.
2. **A stale `CLEAN` verdict gets read as current**, when the code has since changed.
   Nothing in the old review said it was stale, because nothing recorded the revision.

Before Rule 86 the reviews were scattered across `C:\tmp\`, `.ai-workflow/reviews/`,
`docs/ai-workflow/reviews/`, root `review-roundN-packet.md` and Hermes memos. A `*hostile*`
search returns hundreds of files, most of them duplicates inside stale worktree checkouts —
and none of them is *the* place to look. The measured breakdown lives in `README.md` §7 and is
generated by `census-hostile.mjs`; this skill deliberately carries no count of its own.

## The law

> **Every hostile-review pass leaves exactly one file in `Z:\HostileReviews`.
> A review that is not filed there did not happen.**

Filing is part of the pass, not a follow-up. File it before the completion claim that
Rule 73 governs.

Applies to the pass Rule 73 requires, any review Sean asks for by name, any review an agent
runs on its own initiative (Rule 61 slice-internal passes included), and subagent/workflow
reviews — the **dispatching** agent files the artifact, since a subagent's verdict is a
hypothesis until verified (Rule 30).

## Procedure — BEFORE you review

**Which path form you need depends on which Node you are running, and getting it wrong is a
`Cannot find module` rather than a useful error.** The commands in this skill use `/mnt/z/...`,
which is correct for **WSL's Node** only. Under **Windows Node** — Git Bash, PowerShell, cmd —
that form resolves to `C:\mnt\z\...` and fails; use `Z:/HostileReviews/...` instead. (`/z/...`
fails too: it resolves to `C:\z\...`.) Only the path you type changes — the scripts resolve
their own location, so your current directory never matters.

```bash
# WSL's Node:
node /mnt/z/HostileReviews/query.mjs --subject "<your subject>"
# Windows Node (Git Bash / PowerShell / cmd):
node Z:/HostileReviews/query.mjs --subject "<your subject>"
```

If a review exists, **read it first.** Your job is then to test whether its findings still
hold and whether the code has changed since — compare against the `commit` it was written
against. Do not re-derive it from scratch.

Other useful queries:

```bash
node /mnt/z/HostileReviews/query.mjs --repo SS-PT --unproven   # the honesty list
node /mnt/z/HostileReviews/query.mjs --verdict CLEAN          # the DANGEROUS list
node /mnt/z/HostileReviews/query.mjs --critical
node /mnt/z/HostileReviews/query.mjs --superseded
```

The `--verdict CLEAN` list is the dangerous one: those verdicts are the most likely to be
stale and the most likely to be trusted.

## Procedure — AFTER you review

```bash
node /mnt/z/HostileReviews/new-review.mjs \
  --subject "<what was reviewed>" \
  --reviewer <agent> --seat "<harness / model>" \
  --repo <repo|n/a> --branch <branch> --commit <sha|dirty|n/a> \
  --verdict <CLEAN|DEFECTS-FOUND|PARTIAL|INCONCLUSIVE> \
  --scope "In: <...>. Out: <...>." \
  --supersedes <old-review_id>   # ONLY if this round replaces an earlier one — records the FORWARD half

# write the review into the file it printed, then:
node /mnt/z/HostileReviews/reindex.mjs
```

**`--supersedes` is the one step nothing will catch for you.** Omit it while replacing an
earlier round and *both* halves of the link are missing: the new review declares nothing, the
old review never gets `superseded_by`, and its verdict keeps reading as current. `reindex.mjs`
only checks links that were declared, so an undeclared one is invisible to it. `new-review.mjs
--supersedes <old-review_id>` records the forward half; `relink.mjs` writes the backward half, and only once the successor is published.

`--dry-run` prints the file it would create and writes nothing. `reindex.mjs` exits
non-zero if any header is malformed, so a bad header fails at filing time instead of
becoming an invisible gap.

## The header contract (the lookup surface)

YAML front-matter, fixed key set — full definitions in the archive `README.md` §3:

```
review_id  date_local  date_utc  subject  reviewer_agent  reviewer_seat  round
repo  repo_path  branch  commit  scope  verdict  defects{critical,high,medium,low}
unproven  supersedes  superseded_by  tags
```

Four rules that are easy to get wrong:

- **Both timestamps, always** — local for humans, UTC for ordering across machines.
- **`UNKNOWN` is not a verdict.** If you do not know, the verdict is `INCONCLUSIVE` and the
  review's §3 says why.
- **`unproven` is not optional.** It is the count of things the pass could NOT establish.
  Zero unproven on a non-trivial review is a smell, not an achievement. "Unopened" is not
  "clean" (Rule 56), and absence of a grep hit is not evidence of safety.
- **`commit` matters.** A verdict against a dirty tree is only valid for that tree.

## The filename is the lookup key

`<YYYY-MM-DD>-<HHMMSS>-<subject-slug>.md` — local date first, so a directory listing is
already chronological; the slug so the subject is visible without opening the file.
Lowercase `a-z0-9-` only, hyphens not spaces, ≤48 chars, **cut at a word boundary**.
The filename stem IS the `review_id`.

## Supersede, never correct

- **Never edit a filed review into correctness.** A later round writes a NEW file with
  `supersedes: <old-review_id>`, and sets `superseded_by` on the old one. The record of what
  was believed at the time is the value; a quietly corrected review is a fabricated history.
  **The one edit that is required, not forbidden:** setting `superseded_by` on the old
  review is the backward half of the same link, not a correction — it changes no finding,
  no verdict and no count, and leaving it unset makes the older review still read as
  current. `new-review.mjs --supersedes` records the forward half; `relink.mjs` writes the backward half once the successor is published,
  and `reindex.mjs` reports a link that is not reciprocal.
- **Never append a second review to an existing file** — it destroys the `review_id` join
  and makes the index a lie.
- **Never delete** (Rule 34).

The archive is on `Z:`, outside any git repo. There is no `git log` safety net, so these
three are enforced by discipline, not tooling.

## What not to do

- Do not file a review whose `verdict` you cannot support. `INCONCLUSIVE` is a real answer.
- Do not file a `CLEAN` verdict for a pass that only covered part of the surface — that is
  `PARTIAL`, and `scope` must say which part.
- Do not write the review into `TEMPLATE.md`, and do not hand-edit `index.jsonl`.
- Do not treat a memo in the Hermes inbox as a filed review. It is not one.
