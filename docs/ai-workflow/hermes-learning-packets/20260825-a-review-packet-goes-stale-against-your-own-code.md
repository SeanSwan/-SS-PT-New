## The lesson

**A review packet is a claim about code, and it decays exactly as fast as code does — including within a single working session.** I moved the idempotency check ahead of GPU reservation in the morning, then wrote a gate table in the afternoon describing the ordering I remembered rather than the ordering that existed. Two of six seats (one paid $0.06, one subscription) spent their sharpest finding on a P0 that was already fixed. The cost is not just the wasted spend — it is that a seat which opens with a false P0 gets calibrated *by me* as less reliable on its true findings, and I then have to do extra work to separate them.

Yesterday's instance of this class was a stale **line count** (296 vs 227), and it cost two senior seats a blocker built on a bad number. Today's is a stale **gate row**. The pattern is now unambiguous: **anything in a packet that restates the code must be generated from the code at packet-write time.** A line count is a `wc -l`. A gate order is a grep of the guard sequence. A test count is the runner's own output. If I typed it from memory, it is fiction wearing a citation format.

**Second lesson — the panel's value concentrated in exactly two seats, and they were not the expensive ones.** Ox (free) found the only security-class defect: a client-supplied idempotency header used raw, letting owner B land on owner A's batch. GLM (subscription) found the only UX-fatal one: an estimate that reserved the GPU, so the price preview went dark precisely while a batch was running. The $0.235 of paid spend produced confirmations and stale-packet artifacts. This is not an argument against paid seats — it is an argument for reporting per-seat yield every round, so the routing table is learned from evidence instead of asserted.

**Third — "deferred" is only honest when the trigger is named.** Three seats wanted durable batch rows. The right answer was neither "fixed" nor "won't fix" but: today's deployment is one process, the stills themselves already survive as asset rows, the 404 says so in plain words — and it becomes a real defect the moment there is a second process or a client that must reattach across a restart. That sentence *is* the deferral. A deferral without a trigger is a dismissal wearing a schedule.

## Skills created or changed

- **Packet generation (proposed):** every restated-code claim in a review packet is produced by a command at write time. Two incidents in two days is a pattern, not bad luck.
- **Spend estimation (amended):** reasoning-heavy seats need a reasoning multiplier in the dry run, and the ACTUAL figure is reported against the estimate every round.

## Mistakes I made

- **Wrote a gate table from memory about code I had changed hours earlier.** Caught by two seats' false P0s. Prevention: generate, do not recall.
- **Repeated a documented class.** Yesterday's packet recorded "stale line count fed to a panel"; today I did the same thing with a gate row. The write-up did not change my behavior because it named the *instance* (line counts) instead of the *class* (any restated-code claim). A lesson that names an instance will be re-learned on the next instance.
- **Under-estimated panel spend by 1.7x** and only noticed because I recorded the actual. The estimate is what I ask Sean to approve; an estimate that is systematically low is a consent problem, not an accounting one.
- **Shipped `estimateOnly` reserving the GPU.** I wrote the reservation into the shared admission path without asking what a *preview* needs. Caught by GLM, not by me — and my own tests never estimated during a running batch.
