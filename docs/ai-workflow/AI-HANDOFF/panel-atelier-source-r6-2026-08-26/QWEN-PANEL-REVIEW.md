## VERDICT
REJECT — The `rememberKey` eviction logic contains a fatal logic flaw where the `while` loop condition is evaluated against `store.size` (which includes in-flight keys) while the eviction candidate is drawn from `settledKeys`, causing the loop to terminate prematurely or fail to evict when the store is saturated with in-flight requests, thereby breaking the memory bound and potentially allowing unbounded growth or stale data retention.

## BLOCKERS
1. **P0**: **Unbounded Memory Growth / Eviction Failure**: In `composeGuards.mjs`, `rememberKey` uses `while (store.size > IDEMPOTENCY_RETAIN)` as the loop condition. However, it only evicts from `settledKeys`. If the store contains many in-flight (unsettled) keys, `store.size` will be high, but `settledKeys` may be empty or small. The loop will check `store.size > 500`, enter the loop, get `oldest` from `settledKeys`. If `settledKeys` is empty, `oldest.done` is `true` (iterator exhausted), so it breaks. But if `settledKeys` has items, it evicts one. The problem is that `store.size` includes *all* keys (settled + in-flight). If you have 499 in-flight keys and 1 settled key, `store.size` is 500. The loop condition `500 > 500` is false, so it doesn't evict. But if you have 500 in-flight keys and 1 settled key, `store.size` is 501. The loop enters. It evicts the 1 settled key. Now `store.size` is 500. Loop ends. This seems okay? Wait. The real bug: `store.size` is the *current* size. The loop condition is checked *before* eviction. If `store.size` is 501, it evicts one. Now size is 500. Loop ends. But what if `store.size` is 1000, and `settledKeys` has only 10 items? It will evict 10 items, size becomes 990. Loop continues. `990 > 500` is true. `settledKeys` is now empty. `oldest.done` is true. Break. The store is still at 990 items, which is > 500. The bound is violated. The loop breaks because there are no more *settled* keys to evict, but the store is still over the limit. The in-flight keys remain. This is a memory leak. The bound is on `store.size`, but the eviction source is `settledKeys`. If the store is full of in-flight keys, it cannot evict them (correctly, as they are needed), but the bound is violated. The comment says "small enough that the map cannot grow for the life of the process", but it can grow to the number of in-flight keys. If a client sends 1000 concurrent requests, the store holds 1000 keys. This is a P0 memory leak.

2. **P1**: **Stale Replay Data**: In `composeStills.mjs`, the synchronous path stores `slimForReplay(result)` in the store. However, `slimForReplay` removes the `image` data. If a client retries, they get a response with `image: null`. The comment says "the client fetches from the library by `assetId`". But the response shape is different. The first response has `image: { kind: 'b64', data: '...' }`. The replayed response has `image: { kind: 'b64', dropped: true }`. If the client code expects `image.data` to exist, it will crash or fail to render. The comment says "Shape preserved so a client reading `image.kind` does not crash", but `image.data` is missing. This is a breaking change in the response shape for retries. Clients must be updated to handle `dropped: true`. If they are not, they will fail. This is a P1 because it breaks existing clients on retry.

The cheapest way to de-risk is to change the loop condition to `while (settledKeys.size > 0 && store.size > IDEMPOTENCY_RETAIN)` and ensure that the store size is bounded by the number of in-flight keys, which is acceptable if in-flight keys are bounded by the request rate. Alternatively, evict in-flight keys if they are older than a certain time, but that is complex. The simplest fix is to accept that the store can grow to the number of in-flight keys, and document this. But the comment says "small enough that the map cannot grow for the life of the process", which is false. The fix is to remove the claim that the map is bounded, or to implement a proper bound on in-flight keys.
