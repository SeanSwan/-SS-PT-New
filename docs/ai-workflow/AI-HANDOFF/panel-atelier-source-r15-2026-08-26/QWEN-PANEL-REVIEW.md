2. **P1: Correctness / Stale State (Watchdog Race Condition)**
   - **Failure Scenario:** The `watchdog` promise in `localBatchRunner.mjs` (lines 28-32) is created and raced against `withGpu`. If the watchdog fires (timeout), it rejects the race. The `catch` block (line 68) releases the reservation and finishes the batch. However, the `withGpu` callback might still be executing in the background if the GPU driver or ComfyUI socket is hung but not fully dead. The `finally` block clears the timer, but the `withGpu` promise is not cancelled. If `withGpu` eventually resolves or rejects *after* the watchdog has already finished the batch as `failed`, any side effects (like writing files or updating internal state) occur in a zombie state. More critically, if `withGpu` throws an error *after* the watchdog rejection, it becomes an unhandled promise rejection because the race has already settled. While `Promise.race` ignores subsequent settlements, the internal `withGpu` promise is not explicitly cancelled, leading to potential resource leaks or unhandled rejections in the Node.js event loop.
   - **Evidence:** `localBatchRunner.mjs` line 50 `await Promise.race([watchdog, withGpu(...)])`. The `watchdog` rejection does not cancel `withGpu`. The `catch` block handles the race rejection, but the underlying `withGpu` promise continues to exist.
