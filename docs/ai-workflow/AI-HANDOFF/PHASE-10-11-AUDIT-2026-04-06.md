Issue: The blog and social tabs record local success state even when the server call fails. `BlogWriterTab` inserts a draft before the save request resolves, and `SocialDistributionPanel` always queues a scheduled/published post even if the publish request throws. That can mislead admins into thinking content was persisted or scheduled remotely when it only exists in ephemeral client state.
Fix: Only mark success after a confirmed backend response, or explicitly label local-only fallback entries as unsynced/offline state and persist them deliberately.

### 5. HIGH
File: `frontend/src/services/encryption/e2eeCrypto.ts:223`

File: `backend/services/encryption/keyStoreService.mjs:163`
File: `backend/services/encryption/keyStoreService.mjs:176`
Issue: The “signed prekey signature” is not actually verifiable by other clients. The implementation slices raw bytes out of the exported identity private key, uses them as an HMAC key, and signs the prekey public value. Remote clients only know the public identity key, so they cannot verify that HMAC. The code presents a Signal-like signed-prekey model without real authenticity guarantees. It also uses `Math.random()` for the signed prekey ID.
Fix: Replace this with a real signing scheme and a proper signing keypair. If Web Crypto alone is too limiting, use a protocol library that provides actual signed-prekey semantics. Use a CSPRNG or monotonic ID strategy instead of `Math.random()`.

Issue: The server fetch path consumes and returns a `oneTimePreKey`, but the sender never uses it. `useE2EE.encrypt()` always encrypts to `bundle.signedPreKeyPublic`, ignoring `bundle.oneTimePreKey`. That burns one-time prekeys without gaining the intended first-message forward secrecy or anti-replay property.
Fix: Either incorporate the returned one-time prekey into session establishment and message metadata, or stop consuming one-time prekeys until the protocol is actually implemented end to end.

### 7. HIGH

File: `backend/migrations/20260406000001-create-e2ee-tables.cjs:87`
File: `backend/migrations/20260406000001-create-e2ee-tables.cjs:124`
Issue: One-time prekey replenishment can generate duplicate key IDs. The client uses `status.preKeyCount` as the next `startId`, but that value is only the number of remaining unused prekeys, not the next safe identifier. After some keys are consumed, replenishment can recreate IDs that already exist. Local IndexedDB uses `preKeyId` as the object key, so duplicates overwrite stored private keys. On the server, `ignoreDuplicates` does not actually protect against this because the migration defines no unique `(bundle_id, prekey_id)` constraint.
Fix: Track a monotonic next-prekey ID, add a unique database constraint on `(bundle_id, prekey_id)`, and replenish from that monotonic counter rather than from the remaining count.

### 8. HIGH
File: `backend/services/encryption/keyStoreService.mjs:216`
File: `backend/services/encryption/keyStoreService.mjs:222`
Issue: One-time prekey consumption is not atomic. The code performs `findOne` and then a separate `update({ isUsed: true })` with no transaction or row lock. Two concurrent bundle fetches can return the same supposedly one-time prekey.
Fix: Consume prekeys inside a transaction with locking, or use an atomic update-returning pattern so each prekey can only be handed out once.

### 9. MEDIUM
File: `frontend/src/services/encryption/useE2EE.ts:89`
File: `frontend/src/services/encryption/useE2EE.ts:94`
File: `frontend/src/services/encryption/useE2EE.ts:95`
File: `frontend/src/services/encryption/e2eeCrypto.ts:223`
File: `frontend/src/services/encryption/e2eeCrypto.ts:260`
Issue: The automatic low-prekey replenish path also rotates the signed prekey every time it runs. Decryption later reads only the single currently stored signed-prekey private key. That means older messages aimed at the previous signed prekey can become undecryptable after automatic replenish, even though the client was only trying to top up one-time prekeys.
Fix: Separate one-time-prekey replenishment from signed-prekey rotation, keep old signed prekeys until their sessions age out, and include key IDs in session/message metadata.

Issue: E2EE model initialization is treated as non-critical during startup. If model init or sync fails, startup logs a warning and keeps running, but `/api/encryption/*` is still mounted. Subsequent E2EE requests will then fail at runtime with `E2EE models not initialized`, producing unpredictable `500`s instead of a controlled feature-disabled response.
Fix: Gate route availability on successful E2EE initialization, or fail closed and return an explicit feature-disabled `503` until the models are ready.
