## VERDICT
**REVISE** — the tested core (pool law, bundle containment, witness scoping) is solid, but the event write path has a validation hole and an unverified CSRF posture into an *append-only, no-undo* evidence store, and §4's P2 is specced against a validator that would refuse it.

## BLOCKERS

1. **P1 — `validateEvent` has no final `else`: unknown `source` strings bypass the witness law entirely.** The quoted chain (`lib/events.mjs`, validateEvent) is `if (PROFILES.includes(e.source)) {…} else if (SOURCES.includes(e.source) && !allowNonSean()) {…}` — and then nothing. Input: `POST /api/event` with `{"source": "sean2", "profileId": "partner", "projectId": "x", …valid otherwise…}`. `"sean2"` is in neither enum, so **zero errors are pushed**, and `appendEvent` aims it at `partner/x` via `profileOf(e)`. The event is now permanently in the append-only log. `tally` won't count it (counts only `source === witness`), but if `judgedIds(readEventsFor(...))` does not filter by source — the packet never says it does — those candidate ids enter the never-show-twice exclusion set, silently shrinking the pool with no taste evidence behind it. Fix is one line: `else errors.push('unknown source')`. The fact that 214 tests pass without this case shows the suite is happy-path-shaped on the `source` axis.

2. **P1 — the origin gate is evidenced only for `POST /api/projects`; `/api/event`'s posture is unstated, and it is the one write that cannot be undone.** §2 Routes: "`POST /api/projects` sits behind the existing origin gate" — no equivalent sentence for `/api/event` or `/api/keep`. The proof line "foreign-Origin POST → 403" does not name its route. Failure scenario: the owner browses a hostile page; the page fires `fetch('http://127.0.0.1:7331/api/event', {method:'POST', …})` with forged `source:'sean'` grid-selections. If the gate is per-route rather than global, every forged event is **permanently** in the taste brain (append-only, no delete path anywhere in the packet), and the excluded ids poison the pool. This must be verified against code before ship; if the gate is global, write the test that proves it for `/api/event` specifically.

3. **P2 — §4 P2 is specced to fail its own validator.** v1 validation: "candidates are ids + **http(s) URLs**, `data:`/base64 refused anywhere." P2: "candidates = local file ids + **`file://`**/served URLs." As written, the first render-judgement event is refused. Whichever way this is resolved changes a security invariant: admitting `file://` into the event schema also admits it into bundle payloads, where the Midlibrary guard is a *string regex* (`/ml:img:|website-files\.com|midlibrary-reference|midlibrary\.io/i`) — it matches provenance strings, not image content or arbitrary local paths. A render composited from a Midlibrary reference and saved to a neutral path passes the regex. P5's promise ("nothing in a bundle ever carries a render that embeds Midlibrary") is currently unenforceable; say so or scope bundles to shareable-provenance renders only.

4. **P2 — `eventId = sha256(session|type|sorted ids|presentedAt)` excludes the judgement itself, so a corrected judgement of the same presentation is deduped as a duplicate.** Same session, same grid, same `presentedAt`, different closest/miss → identical hash → "already there." The only escape is the `reversal` eventType, and **no reversal UI is mentioned anywhere** — so a misclick after the reason lock is permanent evidence in a system whose entire value is evidence quality. For a daily-use app this is a when, not an if.

5. **P2 — `import-bundle` checks eventId duplicates but not never-show-twice.** Timeline: bundle exported for partner → partner judges grid offline → owner (or partner, on the page) judges overlapping images before import → import records both. `planGrids` excludes `judgedIds` only at *export* time. Result: the same picture judged twice, double-counted in `tally`, and the "a memory never sees the same picture twice" law violated retroactively. Import should refuse (or flag) events whose candidate ids intersect `judgedIds(namespace)` at import time.

6. **P2 — pool exhaustion has no specified behavior.** `probeFor` = pool − `judgedIds`. Shareable pool is 2,722 images ≈ 226 grids; the owner's full pool is smaller per-mix. Daily use hits this in months. What does `/api/probe` return when the exclusion set covers the pool — empty grid, 200 with zero candidates, 500? Unspecified, untested, and it is the exact moment a daily app dies silently.

7. **P2 — check-then-append race on `/api/event` (hypothesis).** Duplicate detection must read existing eventIds, then append. Two concurrent identical POSTs (double-click on Record, retry after a flaky `file://` bundle import) can both pass the read and both append. Node is single-threaded but `fs` is async; unless the dedup-and-append is serialized in one synchronous section or guarded by a write queue, the idempotency proof ("re-import: 2 already there") does not cover concurrency.

## ATTACKS

- **Correctness:** Blockers 1, 4, 5, 7. Also: `tally` counts only `source === witness`, but nothing states `judgedIds` applies the same filter — if flag-gated `agent-placeholder`/`inferred` fixtures ever land in a production namespace, you get exclusion without evidence (silent pool shrink) or evidence without exclusion, depending on which side filters. The `SOURCES` enum carries `imported`, yet the importer writes `source == profileId` with `channel: 'bundle'` — `imported` is dead or legacy; dead enum values in a witness law are drift bait.
- **Security:** Blocker 2 is the big one. Additionally: no rate limit on a 64 KB append endpoint — combined with any gate gap, that is a disk-fill DoS that also *permanently* pollutes evidence. Stored-XSS hypothesis: project `title ≤80` and bundle free-text reasons render into `/brief`; the bundle escapes `<` in its *payload*, but I see no statement that `/brief` escapes titles/reasons — the off-machine bundle is exactly the trust boundary where that matters. The Who-select trust model is acknowledged, but note it also means the partner can accidentally judge as `sean`, and there is no reversal UI (Blocker 4) to repair it.
- **Data-truth / schema drift:** Blocker 3 (`file://` vs http(s)-only) is the headline. Also: `poolFor` reads `pj?.pool` from disk with no stated re-validation — the `profile !== 'client'` guard saves client, but a hand-edited partner `project.json` with `pool:'full'` plus a future bundle-code change that trusts `poolFor` would leak Midlibrary off-machine; the regex backstop is the only thing standing there, and it is string-matching (Blocker 3). Frontend response-shape: `/api/profile` returns `picks` with `pageUrl` — unversioned; the bundle inlines `probe.js`, so any response-shape change must ship bundle-compatible or old bundles break on import.

**§4 direction attacks:** (a) P2's closed loop — taste steers prompts → renders judged → judgements sharpen taste — has a failure mode nobody named: **generator bias becomes taste bias**. The memory sharpens toward what the 5090 renders well, not what the witness loves. Mitigate by capping the weight of `generated`-provenance events in `tally` and keeping real-picture grids in the rotation permanently. (b) P1 weights srefs by `closest − miss` margin, but the owner's own DONE_FLOOR is 8 judgements — margins on n=8 are noise; gate evidence-tier weighting behind a minimum-n per sref, not just the grid floor. (c) P4's four-tab shell will pressure the ≤300-line file rule and must not break `probe.js` inlining into the bundle — that constraint belongs in the plan now, not after the rewrite. (d) Ordering: P1-first is right; but a reversal UI and a `taste/**` backup story are cheaper than P3 and protect everything else.

**House rules:** no MUI/Recharts/yoga-language/credential violations found; 44 px and 414 px proven. Unverified: dark-first and WCAG 4.5:1 are nowhere evidenced; `var(--token,#fallback)` palette usage unstated — and note the judging well *should* stay neutral gray (brand palette in the well would contaminate taste evidence), so scope the palette rule to chrome. This packet is raw HTML with "no build step," which sits awkwardly with "styled-components only" — flag the governance ambiguity rather than pretend it complies.

## HIGHEST RISK

**Unauthenticated, unverified-gate writes into an append-only store with no correction path** (Blockers 1+2+4 compound here: a forged or mistaken write is forever). Cheapest de-risk before ship, in order: (1) one-line `else` rejecting unknown sources; (2) a test proving the origin gate covers `/api/event` and `/api/keep` by name; (3) have `/api/probe` issue the `sessionId` server-side and refuse events for unissued sessions — kills CSRF forgery and double-click races in one move. All three are under a day of work.

## CONFIDENCE

I reviewed a packet, not code. Explicitly unverified: whether the origin gate is global (the "existing origin gate" phrasing suggests it might be — if so, Blocker 2 downgrades to a missing-test finding); whether `judgedIds` filters by `source`; whether `/brief` escapes rendered text; whether append is serialized; what `/api/probe` does on pool exhaustion. Each of these is settleable in minutes: grep the gate registration, read `judgedIds`, read the `/brief` template, read `appendEvent`, and call `probeFor` with a fully-excluded namespace. My highest-uncertainty claim is Blocker 7 (race) — it is inference from architecture, not evidence. My highest-confidence claim is Blocker 1 — the quoted `if/else-if` chain demonstrably has no terminal rejection, and no amount of passing tests with in-enum sources covers it.
