## VERDICT
REVISE — the round-1 fixes mostly hold, but the P2 contract as written cannot survive its own writer gate: render candidates fail `validateEvent` on three enum/URL checks, so "Judge my renders" would be refused at `appendEvent` on day one.

## BLOCKERS

1. **P0 — P2 render grids are unwritable under the current writer law.** §4.5 specifies render candidates with `url: /renders/<token>/<n>`, `provenance: 'local-comfy'`, and events with `generatorDistribution: 'local-comfy'`. §2 `lib/events.mjs:validateEvent` rejects all three: `candidate.url must be http(s)` (`/^https?:\/\//.test(c.url)`), `candidate.provenance must be one of PROVENANCES`, `generatorDistribution must be one of GENERATORS`. Input: a perfectly valid render grid from §4.5 → `appendEvent` returns `{ ok:false }` with three errors. The contract's test plan (§4.8) never lists "extend the enums," so this ships broken. Fix is cheap but must be in the contract: add `'local-comfy'` to `GENERATORS` and `PROVENANCES`, and permit `^/renders/[a-f0-9]{12}/\d+$` as a URL shape.

2. **P1 — `/api/keep` takes `profileId`/`projectId` from the body with no slug validation → path-traversal write hypothesis.** §2 `serve.mjs` excerpt: `const profile = body.profileId ?? DEFAULT_PROFILE, project = body.projectId ?? DEFAULT_PROJECT;` then `keepFor(profile, project, ...)`. `keepFor` gates on `readProject(profile, project)` returning truthy, but neither `isProjectId` nor `PROFILES.includes` is applied. If `readProject`/`keptPath` compose paths by joining (as `eventsDirFor` appears to), a loopback POST with `profileId: '../../taste'` (or a crafted projectId) that resolves to an existing JSON file passes the gate and `keepFor` then **writes** `- <prompt>` into `keptPath` of an arbitrary location. Household trust does not cover this: any process on the box (browser tab on a malicious page can't — origin gate — but any local script can) gets file write outside the namespace tree. Fix: run the same `PROFILES.includes` + `isProjectId` checks in the route before `keepFor`.

3. **P1 — replay double-count is only fixed for grids; `pair` events still replay.** Round-1 disposition claims "Replay with a new timestamp → refused," but the refusal lives in the `e.eventType === 'grid-selection'` branch of `appendEvent`. `eventIdFor` still mixes in `presentedAt`, so a `pair` event re-sent with a fresh timestamp gets a new `eventId`, passes the substring duplicate check, and is appended and tallied twice. Input: same pair, `presentedAt` +1s → two tallied judgements on one presentation. Either drop `presentedAt` from the hash (never-show-twice now carries the anti-replay load) or extend the seen-ids refusal to pairs.

4. **P2 — `tasteFor` contradicts the round-1 disposition on non-Sean labelling.** The disposition table says partner/client taste is "labelled `words-only` until evidence." §2 `tasteFor` returns `tasteSource: 'evidence'` unconditionally for non-default namespaces, even when `loved.length === 0` and the entire payload is theme words. The prompt page's `tasteMeta.source` will therefore claim evidence backing that doesn't exist — exactly the honesty bug round 1 claimed to close. Also `evidenceLoved` admits `closest >= 1` at rating 4, while §4.6 asserts "the evidence floor (2 closest) is unchanged" — one closest currently mints a "loved" sref. Pick one floor and one label.

## ATTACKS

- **Correctness — duplicate check is per-session-file.** `appendEvent` reads `path.join(dir, sessionId + '.jsonl')` and substring-searches it. The same grid re-sent under a *new* sessionId lands in a different file; only the never-show-twice branch saves grids — pairs and any future event type silently duplicate (compounds blocker 3).
- **Correctness — double reversal of one grid is accepted.** The reversal gate checks only that `reversalOf` names a non-reversal event; nothing refuses a second reversal of the same grid. `activeEvents` is set-idempotent so the tally survives, but the log accrues contradictory undo records and "cannot reverse a reversal" is the only storm guard. Cheap fix: refuse if an active reversal already names `reversalOf`.
- **Correctness — `judgedIds` counts pair candidates.** `judgedIds` iterates all active events, not just grids. One pair event permanently excludes those pictures from `probeFor` and blocks any future grid containing them ("refused: N of these pictures were already judged"). If pairs are meant to be lighter-weight judgements, this is an off-by-semantics bug; if intentional, the refusal message ("undo that grid first") is wrong for pairs — there is no grid to undo.
- **Correctness — `keepFor` dedup is fragile.** `md.includes('- ' + text + '\n')` misses a duplicate if the kept prompt is a prefix of another line or if the file's final line lacks `\n`. Low impact (duplicate exemplars), but the `/api/keep` response lies about `kept` counts.
- **Security — `/renders/<token>/<n>` namespace binding is unspecified (IDOR-shaped).** §4.4 says "the requesting namespace" owns the token, but the URL carries only token and n. If namespace comes from a query param or referer, any loopback caller names any namespace and reads its renders; if tokens are treated as bearer capabilities, say so explicitly and drop the namespace check. Specify the mechanism or the tests in §4.8 ("right token wrong namespace → 404") have nothing to bind to.
- **Security — intent minting is unauthenticated loopback and unbounded.** Any local process can mint intents into any namespace (`profile`/`project` are caller-chosen; the origin gate only stops browsers). `intents.jsonl` has no expiry, no cap, no compaction — a daily loop plus one buggy script grows it forever, and every ingest re-scans it. Add a mint-rate cap and a consumed/expired sweep.
- **Security — TOCTOU between ingest and serve.** `index.json` records `bytes` at scan time; §4.4 streams whatever currently sits at the composed path. Anything that can write the ComfyUI output dir can swap a known token's file post-ingest. The planned magic-bytes check (§4.8) mitigates content sniffing; also re-stat size at serve time and refuse on mismatch with the indexed `bytes`.
- **Data-truth / schema drift — `tasteSource` values.** Disposition says `words-only`; code says `evidence`; Sean's branch says `markdown+evidence`. Three vocabularies for one field across table, code, and `tasteMeta` — the frontend will key on one and mislabel the other two.
- **Data-truth — `ratedCount: loved.length` for non-Sean** counts only positive evidence; a memory with 40 misses and 1 closest reports `ratedCount: 1`, inflating confidence inputs downstream (`confidenceOf` sees `positiveCount: 1` but the miss history is invisible).

## HIGHEST RISK

Blocker 1 — the enum/URL drift — because it is certain, not hypothetical: the P2 slice's core action (judging a render grid) is refused by the very writer law this round hardened, and §4.8's test plan doesn't include the enum extension, so it would be discovered in the browser, not in CI. Cheapest de-risk before anything is built: a 10-line contract test that constructs the exact §4.5 render grid event and asserts `validateEvent(e).ok === true` — it fails today and forces the `GENERATORS`/`PROVENANCES`/URL-shape amendments into the contract before the Python node is touched.

## CONFIDENCE

I could not verify: (a) `keptPath`/`readProject`/`projectFile` path composition — blocker 2 is a traversal *hypothesis* that collapses if those helpers slug-validate internally; one quote of `keptPath` settles it. (b) `cli(['--keep', ...])` in `/api/keep` — if it spawns with an argv array, fine; if it string-concatenates a shell command, the sean/default keep path is a command-injection sink; the `cli` source settles it. (c) The contents of `GENERATORS`, `PROVENANCES`, `MEDIA` — blocker 1 assumes `'local-comfy'` is absent; the contract never says it was added, and §4.8 omits it, so I rate absence likely but not proven. (d) `checkWriteRequest`'s treatment of Origin-less loopback POSTs — my minting-abuse point assumes they're allowed. (e) `tally`'s excerpt is truncated, so the 0.5/1.0 partition and the witness filter's interaction with `reversal` events are unreviewable; my design position stands regardless: generated judgements should count **0** toward sref/style tallies (0.5 still lets the loop grade its own homework) and 1.0 toward subjects only. House rules: nothing in the packet violates them (loopback tooling was ruled out of component scope; no forbidden language, no credential claims, no PII).
