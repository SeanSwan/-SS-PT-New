## BLOCKERS
1. **P1 — Blind delete after an await evicts a live owner's claim (`resolveReplay`, catch branch).** The docstring on `claimIfAbsent` states the doctrine — "the identity check that makes a stale release harmless. A blind write is what both were missing" — and `release()` is identity-checked at `localStillLane:141`. But `resolveReplay`'s catch does `store.delete(key)` with no check that the key still holds *the promise that rejected*. Concrete interleaving (single-threaded, FIFO microtasks, no exotic scheduling):
   - A claims K (`store.set(K, P_A)`), renders; B's pre-check hits `replayIfFresh` → `resolveReplay(P_A)` → B suspends on `await pending`.
   - A fails. Its failure reaction is enqueued; C's earlier-awaited gate/brandKit promise resolves in the same tick, so C's continuation is enqueued behind A's.
   - Drain: A's fail handler runs (`release; delete; rej`) → enqueues P_A's reactions [noop, B's catch]; **C's continuation runs next → `claimIfAbsent` succeeds → `store.set(K, P_C)`, C begins rendering (seconds)**; then B's catch runs → `store.delete(key)` **deletes P_C, which B does not own**; B's loop then claims K as P_B.
   - Result: B and C both believe they own K → two renders, two batchIds, two run-cap debits for one idempotency key — the exact k-owners failure round Z closed, reopened through the sibling path. This is the fifteenth pair-defect: the rule holds on every synchronous path (`judge`, `claimIfAbsent`) and breaks on the one write that sits behind an await. It also poisons the `.finally` stub write downstream (C's plain `store.set` of its stub can then clobber B's claim). Fix is two lines: `if (store.get(key) === pending) store.delete(key);` — the orchestrator-already-deleted case still no-ops correctly, and the defense-in-depth for non-deleting callers is preserved.
