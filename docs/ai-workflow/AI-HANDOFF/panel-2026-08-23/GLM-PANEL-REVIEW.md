## VERDICT
REVISE — the direct/execute split is logically sound (and better than the "move/clone/leave" framing), but as written the plan's founding promise fails: brain-dependent scheduled work like the daily briefing has no legal home, and every mechanism that would report a failure lives on the box that fails.

Preamble to the blockers, since it answers §7.1 directly: the operator's *logical* architecture is correct and I would not replace it. The one materially better arrangement is **inverted residency**: the agent *runtime* (Telegram polling, persona, orchestration, queue) moves to radar; Machine A becomes a pure inference appliance (Ollama behind Tailscale). What it buys: the Telegram interface is always reachable, fail-closed becomes *observable* (the agent can ACK and report "brain dark" instead of total silence), and the vault/scheduler/agent-state all get one home. What it costs: a WSL2→Linux port of a 14GB stack, and an inbound-connection fix into NAT'd WSL2 (Tailscale inside WSL2, or mirrored networking, or Ollama-as-Windows-service). Decision rule, stated plainly: if the operator's intent is "no brain, no voice at all," his residency is correct as-is and inversion buys nothing he values. If fail-closed means "never degrade to cloud, but the shell may speak," invert. Either way, add the durable job queue on radar described below.

## BLOCKERS
(Document has no file:line; section citations stand in.)

1. **P0 — Scheduled work that needs the brain violates constraint 5 by construction.** Inputs: the morning briefing timer (§3) fires at 06:30 on radar; state: Machine A off (§2 "not always on"), radar barred from inference (§4.4), fail-closed no-cloud (§3). Output: the flagship scheduled job silently never fires — the exact hostage problem radar was bought to solve, surviving the redesign. Fix: partition scheduled jobs into *deterministic* (radar; briefing becomes a template-based digest) and *brain-gated* (queued on radar, drained when A wakes). radar is the sole time authority either way.

2. **P1 — Agent liveness is fused to brain liveness, plus Telegram replay.** Single polling consumer on a sometimes-off machine (§4.2, §3): desktop off → operator's messages get no ACK; Telegram retains unpolled updates ~24h → next boot executes hours-stale directed commands against changed state. Crash before the offset commits → duplicate side effects on radar. Fix: on startup, drain-and-ack updates older than N minutes with a "skipped N stale commands" notice; persist offset before executing; idempotency keys in radar's executor.

3. **P1 — The dead-man's switch monitors itself.** §6 places the heartbeat on radar. radar's disk fills (217GB; host logrotate does **not** cover Docker's json-file container logs; pinned images accumulate) → timers, database, and heartbeat die together; nobody is paged. Fix: external dead-man service (healthchecks.io-class) plus send-only Telegram receipts from every radar timer — *sending* via the bot API does not violate the one-poller rule (§4.2 bans a second poller, not a second sender). "radar is never on Telegram" (§6) is over-broad as written and creates this gap.

4. **P1 — No backup exists anywhere in this plan for the irreplaceable asset.** A 3.2GB / 4,742-file vault built over months (§3), on a sometimes-off desktop, proposed to move to one always-on consumer disk. Single-machine loss = months gone. Fix before any migration: restic to an encrypted cloud target (~cents/month at this size), 3-2-1. This answers §7.4: vault canonical on radar (with the reader and scheduler), Syncthing working copy on A for editing — never two canons.

5. **P1 — "No sudo" (§4.6) is theater if the service account touches Docker.** docker-group membership is root-equivalent. Worse, §6/Q5 put coding agents — which *execute model-generated code* — on the same box, under the same account, as one-time browser-auth profiles and SSH keys. One poisoned npm postinstall exfiltrates the browser profile and ladders to A over the tailnet. Fix: no Docker socket for the service account; per-concern `DynamicUser=` units with `ProtectSystem=strict`; agent-run containers `--network none` by default; forced-command keys; receipts tagged with origin (operator | timer | agent) or the audit requirement (§3) is unauditable.

6. **P2 — Two schedulers during and after migration.** Agent-native crons on A (§3) plus new systemd timers on radar = two sources of truth (this answers §7.3: no, it is not clean as written). Concrete: radar ingest fires 06:00; operator powers A at 06:05; legacy cron ingest 06:10 → two writers, duplicate rows / unique-violation crashes. Fix: one job manifest in git from which systemd units are *generated*; disable A's crons in the same changeset; run a shadow week diffing old vs. new outputs.

7. **P2 — "Permanent residence" on A assumes resurrection nobody built.** Power blip → Windows reboots to a lock screen → WSL2 never starts → agent dark despite the machine being "on." Post-sleep WSL2 clock skew then breaks TLS/Tailscale sessions. Fix: boot-time task to start WSL + stack (or Ollama as a native Windows service), timesync on resume, and one practiced cold-boot→agent-up drill.

## ATTACKS
- **Correctness:** Orphaned long jobs — a coding-agent run on radar outlives A's power-off; with the agent as the only Telegram voice, the result has no return path. Fix: durable queue on radar (file or Postgres `SKIP LOCKED`; no new broker) plus radar-side send-only receipts. OOM contention on 16GB: Postgres + headless Chromium + Node CLIs + nightly vault ingest, with systemd-oomd and no per-unit `MemoryMax` → the postmaster gets killed mid-WAL. Fix: per-unit memory ceilings, swap/zram, coding-agent concurrency = 1 (singleton unit + flock). Non-idempotent ingest reruns after partial failure → duplicates; make idempotency a per-timer acceptance test. §7.5 verdict: coding agents on radar is the *right* placement — they act on radar's services and checkouts — but only under those caps, and only if the projects they edit live on radar; browser harness on radar is unambiguously correct (desktop-off browsing was previously impossible), with approval kept synchronous and out of the scheduled path.
- **Security:** Tailscale is installed but *unauthenticated* (§2) — until joined there is no overlay, and after joining, node key expiry can silently evict radar from the tailnet, leaving a headless box with no iGPU console unreachable. Fix: disable expiry for this node, enable Tailscale SSH, keep LAN sshd as break-glass; verify sshd hardening now. Pinned image tags (§6) + host-only unattended upgrades = patched host, frozen containers: a pinned Postgres with a CVE stays because nobody owns the bump. Fix: weekly grype timer whose output is a send-only Telegram receipt. Transport (open sub-question): agreed, extend the existing bridge — but add per-principal credentials with forced commands, request-IDs for retry idempotency, and an executor egress allow-list. **House-rule flag — "zero PII to LLMs (IDs only)":** the vault→local-LLM path (§3) is in literal tension. My judgment: an operator-personal vault to a local, fail-closed, no-cloud model is within the rule's spirit; any SwanStudios *client* PII inside retrieved chunks is not. Settle it with a retrieval-time scrub/ID-substitution layer or a recorded scope ruling. The fail-closed posture itself is the compliant half — keep it.
- **Data-truth / schema drift:** Job-definition drift between the agent's ~12 hand-iterated config revisions and radar's units is the default outcome absent generation from one manifest (§7.3's real risk). Vault dual-home drift (§7.4): two canons without a sync tool means edits on A vanish from retrieval on radar. Result-state split: the agent's memory of "what I directed" vs. radar's queue/results — receipts must be the single record, and their schema (origin, request-id, exit code, duration, artifacts) must be decided now or the audit-receipt requirement decays into unqueryable text. The PascalCase/snake_case analog here: twelve manual config revisions guarantee key-naming drift; normalize once during the move while everything is being touched anyway.

## HIGHEST RISK
**Silent failure of the always-on promise**: radar can die (disk-full, OOM, tailnet eviction) in ways that also kill the only thing that would report it — while the flagship brain-dependent job was never schedulable there at all. Cheapest de-risk, one afternoon: (1) external dead-man pinger; (2) send-only Telegram receipt from every radar timer; (3) restic backup of the vault; (4) one deliberate radar reboot test and one cold-boot drill of A. De-risk by deletion (§7.6): approval gates on *scheduled* browser runs (approval is for directed work only), any second transport, any message broker, and the plural in "coding agents" — start with one CLI at concurrency 1. One cheap experiment before accepting "remote wake is dead" as permanent: BIOS "restore AC power state = on" plus a LAN-local smart plug is a wake path that survives dead WoL (~$20; mind BitLocker/autologon before relying on it).
