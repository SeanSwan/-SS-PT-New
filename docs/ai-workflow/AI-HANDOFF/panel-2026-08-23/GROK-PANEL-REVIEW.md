## BLOCKERS
1. **P0 — Telegram consumer dies with Machine A; pending updates expire.** Operator sends a Telegram message while the desktop is off/asleep/WSL2 not running → no `getUpdates` consumer exists (§6: “radar is never on Telegram”; §4.2: exactly one polling consumer; §3: Telegram is the interface; §2: Machine A is not always on, remote wake dead). Telegram holds unread updates ~24h then drops them. Fail-closed inference was the requirement; fail-closed *interface* is an unstated extra that makes the always-on box invisible to the only human channel. A “brain offline, queued” ack is not a cloud-LLM fallback and does not require a second identity.

2. **P0 — Directed work has no working transport today, and the proposed one is the wrong shape.** Agent in WSL2 NAT (§2) must “reach radar over the private overlay and execute there” (§6) but Tailscale on radar is “installed, unauthenticated” (§2). Current state → overlay down, WSL2 NAT may not see Tailscale IPs even after auth, Windows sleep kills WSL even when the tower is “on” → directed work silently does not run. Extending a remote coding bridge as the general exec fabric turns an interactive dev tunnel into unattended RCE with no allowlist, no idempotency keys, and no audit story.

3. **P0 — No-sudo service account cannot own the scheduler it is assigned.** §4.6: jobs run as a no-sudo account. §6: “radar owns its own scheduler” via systemd timers. User-level timers need linger (root, once); system timers need root every change. Hermes therefore cannot turn directed work into durable scheduled work (“brief me every morning”, “retry when the GPU is back”). Native agent cron (§3) will keep existing → two writers, double-fires or dropped jobs. systemd is a runner, not a source of truth, and this account cannot even write the runner’s config.

4. **P1 — Coding agents + browser harness on radar cannot authenticate and will OOM the box that holds the database.** §7.5: one-time browser auth. §2: headless, no GUI. §4.7: preferred remote GUI “impossible”; SSH only. OAuth/device-login for Codex/Claude CLI/browser harness has nowhere to complete without copying session cookies over SSH. Same 16GB Zen 1 box also runs Docker, Node 22, pinned DB containers, and a Chromium harness (§2, §6). Input: Claude CLI + one Chromium + Postgres/SQLite under load → OOM killer → DB process dies on the always-on source of truth.

5. **P1 — Brain-shaped scheduled jobs fire into a black hole with no catch-up.** Daily morning briefing (§3) needs vault + 27B model. systemd on radar fires it while Ollama is unreachable (§3 fail-closed; §2 Machine A off) → fail or empty draft; desktop later powers on → nothing replays unless a job ledger exists (it does not). §4.5 (“must fire regardless”) is only true for jobs that do not need the brain; the packet never inventories which jobs those are.

## ATTACKS
- Correctness: Happy-path-only split of “systemd = must-happen, agent = directed.” Directed work *becomes* scheduled work; there is no job table, no lease, no replay when the GPU attaches, no idempotency key, no single writer. Agent cron (§3) + systemd timers (§6) = double-run after a partial migration. “Desktop powered on” ≠ “WSL2 agent stack up” (WSL2 does not linger at boot unless explicitly configured; Windows sleep is not “off” and is not wakeable). Vault left on A means radar ingest/briefing reads stale or zero files; vault copied both ways without a single primary = silent 4,742-file split-brain. Coding-agent memory and Hermes persona will disagree about what was done on radar. Browser-harness “read-only by default / per-run approval / audit receipt” has no approval path when the operator is on a phone and the harness is headless on B. Pinned image tags do not pin Docker Engine, kernel, or volume schema.

- Security: §6 is remote execution by design, commanded by a Telegram bot token (single-factor, phishable, replayable). Blast radius is the always-on box, not the sleeping workstation. No allowlisted verbs, no forced-command SSH, no per-job approval for non-browser actions, no mention of where bot token / Claude / Codex keys live (always-on disk is the worse place). Tailscale still unauthenticated = the “private overlay” is not a security boundary yet. Browser harness + coding agents on an always-on host with network and a DB is a persistent foothold; “human ships outward-facing” does not stop a tool with a git or cloud credential from shipping anyway. Two-machine approval is split-brain: when A is off, either jobs run unapproved or they never run.

- Data-truth / schema drift: Vault primary unspecified → Obsidian-style paths and IDs will drift from whatever retrieval the brain used last. Scheduler state in unit files vs agent config vs any future DB on radar = three schemas for “what should run.” Containerized DB on B vs whatever the desktop agent already wrote locally. Audit receipts, harness cookies, and persona/config (12 revisions) stay on A while execution moves to B → receipts that do not match actions. Frontend response-shape / PascalCase / MUI / Recharts: not in this packet; no house-rule UI violations present. Do not invent a second transport that speaks a different job JSON than the “proven” coding bridge.

## HIGHEST RISK
Live “agent directs; radar does” remote exec on the always-on box, authenticated by Telegram, over an overlay that is not even up, with coding-agent secrets and a database as neighbors. Cheapest de-risk before any further build: **delete the control plane.** Radar is an independent worker with one job ledger (sqlite or a directory of signed job files) as the only source of truth; systemd only ticks “any due row?”; desktop may *enqueue* allowlisted job types when it is on; no shell, no coding bridge, no Telegram on two hosts. Put vault primary on radar (desktop mounts or pulls retrieval chunks). Optional and separate: move the *single* Telegram poller to radar as a mailbox that acks/queues and never generates. Keep Ollama, Hermes interactive tools, Codex/Claude CLI, and the browser harness on the 5090 machine that has VRAM, RAM, and a GUI.
