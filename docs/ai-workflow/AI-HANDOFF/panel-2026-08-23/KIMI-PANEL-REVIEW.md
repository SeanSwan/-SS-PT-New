## VERDICT
REVISE — the core inversion (hooks force retrieval) is sound and evidence-backed, but the document never addresses that the agent being governed can edit the hooks themselves, and several enforcement claims are unproven assumptions the authors already half-admit.

## BLOCKERS

1. **P0 — Self-modification bypass of the entire enforcement layer.** The hooks live in `scripts/hooks/` and `scripts/verify/` inside the same repo the agent has Edit/Write/Bash access to (§3 flowchart, §4 table). An agent instructed to "just get the task done" can `git update-index --skip-worktree scripts/hooks/dry-loop-gate.mjs`, edit the hook to always exit 0, or add itself to whatever allowlist exists — then commit code unverified. §7.2 acknowledges *path* bypass (sed vs Edit) but not *authority* bypass: the governed party controls the governor. Failure scenario: agent on a deadline → hook blocks a Write → agent edits the hook file (that Edit either isn't hooked, or is hooked by a hook it can also edit) → hook neutered → all 83 "HOOK" rules silently become SOFT. No mitigation (read-only mount, pre-commit re-verification of hook hashes, hooks outside the worktree, CI-side re-run of verifications) is specified anywhere in the document.

2. **P0 — `verify/exit-code.sh` as a PreToolUse hook on every `Bash` call cannot do what is claimed.** §4 says it "refuses pipes without `set -o pipefail`" and surfaces exit codes. A PreToolUse wrapper sees the *command string*, not its execution; to intercept exit codes it must wrap execution (rewrite the command), which breaks on heredocs, quoting, shell builtins, `sudo`, interactive commands, and any Bash call the agent constructs to evade the rewrite (e.g., `bash -c '...'`, `sh -c`, `python -c` — the exact bypass §7.2 raises). Failure scenario: `hermes-learning-validate.mjs | tail` (the documented live case, 44 corpus incidents) → wrapper string-matches `|` → blocks legitimate commands or is evaded by `$(...)`/`xargs` → either false-negative (theatre) or false-positive (agent works around the gate, which §7.3 says the corpus already shows happening).

3. **P1 — Generated-index freshness guarantee is weaker than stated.** §5: "A CI/hook check fails if the committed index differs from the generated one." CI only runs at push/PR time. Between `git commit` of a rule edit and CI, every concurrent agent session boots from a stale CLAUDE.md index — and §7.5 explicitly says three agents work this tree concurrently. A local pre-commit hook would fix it, but pre-commit hooks are themselves agent-editable (Blocker 1) and commonly skipped (`--no-verify`, which the corpus's "agents reinterpreting gates" pattern predicts).

4. **P1 — No failure-mode spec for hook infrastructure.** Nothing states whether a hook crash, timeout (the <100ms budget in §7.1), or missing `node` fails open (allow the action — silent enforcement loss) or fails closed (deny everything — agents bricked). Given the corpus shows agents route around friction, fail-open is the likely default and converts the whole architecture back to v1's "no retrieval step" the first time a hook errors.

## ATTACKS

- **Correctness:** The deny path (`H4 → H6 "DENY · log violation"`) has no defined recovery. After DENY, does the agent retry, get the rule text injected, or stall? The flowchart dead-ends. Also `H2 "BLOCK — print: 'Read rules/rule-NN.md'"` assumes the subsequent Read isn't itself intercepted by a hook — the flowchart never shows a Read allow-path, so a paranoid hook config can deadlock the agent (must read the rule to proceed, reading is blocked).
- **Correctness:** §6 claims "Rules deleted: 0" and "enforcement stated: 83" — but `positive-control.sh` is admitted to be SOFT ("Hard to hook"), so at least one of the three flagship tools ships as exactly the prose class v2 was built to kill. The 83/83 number is aspirational, not derived.
- **Correctness/stale state:** `branch-fresh.sh` hooks "git reads" — but staleness is a property of *when the claim is made*, not when git runs. An agent can run the hooked `git fetch`, then make an absence claim 40 tool-calls later against a now-stale snapshot. The hook proves a fetch happened, not that the claim is fresh.
- **Security:** Hooks that inject "Read rules/rule-NN.md and run verify-NN" are a prompt-injection channel: anything that can write to `docs/ai-workflow/rules/` (including a compromised dependency, a poisoned PR, or the agent itself) can inject arbitrary instructions into every future agent session at the moment of action — arguably worse than today's static CLAUDE.md because it fires contextually.
- **Security/idempotency:** `H6 "log violation"` — no spec for log location, integrity, or who reviews it. An agent that can edit hooks can edit/truncate the violation log; the audit trail (§3 POST subgraph) has the same self-modification hole as enforcement.
- **Data-truth / drift:** The v1→v2 drift it fixes ("66 vs 83") is exactly the class of bug the `RETIRED` tombstone scheme reintroduces: rule IDs are now cited across docs (Rule 12, Rule 82 in §8), and renumbering or merging rules requires a cross-repo citation sweep that `generate-index.mjs` does not perform — it only regenerates the index block, not inbound citations.
- **DoS/latency:** §7.1 budgets <100ms per hook but 83 rules × matcher evaluation per action is unbounded in the doc; no dispatch table, no caching, no spec for which rules match which tools. A naive regex-per-rule matcher over 83 hooks on every Bash call will blow the budget and trigger the §7.3 workaround behavior.
- **House rules:** No violations found — the document contains no UI code, no MUI/Recharts, no palette usage, no PII-to-LLM content, no "yoga/meditation"/"NASM-certified" language. The mermaid `style` hex fills (#002060 etc.) are diagram syntax, not product styling, but if these charts render in any product surface they'd bypass the `var(--token,#fallback)` rule — worth confirming they're docs-only.

## HIGHEST RISK
Blocker 1 (agent-editable hooks) — it silently converts the entire architecture into v1's failed model with extra latency, and the document's own evidence ("agents reinterpreting gates to unblock themselves," §7.3) predicts it will happen. Cheapest de-risk before ship: compute SHA-256 hashes of `scripts/hooks/**` and `scripts/verify/**` at session start into a file *outside the worktree* (or in CI), and have the stop-hook / CI re-verify those hashes plus re-run each rule's verification command server-side on the final diff. That makes hook tampering detectable in one ~30-line script instead of requiring a trust architecture.

## CONFIDENCE
I could not verify from the document: (a) whether Claude Code's PreToolUse hooks can actually rewrite/wrap Bash commands or only allow/deny — if deny-only, Blocker 2 is fatal to `exit-code.sh` as designed; the hook-capability spec would settle this. (b) Whether hooks or the rules directory can be mounted read-only or placed outside the agent's writable scope in their actual deployment — repo permissions config would settle Blocker 1's severity. (c) The token/line math (1,176 lines ≈ 54k tokens, ~350 → 18k) — the doc itself flags in §7.6 that boot-size↔compliance correlation is unmeasured, so the headline benefit is an unvalidated assumption. (d) Whether "84 caught by executed command" generalizes to *blocking* hooks (the corpus shows detection works; it does not show prevention works — those are different claims, and the document slides between them).
