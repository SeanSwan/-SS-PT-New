Evidence: `usePostCardModeration.ts:47-49`; `PostHeader.tsx:177-179`; blueprint comment `:20` (`future: POST /api/mute`). **Remove the item this week; do not implement mute as the P0 fix.** A missing control is honest; a fake one is harassment-exposure. ## ATTACKS
- Correctness: Happy-path lie is the pattern, not the exception. `noopUpdateProfile` / `noopOpenEditor` turn “optional callback” into “always success” (`UserDashboardTabsV3.tsx:105-106,248-249`) — null/undefined is the case that should hit the network fallback, and it never does. Two mount sites, easy to patch one and miss the other (`UserDashboard.V3.tsx:128` vs `:183`). Slider is a classic omitted-setter freeze (`PostCard.tsx:56`). Mute is an unhandled TODO on a click path that swallows the error by never trying (`usePostCardModeration.ts:47-49`). WorkoutsTab page-1/limit-200 is an off-by-pagination under-report with no error/empty-vs-truncated distinction (`WorkoutsTab.tsx:91`). The save “test” is source-text regex — it cannot catch the noop, races, or a renamed import. **Prescribed settings fix is wrong if it is “let the PUT fallback run”:** `UserSettingsHub.tsx` itself was never pasted; the else-PUT is inferred from a grep test. Sufficient fix is: pass `onUpdateProfile={dashboard.updateProfile}` at **both** mounts, stop coalescing to noop (pass `undefined` through), and add a render test that asserts the write. Fallback-only leaves the sibling editor path and any future truthy stub open.

- Security: Fake mute is an authz-UX hole — the member performs a protection action and the system does not apply it. Privacy/visibility fields riding the same dead settings save are worse than units not sticking: user thinks transformation photos went private and they did not (IDOR-adjacent exposure, not a classic IDOR). Profile `PUT` authn/authz, IDOR on `post.user.id`, and whether mute/block/report are server-enforced were not in the packet — do not “implement mute” until those exist, or you ship a client-only hide that another session/device undoes. Unverified “role-aware routing bypassed by hard-coded client paths” would be a real authz bug if true; it is not evidenced here, so it is not a P0 you can schedule. `logger.warn(..., post.user.id)` is IDs-only (house-rule safe) but still a stub.
