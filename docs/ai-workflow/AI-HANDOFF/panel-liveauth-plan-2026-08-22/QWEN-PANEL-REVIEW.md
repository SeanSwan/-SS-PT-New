## ATTACKS
- **Completeness**: The plan misses **concurrent edit conflicts**. If two users (or the same user in two tabs) edit the same privacy setting simultaneously, what happens? The plan assumes a single-user, single-session verification. It also misses **network failure states**. What if the save request times out? Does the UI revert? Does it show an error? The plan only tests the "happy path" of persistence.
- **Correctness of the settled claims**: The claim "There is no member-reachable photo upload" (§3) is settled on the evidence that "No presign or direct-upload leg exists." However, this is a *current state* observation, not a *security guarantee*. If the `POST /api/photos/:userId` endpoint is exposed and accepts a `storageKey` that can be guessed or enumerated, a malicious user *could* upload photos by bypassing the UI. The plan treats the absence of a UI button as proof of security, which is a classic "security through obscurity" fallacy. The next agent should verify that the *API* itself rejects unauthorized uploads, not just that the UI hides the button.
- **Process/safety**: The plan instructs the agent to use `agent-browser` or `Playwright MCP` (§2). These tools often run in headless or semi-headless modes that may not trigger all client-side JavaScript events (like `pointerup` or `dragend`) in the same way as a real browser. The plan assumes the automated harness will behave identically to a human, which is not guaranteed. The "live authenticated pass" is supposed to be a *human* check, but the plan offers automated tools as the primary route, creating a mismatch between the intent (human verification) and the method (automated simulation).
- **Self-defeat**: The plan claims to fix "surfaces that claim a capability they do not have." Yet, the verification step itself relies on the agent *assuming* the capability works unless they explicitly break it. The "hard-refresh" check is a passive observation, not an active proof. If the agent sees the value persist, they assume the fix works. But if the fix *only* works for specific data types (e.g., integers but not strings), the agent might miss it. The plan does not specify *which* values to test, leaving the agent to guess.
