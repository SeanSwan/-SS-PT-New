### One correction I had to make to my own work

While writing the loop tests I concluded that the `revealStart === 0` sentinel was a real
bug — a first frame at `ts = 0` would re-anchor the clock forever. I traced it rather than
trusting the reasoning: **it is not observable.** On a 0-anchored clock the reveal still
settles at ts=720 on a 16ms cadence, because `requestAnimationFrame`'s own timestamp is
what anchors it and elapsed time coincides with absolute time. Reverting the sentinel
passes all 13 loop tests.

The `null` sentinel stays — it removes a trap that any caller supplying its own clock would
hit immediately — but the code comment and the test comment now say "latent, not observed"
rather than claiming a bug I did not demonstrate. I also corrected the test itself, which
had been written as a regression guard for something it cannot catch.

## BLOCKER — the git object store is damaged, so no commit can be recorded

Found while surveying the tree for a careful commit. **`git commit` cannot run in this
repository at all.** This is independent of anything A8 did; it predates this session.

The immediate symptom, reproduced twice:

```
$ git commit --dry-run --allow-empty
error: Could not read 3bc947da508852ae07c87c02bf79abc12bd96269
error: could not parse commit 3bc947da508852ae07c87c02bf79abc12bd96269
fatal: bad revision '99b970bd40748758d5f943ee254a43730767bc7b...4c93db148fcee179385cb44b83953a49e9061af4'
```

**Root cause: `HEAD^` is a missing object.** `HEAD` is `99b970bd40748758d5f943ee254a43730767bc7b`
(moved from the session-start `6e45e2392f`); `git cat-file -p HEAD` parses fine and reports
`parent 3bc947da508852ae07c87c02bf79abc12bd96269` — and that parent cannot be read. Git needs
to walk history to build a commit, and it cannot walk past the gap.

### What survives, and what does not

| probe | result |
|---|---|
| `git cat-file -p HEAD` | **OK** — `tree 6e351e7f`, author SeanSwan, *"docs(round8): inline every artifact…"* |
| `git ls-tree HEAD` | **OK** — 77 entries. HEAD's own tree is intact. |
| `git cat-file -e HEAD:frontend/package.json` | **OK** |
| `git rev-list HEAD` | **FAILS** — *Failed to traverse parents* |
| `git commit` | **FAILS** — `fatal: bad revision` |
| `git reflog` | **empty** — `.git/logs/HEAD` does not exist |
| `git fsck` | 218 missing blobs, 37 missing trees, 4 missing commits, 40 broken links from 40 trees, 9 unreadable objects |

**This is not total loss.** HEAD's tree is readable, so the current state of every tracked
file is recoverable. What is lost is the *history behind* HEAD and the ability to *append*
to it. The 2,134 dangling blobs and 380 dangling commits fsck reports are unreferenced
objects still on disk — some may be recorable, none are reachable from HEAD.

Collateral corruption in the same store:
- 9 stale `.git/next-index-*.lock` files (these would block index writes even if history were fine)
- 3 `.git/objects/*/tmp_obj_*` garbage objects
- 13 `invalid sha1 pointer in cache-tree of .git/index` — the index itself is inconsistent
- Three sibling worktrees carry their own corruption:
  `.git/worktrees/ss-media-api/index` (3 cache-tree errors),
  `.git/worktrees/swan-coach-astra-owned-20260906/index` (5 cache-tree errors),
  `worktrees/ss-media-api/HEAD: invalid reflog entry` (5 errors)

### Why this must not be "fixed" by me

`git fsck` shows 380 dangling commits. Several plausible repairs exist — pruning the gap,
grafting, re-initialising — and **every one of them writes to the object store**. Writing to
a damaged store with 218 missing blobs and 380 dangling commits risks making the loss
permanent, and the dangling objects may themselves be the material worth recovering. This
needs a human decision (or a proper recovery tool) with a full copy of `.git/` taken first.
No repair was attempted.
