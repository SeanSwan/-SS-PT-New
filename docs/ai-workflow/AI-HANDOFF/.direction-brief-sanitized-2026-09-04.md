# Direction brief — sanitized external review

You are an advisory architecture/orchestration reviewer. Do not edit files,
invent deployment proof, or treat this brief as authorization to ship.

Context deliberately excludes repository names, paths, credentials, customer
data, owner identity, and infrastructure identifiers:

- A production personal-training SaaS uses a React/TypeScript frontend and a
  Node/Express/PostgreSQL backend.
- A non-breaking open-source component upgrade program has already shipped
  payment-client centralization, shared validation, an accessible dialog
  primitive, durable-worker scaffolding, DSN-gated error reporting, CI-gate
  work, and executed webhook-redelivery proof.
- Remaining work is mostly owner-gated closure: confirm an external payment
  configuration before a later compatibility phase, make CI enforcement real,
  configure the error-reporting destination, and enable the durable worker only
  after a restart proof and a safe observation window.
- The primary checkout is intentionally dirty; isolated workspaces are used for
  build slices.
- Existing model consultation tooling has two subscription review seats on the
  same provider lineage, a single-flight lock, a bounded review-round budget,
  a seat registry, and lane coordination. Provider output is advisory; the
  active builder must reproduce claims locally.

Questions:

1. What is the highest-value next engineering slice? Rank owner-gated closure,
   CI reliability, release/observability, and new OSS work. State what waits.
2. What is the smallest durable queue/lease protocol for model consultations
   and delegated build slices when seats are busy? It must prevent duplicate
   dispatch, expose busy/free state, tolerate stale workers, preserve model
   identity and receipts, and fail closed on ambiguous state.
3. What belongs in local scripts/docs versus an external scheduler or task
   coordination layer? Do not recommend a broad rewrite or an unreviewed
   API/base-URL proxy.

Response contract — these labels are mandatory machine-checkable fields, not
optional suggestions:

- The first non-heading line under `## VERDICT` must begin exactly with one of
  `APPROVE`, `REVISE`, or `REJECT`.
- Under `## BLOCKERS`, include either `No P0/P1/P2 blocker reproduced.` or
  numbered findings beginning with `P0`, `P1`, or `P2`. Every numbered finding
  must also include `Scenario:`, `Evidence:`, and one of `Correction:`,
  `Test:`, or `Vector:`.
- Across the response, include literal labeled fields `Scenario:`,
  `Evidence:`, `Verified:`, `Reproducible:`, `Confidence:`, and
  `Uncertainty:`. Use `UNPROVEN` when a fresh probe is required.
- Do not put the verdict only in prose, and do not omit a field because there
  is no blocker; write `No ... reproduced` or `Not tested — UNPROVEN`.

Return exactly these headings: `## VERDICT`, `## BLOCKERS`, `## ATTACKS`,
`## HIGHEST RISK`, `## CONFIDENCE`. Use `VERIFIED`, `LIKELY`, and `UNPROVEN`.
Give ordered actions and a minimal queue state machine/schema. Call out every
assumption that needs a fresh local probe.
