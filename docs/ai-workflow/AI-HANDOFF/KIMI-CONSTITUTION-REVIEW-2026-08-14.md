**(a) VERDICT: SHIP-WITH-CHANGES** — the repair is sound and the guard is real, but the guard's threat model is narrower than the incident it claims to prevent, and one claim in the packet is unsupported.

---

**(b) DEFECTS, most severe first**

**D1. The guard does not catch the actual failure class it was built for.** The incident was a *stale-copy clobber*: an agent rewrote the whole file from an old snapshot. The guard catches the *symptom* (rule removal/renumber) only when the clobber deletes or renumbers rules. A stale-copy clobber that **rewrites rule bodies in place** — same names, same numbers, older text — passes all three checks cleanly. That is exactly what a context-snapshot overwrite does to rules the agent didn't intend to touch. Exact breaking scenario: agent holds a snapshot from Monday; on Wednesday a rule body is amended (e.g., the review-gate policy in rule 46 — note the incident *itself* included a body reversion of rule 46, not just deletions); on Friday the agent regenerates from Monday's snapshot, preserving its own edit. Names intact, numbers intact, mirror regenerated so drift check passes. Guard: green. Law: reverted. The packet's own incident included a body reversion ("reverted rule 46 from a newer review-gate policy to a superseded one") and the guard as specified would **not** have blocked that part of the commit. This is the central hole and the packet buries it in question 1 instead of listing it as a defect.

**D2. The escape hatch is keyed by HEAD number and never expires — it is a persistent bypass credential.** `SWAN_ALLOW_RULE_REMOVAL="46,73"` authorizes removal *and* renumber of those rules. Nothing scopes it to one commit. Exact scenario: an agent (or a shell profile, or a CI env var left set after the repair) exports the var once; every subsequent commit can silently delete rules 46 and 73 forever. The guard "prints its verdict on every path" but a printed "allowed by override" line in a wall of pre-commit output is not a control. The hatch should be single-use (e.g., require the value to also appear in the commit message trailer, so the authorization is bound to the commit and auditable in history).

**D3. Fail-open on git errors contradicts the stated purpose.** "Cannot block unrelated work" is backwards reasoning for a guard whose entire value is catching silent clobbers. Exact scenario: `git show HEAD:CLAUDE.md` fails for any reason (corrupt object, partial clone, shallow checkout in CI, PATH hijack shadowing `git` with a stub) — the guard exits 0 and the clobber sails through *precisely when tooling is already misbehaving*. Fail-open should be restricted to "no HEAD yet" (initial commit); any other git error should fail closed with a loud message. A guard that fails open on its own infrastructure errors is a guard that fails exactly when you need it.

**D4. The mirror-drift check is trivially satisfied by the clobber itself.** Check 3 verifies AGENTS.md == mirror of CLAUDE.md. But the incident's aggravating factor was that the prescribed fix *regenerates AGENTS from CLAUDE*. Any commit that includes both the damaged CLAUDE.md and a regenerated AGENTS.md passes check 3 by construction. The drift check only catches *partial* commits (CLAUDE changed, AGENTS not regenerated). It provides zero protection against the documented failure mode and should not be counted as one of three defenses — it's a consistency check, not a clobber check.

**D5. Unsupported claim: "7/7 pass" and "live-fired against the real repair."** The packet asserts test results with no harness output, no commit reference to the tests, and no way for a reviewer to verify. Given the packet elsewhere boasts "all counts machine-verified," the absence of verifiable evidence for the guard's own test suite is conspicuous. Also unsupported: the claim that the guard "blocked the repair's own legitimate renumber" — plausible, but asserted, not shown.

**D6. The repair's splice script "refuses to write if a splice would be a no-op" — but the merge itself was one-shot and unaudited.** The 13/4 hunk split was adjudicated by a human reading. There is no recorded per-hunk rationale artifact. If the 4-vs-13 call was wrong on even one hunk, the error is now in *both* files and, per §3's own logic, invisible to diffing forever. The repair needed a written per-hunk decision log committed alongside; the packet doesn't mention one.

**D7. Post-condition "0 unadvertised capabilities" is asserted for a hand-maintained table with no new enforcement.** §3.3 says the table drifted 43% while a runtime validator passed. The repair fixed the table once. Nothing in §4 or §5 adds a check that keeps it fixed. This defect regenerates on the next capability addition. (See answer 7.)

**(c) ANSWERS TO THE SEVEN QUESTIONS**

**1. What passes all three checks and changes the law:** any body rewrite preserving name and number — weakening "MANDATORY" to "recommended," changing a threshold, reverting a policy (as rule 46 was reverted in the incident itself), deleting an enforcement paragraph. This is **not acceptable** — it is the incident's own mechanism. A full body-hash ledger is overkill; the cheap correct fix is: hash each rule body at HEAD, and on any body change to a rule tagged MANDATORY, require a commit-message trailer (`Rule-Change: 46`) naming the changed rules. That converts silent body edits into declared ones without blocking honest edits. Diff the body, don't freeze it.

**2. Name-keyed matching:** rename+renumber in one commit reads as removal+addition and produces a **false block** — but a *useful* one, provided the escape hatch names it. The danger is training bypass. Fix: when the guard sees removal-of-X plus addition-of-Y in the same commit, it should say "possible rename of X→Y; if intentional, declare `Rule-Rename: X=Y`" rather than dumping the operator into the generic removal hatch. Rename is a first-class operation; treating it as an error is what trains `--no-verify`.

**3. `--no-verify`:** pre-commit is a convenience, not a control. The guard belongs in CI **in addition** — client-side for fast feedback, server-side for enforcement. Cheapest CI form: a single job running the same `constitution-guard.mjs` against `origin/main...HEAD` on every PR, plus (if the platform allows) a required status check. That closes `--no-verify` and direct pushes to the branch only if branch protection requires the check — without branch protection, CI is also advisory. Say so in the doc.

**4. Merge direction:** Base=AGENTS was correct *for this incident* because 13/17 hunks favored it and the 4 CLAUDE wins were individually read and justified. But the method is the problem, not the direction: a one-shot human-adjudicated merge with no recorded rationale. The inverse (base=CLAUDE, splice 13) would have been worse — more splices, more anchor-failure surface. The right structural answer is the per-rule provenance ledger the question offers: each rule block carries a `last-modified` marker (commit hash or date), and the merge becomes mechanical — newest wins per rule, conflicts flagged. One-shot merges of diverged mirrors will recur as long as two writable copies exist (see 5).

**5. One-way generation:** one-way generation is **the root defect** and the guard does not make it safe — it makes it *detected*. The aggravating factor in §1 (the drift hook prescribing a clobbering regeneration) still exists: the next divergence will again produce advice that destroys the newer copy, and the guard only fires at commit time, after the damage is in the working tree. Replace with a single source (`CLAUDE.md`) and AGENTS.md as a **build artifact** — generated, never edited, marked `DO NOT EDIT`, ideally not even committed (generated at session start or checkout). If it must be committed, the drift hook must never prescribe regeneration as a fix for divergence; it must prescribe *investigation*. The current hook advice is an active hazard and should be changed today, independent of any other work.

**6. Mechanical check for "both agree, both contradict a third thing":** you cannot generally mechanize contradiction-detection in prose, but you can mechanize the *specific* instances found. §3.1 (stale authority chain): the review chain is presumably named in a config or registry somewhere — add a lint that every authority/chain name cited in the constitution resolves against the current registry. §3.2 (instruction vs. retraction): maintain a `RETRACTED.md` (or a retractions section) and lint that no constitution line contains an imperative matching a retracted instruction's signature (command string, script path). Generalize: every externally-verifiable assertion in the constitution (names, chains, commands, counts) gets a resolver; the lint fails on unresolvable references. That's the scalable core of "reading for contradiction": extract assertions, resolve them against ground truth.

**7. Unadvertised capabilities:** generate the table. A script enumerates capabilities on disk (the runtime validator already knows how to find them), renders the routing table, and a `--check` mode fails CI if the committed table differs — same pattern as the mirror generator, which the team already trusts. If the table must stay hand-written (descriptions, routing hints), then the check is set-equality only: fail when `installed − documented ≠ ∅` or `documented − installed ≠ ∅`, ignoring prose. That is ~20 lines and directly kills the "skills don't fire" mechanism. The claim "0 unadvertised" in §4 is a point-in-time assertion with no persistence mechanism until this exists.

---

**(d) SINGLE HIGHEST-IMPACT CHANGE**

**Make AGENTS.md a non-editable generated artifact and fix the drift hook to never prescribe regeneration as a remedy for divergence.** Every other defect — the clobber, the bidirectional merge, the mirror-drift theater, the hook that nearly destroyed the only good copy — traces to two writable copies of one law plus a remediation path that copies the wrong direction. The guard is a patch on that root defect; deleting the second writable copy removes the defect class. Everything else (body-change trailers, CI enforcement, capability-table generation) is secondary hardening.
