## VERDICT
REVISE — the wiring direction is sound and unusually well-verified for this repo, but the money guard is opt-in, the concurrency claim is overbroad, and the whole design assumes a single-writer topology the packet never proves.

## BLOCKERS

1. **P1 — The cap is opt-in, so it can be silently absent.** Scenario: `runGenerate` defaults `ledger = null`; `render-agent.mjs` now happens to pass one, but any other current or future caller (CLI, second agent, debug entry, a new route) that invokes `runGenerate` without a ledger gets **unbounded spend with no signal**. The positive control was a grep for one symbol — that proves nothing about call paths. Evidence: §1 ("`runGenerate` takes `ledger = null`"), §2 (`render-agent.mjs` "passes `{ api, ledger: videoLedger }`"). For `composeStills`, the packet says "one new `record()` dep" without showing whether omitting it no-ops or throws. A money control must fail closed: make the ledger mandatory, or require an explicit `allowUnmetered: true` opt-out, and assert at startup.

2. **P1 — The check→record race survives; commit-before-spend does not close it, and the packet claims it does.** Scenario: two concurrent image-lane requests both run the existing `checkRunAllowed` gate against the same file totals before either records; both pass; both bill; cap exceeded. Moving `record()` to `composeStills.mjs:225` (after `estimateOnly` at :206, before the branch at :231) only removes the *generate→record* divergence. Unless check and record execute with no intervening `await` (or behind a mutex / atomic `tryReserve`), the *check→record* window is still open — and the falsification test ("two **sequential** batches") cannot exercise it. Evidence: packet §2 explicitly frames the concurrent-batch window as the thing being fixed.

3. **P1, conditional on topology — per-host file ledger under-enforces by replica count; sticky flag is incoherent across processes.** Scenario: two backend replicas (or backend + second agent host) each keep their own ledger file → effective daily cap = N×cap; and the write-failure flag is "remembered in-process," so replica A refuses while replica B serves the same shared file. If deployment is genuinely one process on one durable disk, this downgrades — but the packet never states the topology, and file-based global state is a deployment coupling that must be an asserted invariant, not an accident.

4. **P2 — Sticky-degraded with no auto-recovery and no alerting.** Scenario: a transient write failure (EMFILE, momentary ENOSPC) at 00:05 UTC refuses the billed lane for the rest of the day until someone manually restarts — and on a PaaS the restart cadence is arbitrary, so the "explicit human act" framing is illusory either way. §5 admits alerting is missing, so this failure is silent. The author asked "is there a state where this refuses a lane it should not?" — yes: recovered-disk states.

5. **P2 — House-rule violation admitted but not resolved.** `render-agent.mjs` is 344 lines > 300 cap ("Pre-existing 338 at HEAD. My delta is +6"). Pre-existing doesn't exempt the delta; the agent bootstrap and the `runGenerate` wrapper should have been split rather than extended. Flagged per the binding cap rule.

## ATTACKS

- **Correctness:** The two lanes call `record` with **different signatures** — image: `record({ runs, spendUsd })` (day computed internally, §2), video: `ledger.record(day, { runs: 1, spendUsd })` (day passed explicitly, `generateVideo.mjs:216`, §3). Under "one implementation for both lanes," the day source of truth differs per lane, and clock-injection tests (if any exist — not shown) cover one lane at best. Also: estimate commit means every retry of a failed batch consumes phantom budget; without idempotency keys a retry storm ratchets the monotonic counter on spend that never happened — bounded, yes, but it converts provider flakiness into operator cap exhaustion exactly when operators are most likely to retry.
- **Security:** The lane-global cap with **no per-workspace attribution** is a fairness/forensics hole: tenant A can burn the entire daily budget and tenant B gets "wait for the UTC day to roll over" with no way to identify who consumed it. IDs-only attribution satisfies the zero-PII rule, so this is implementable. Additionally the refreshed refusal text is operator-facing; if it surfaces to end users it leaks internals (ledger paths/policy) — can't verify from the packet.
- **Data-truth / schema drift:** The old status stub returned `ledger: 'absent-this-slice'` — a **string sentinel** in a field that now presumably becomes structured/boolean. Any consumer (including the 107 frontend tests, which were written against the stub shape) branch-checking that sentinel silently falls through; the packet's `atelierStatusMap` lists 51 codes but no `degraded` semantics are shown, and UI handling of refused-vs-degraded is unverified. Separately: the repo's own `associationsModelRegistryParity` suite is **already red at baseline** — this is a shop with live schema-drift regressions, which raises the prior on unverified drift.

## HIGHEST RISK
The non-atomic check→record race on the image lane — dangerous precisely because the packet believes it closed the window, so nobody will re-visit it. Cheapest concrete de-risk: give `laneLedger` an atomic `tryReserve(estimate)` that performs read-check-append in one critical section (synchronous fs, or an in-process mutex — Node's single thread makes this trivial if no `await` intervenes), have `composeStills` call it instead of separate check/record, and add a genuinely concurrent test (two parallel invocations, not sequential) beside the falsification test. Then make the ledger mandatory per Blocker 1.

## CONFIDENCE
I could not verify, from the packet: (a) whether check and record are separated by an `await` or guarded — the packet shows the record site but never the check call site; (b) whether lanes share one file or have per-lane files ("one implementation" is ambiguous either way); (c) deployment topology — the file ledger's validity hinges on single-process/single-disk, and `render-agent` implies a multi-process architecture already; (d) whether spendGuard's "64 passing tests" ran under vitest or are among the 31 `node:test` files vitest cannot collect — if the latter, the headline "343/343" is covering a different corpus than claimed; (e) the production path for `.ai-workflow/spend/` (gitignored at `.gitignore:515` suggests a dev-relative path; the injected-fs tests prove zero about prod resolution); (f) whether `degraded` reaches any UI or log sink. Evidence that settles each: the `checkRunAllowed` and `laneLedger` sources, the deploy/replica config, the CI runner inventory, and the frontend consumer of the atelier status endpoint. On the author's explicit asks: commit-before-spend is defensible **only if** atomic; the monotonic/no-negative-delta rationale is a category error (anyone with fs write access can delete the file and mint headroom anyway) — append typed `reserve/confirm/release` events instead of forbidding downward movement; and the "durable storage when >1 operator" trigger is the wrong axis — a money counter needs durability at one operator and two replicas, today.
