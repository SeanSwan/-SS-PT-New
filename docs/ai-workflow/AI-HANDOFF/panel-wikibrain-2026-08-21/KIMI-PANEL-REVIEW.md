## VERDICT
REVISE — the epistemics framing is sound and the "produce rows" discipline is right, but the plan ships a second, parallel claims schema with no idempotency, no correction/retraction model, and an unspecified load-bearing mechanism (syndication detection).

## BLOCKERS

1. **P0 — Duplicate extraction has no idempotency guard, and there is no processed-marker on `news_items`.** §8 sequence shows `I->>X: unprocessed items`, but the §5 schema has no `processed_at`/`extracted_at` column on `news_items` and no unique constraint on `claim (source_item_id, assertion)`. Concrete failure: extractor job retries or is re-run after a crash → same item re-extracted → duplicate `claim` rows → `distinct_origins` and cluster counts inflate, silently corrupting the one number the product exists to display. Fix is cheap (unique index + processed watermark) but it is absent from the schema, not merely unmentioned.

2. **P0 — Append-only durable record with no correction/retraction path contradicts how wire news actually behaves.** §8: "append-only; nothing rewritten." §12.3 asks the question but the schema doesn't answer it. Concrete failure: AP issues a correction at 14:00 changing a casualty figure; the 09:12 claim row and the cluster's `canonical_assertion` remain; the disagreement map now shows the *corrected* figure "disagreeing" with the *original* figure as if two sources dispute reality. `claim_cluster.canonical_assertion` is a single frozen text field with no supersedes/version chain. This is a correctness defect in the core surface, not an edge case.

3. **P1 — The plan creates a second claims universe instead of feeding the existing one.** §0 tables: `comment_extracted_claims`, `comment_claim_fact_checks`, `influence_wiki_facts` all exist at 0 rows. §5 then defines brand-new `claim` / `claim_cluster` / `entity` tables with different shapes. Concrete failure: W3's "human verdict" UI writes to… which table? The wireframe (§7.2) says verdicts are human-set and §3 says "the verdict column exists (`comment_claim_fact_checks`)" — but `comment_claim_fact_checks` presumably FKs to `comment_extracted_claims`, not to the new `claim` table. Either the verdict UI can't attach to news claims, or two verdict stores diverge. This is exactly the FK-target drift the house rules warn about, and the plan never reconciles it.

4. **P1 — Syndication detection, declared "load-bearing, not a nicety" (§3), has zero mechanism specified.** `distinct_origins` requires knowing outlet B republished AP's wire. §6 mentions MinHash/SimHash for *clustering*, but origin-collapse needs wire-attribution metadata or near-duplicate detection against a known wire source — a different problem. Failure scenario: detection misses rewritten wire copy → `distinct_origins` reads 5 when truth is 1 → the product's central claim inverts, and §11's W3 gate ("collapses to 1 origin on real data") is a gate with no implementation behind it.

5. **P1 — W5 (desktop → inbound reports) routes owner-supplied arbitrary text into an LLM extractor with no sanitization, no PII posture, and no trust boundary.** House rule: zero PII to LLMs, IDs only. §9 W5 produces "inbound items" that flow through the same `ITEM → CLM` pipeline (§2 diagram). Concrete failure: a desktop report containing names/messages/quoted DMs gets sent to the extraction model — house-rule violation — and hostile or careless content in an inbound report is a prompt-injection vector against the extractor. The plan never states whether inbound items bypass extraction, get sanitized, or are scoped differently.

6. **P2 — No authn/authz or tenancy statement anywhere.** The verdict-save control (§7.2) is the sole write path into the knowledge layer and no endpoint, role check, or owner-scoping is specified. If SwanGuard is single-owner this is fine but should be *stated*; if multi-tenant, every table in §5 lacks an `owner_id`/tenant column and the disagreement map leaks across tenants by construction.

7. **P2 — Volume/retention admitted unaddressed (§10.4).** 1,445 items/poll × fan-out with no retention policy, no index plan for FTS over a growing `news_items`, and `claim_entity` as a bare join table with no indexes declared. Not a ship-blocker for N2/W0, a blocker for W3 at real volume.

## ATTACKS

- **Correctness:** `claim.asserted_about` is `date` — wire stories assert about times ("Tuesday morning") and ranges; a bare non-null `date` forces the extractor to invent precision or fail. `claim }o--|| claim_cluster` means single-cluster membership: a claim that fits two developing stories must be duplicated or mis-clustered, and re-clustering after an extractor upgrade (the stated reason for the `extractor` column) requires rewriting cluster assignments the schema treats as permanent. `cluster_relation.detected_by` has no version stamp, so relations computed by clustering-v1 are indistinguishable from v2 after reprocessing — the auditability the `extractor` column was created for stops one layer up. W0's gate ("citations resolving to the source URL") doesn't specify behavior when the source URL 404s or paywalls later — stale citation state unhandled.
- **Security:** W5 prompt-injection and PII-to-LLM as above. W4 archival lane (Internet Archive/GDELT fetching) is outbound fetching to third-party services with no SSRF/allowlist discussion and an admitted legal-posture gap (§10.7). No rate-limit statement on the N2 trigger path — an owner toggling a connector, or a retry loop, can hammer 39 feeds. Verdict save has no idempotency/replay statement (double-submit creates what — duplicate verdicts? last-write-wins? unspecified).
- **Data-truth / schema drift:** The big one is blocker 3: two parallel claim/verdict models (`comment_extracted_claims` + `comment_claim_fact_checks` vs new `claim` + human-verdict-UI) with no mapping, no migration, and no statement of which is canonical. Secondary: §5 uses lowercase snake_case table names (`claim`, `entity`) while §0's existing tables are also snake_case but the doc never shows the actual DDL of the existing tables, so FK compatibility of `claim.source_item_id → news_items` is asserted, not evidenced. `entity` is a reserved-ish, collision-prone table name in a repo that already has `creator`; naming drift risk is real.

## HIGHEST RISK

**Blocker 1 + 4 combined: the entire product value is one derived number (`distinct_origins`), and nothing in the plan guarantees that number is correct — no idempotency against double-counting, no specified syndication mechanism against under-counting.** Cheapest de-risk before ship: build W1 with a hard unique constraint on `(source_item_id, normalised_assertion_hash)` and a `processed_at` watermark (one migration, hours of work), and pull the §11 W3 gate *forward* — before writing any W3 UI, run the deterministic clustering + wire-collapse on the 1,445 already-seeded items and publish the precision/recall numbers against a hand-labelled sample. If deterministic collapse fails there, you learn it for the cost of a script instead of after building the disagreement map on sand.

## CONFIDENCE

I could not verify from the document: (a) the actual DDL of `comment_extracted_claims` / `comment_claim_fact_checks` — if those tables are generic enough to FK to news claims, blocker 3 downgrades to a naming/ownership concern; the existing schema files would settle it. (b) Whether SwanGuard is single-owner — if so, blocker 6 is P2 documentation debt, not a leak; the auth middleware on existing routes would settle it. (c) Whether `intelligenceWiki.ts` citations already handle dead URLs. (d) Whether any syndication/wire metadata (e.g., `dc:source`, AP byline tags) exists in the 39 seeded feeds — a sample of raw feed XML would settle whether blocker 4 is hard or trivial. (e) House-rule compliance (styled-components, Victory, palette tokens, 44px targets, 300-line cap) is unverifiable — this is a plan with ASCII wireframes and no code; the wireframes show no rule violations, but "no violation visible" is not "compliant." I am most uncertain about (a); it is the difference between "REVISE" and "REJECT the schema section."
