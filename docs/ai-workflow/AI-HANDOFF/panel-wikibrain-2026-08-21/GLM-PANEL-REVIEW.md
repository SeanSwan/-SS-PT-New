## BLOCKERS
No P0s. Nine P1/P2s; the P1s must be resolved in the plan text before any slice is cut.

1. **P1 — Schema cannot produce the flagship surface.** §7.2 renders "DIFFERS ON: figure: 12 vs 14 · date: 19th vs 20th." That requires slot/attribute extraction (claim → {attribute, value}). §5's `claim` carries only `assertion` text + `asserted_about date`. Failure: W3 ships, the disagreement map can show "sources disagree" but has no diffable field — every contradiction degrades to two raw strings side by side, and the plan's own value proposition ("differ on: date, casualty figure") is unimplementable. Add `claim_slot(claim_id, attribute, value)` or cut the DIFFERS ON column from v1 honestly.
2. **P1 — Syndication detection run on restated text over-collapses independent reporting.** §8 clusters by normalise→shingle→group; §4 defines claims as LLM *restatements*; §5 stamps one `extractor` model. One model restating two *independently reported* versions of the same fact yields near-identical text → shingle match flags syndication → `distinct_origins = 1` for genuine corroboration. This is the exact inverse of §10.2, it is unlisted, and §3 declares syndication detection "load-bearing." Detection must key on source-side evidence (verbatim headline/snippet similarity, wire-service attribution string, first-seen timing proximity), never on restatement text.
3. **P1 — FK target drift: `outlets` does not exist.** §0's live verification lists `news_rss_sources` (39 rows); §5's ERD references `outlets ||--o{ news_items` and `claim.outlet_id FK→outlets`. Implemented as written, the FK targets a nonexistent table — precisely the N1 `connector_key` class of bug (§11's own precedent: passes fake suite, dies on real Postgres). Worse: W4 archival items (Chronicling America titles) and W5 inbound items have no outlet row at all — `outlet_id` is either NOT-NULL and inserts break, or nullable and `distinct_origins` counting breaks.
4. **P1 — Verdict storage home is cross-lane and shape-mismatched.** §3: "The verdict column exists (`comment_claim_fact_checks`) and stays human-set." That table FKs to *comment* claims; §7.2 collects a per-**cluster** verdict ("YOUR VERDICT … CLAIM CLUSTER"). §5 defines no `cluster_verdict`. The implementer must either reuse the comment table (FK drift, wrong lane) or invent an unreviewed table. Also unstated: who is authorized to set it.
5. **P1 — Mandatory cluster membership contradicts the async pipeline, with no idempotency anywhere.** §5: `claim }o--|| claim_cluster` — every claim belongs to exactly one cluster. §8 sequences extraction and clustering as separate async stages. Either the extractor mints a singleton cluster per claim (merge semantics undefined — and merging orphans `cluster_relation` rows) or the insert violates the constraint. No uniqueness/hash on `canonical_assertion` means two concurrent clusterer runs (scheduled poll + manual N2 trigger) mint duplicate clusters, and re-extraction after a mid-batch crash double-counts agreement. There is no idempotency key at any stage.
6. **P1 — Untrusted text → LLM extraction → agent retrieval, with zero injection containment.** RSS headlines/snippets are attacker-influenced input; §8 feeds them to the Extractor; W0 renders the output into wiki pages; W6 serves it to Hermes/Codex/Claude. A crafted headline becomes stored `assertion` text that is both displayed to the owner and retrieved by tool-calling agents. No taint boundary, sanitization, or agent read-only constraint is mentioned. Severity escalates to P0 if Hermes holds write tools — unverifiable from this document.
7. **P1 (house-rule violation, prospective but baked into the architecture) — W5 routes desktop report text into the LLM extractor.** §2's flow diagram: INB → ITEM; §8: ITEM → X. Binding rule: zero PII to LLMs, IDs only. Inbound "messages and reports" are the likeliest PII in the entire system and the plan gives them no scrubbing gate. W5 must carry an explicit ID-only/redaction contract or the flow diagram itself violates a non-negotiable.
8. **P2 — Retraction/correction lifecycle absent.** §12.3 asks the question; §5 answers it with silence — no `correction_of`, no claim status, no cluster recency. A story six outlets later retract keeps counting as "MOST CORROBORATED" (§7.1) indefinitely, in an append-only store that "never rewrites." This is the nearest thing to a Snopes-killer the schema lacks.
9. **P2 — No dedupe, uniqueness, or retention on `news_items` or `cluster_relation`.** §8 is append-only with no unique(url, published_at); daily polls of 39 feeds re-ingest overlap and skew counts. `cluster_relation` has no unique(cluster_id, other_cluster_id, relation) — symmetric "A contradicts B / B contradicts A" rows double the disagreement count. §10.4 admits no retention while W4 (bulk archival) is sized L with no volume budget.

## ATTACKS
- **Correctness:** `distinct_origins` is a stored, denormalized int — stale after late syndication discovery or cluster merge; no recompute trigger (§5). `claim.confidence` is extractor self-report; any use in ranking "MOST CORROBORATED" lets an LLM's calibrated-looking number steer the hero surface — its consumption is unspecified. `asserted_about` is a tz-naive `date`: the wireframe's own example ("Al Jazeera … date: 19th vs 20th") can be a UTC-vs-local artifact, manufacturing a disagreement that isn't one — no normalization policy. `first_seen` but no `last_seen`/`updated_at` means the existing `staleAfterDays` frontmatter in `intelligenceWiki.ts` cannot be computed for news pages. W0 ships before W1, so the home hero (which needs W3's `distinct_origins`) is empty for weeks — sequence the surface honestly.
- **Security:** prompt injection per Blocker 6; RSS XML parsing (XXE / billion-laughs — pin parser config); feed-URL management surface unstated (who adds sources — SSRF if non-owner); W5 inbound has no authenticity/integrity design at all (`official_connector_states` = 0 rows, no signing of desktop payloads) → spoofable knowledge-base poisoning that the owner then "verifies"; entity/cluster endpoints need server-enforced owner authz, not a hidden nav item; no rate limit on the N2 trigger → LLM cost blowout via claim fan-out. House rules: no in-document violations found (wireframes are ASCII, no stack chosen) — but the plan creates three UI surfaces and a third module in `apps/api/src/intelligenceWiki.ts` without recommitting to Victory-only charts (entity timeline), the ≤300-line file budget, palette tokens, 44px verdict controls, or WCAG 4.5:1 with non-color redundancy for the ✅/❗ markers. State them in the slice specs or they will be discovered as violations at review.
- **Data-truth / schema drift:** `outlets` vs `news_rss_sources` (Blocker 3); verdict home comment-table vs cluster surface (Blocker 4); W4 historical items mixed into `news_items` with no era/lane column — "TODAY" queries, retention policy, and FTS ranking all need a discriminator that doesn't exist; W5 inbound items have no `outlet_id` semantics; W0 must map news onto the existing page contract (frontmatter `confidence`, `citations[]`) whose shape was defined for comment/influence facts — a news item has no confidence, so W0 either fakes one or breaks the existing response shape for `intelligenceWiki.ts` consumers; snake_case is consistent with the `comment_*` tables — no case drift observed. Missing from §10 entirely: GDPR erasure — `entity` pages about living people built from derived claims have no deletion cascade story.
