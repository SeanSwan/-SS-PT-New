## ATTACKS
- **Correctness.** Blockers 1, 2, 5 are the correctness core. Additional: the `[incoming]` dependency is object identity — safe today only because the hub constructs a fresh object per click; memoize `reused` and the adopt effect silently stops refiring. A failed batch (`c.error` set, `c.result` null) correctly leaves `adopted` alive — that path is fine. "Arriving twice with the same asset" works by accident of identity, not by design. The hub's `if (!a.sha256) return;` is a guard with no feedback — unreachable through the disabled button, but if ever reached it fails silently; a guard and its user-facing half are a pair too.
- **Security.** Question 1, answered directly: publishing `sha256` on an owner-scoped list is safe — it's a content hash of the caller's own artifact, not a capability; no read path derives from knowing it, and preimage resistance means it leaks nothing about the image. Keeping the argument is **not** theatre, but the property is narrower than claimed: it is a *consistency token* (the hash the UI displayed at list time must equal the server's record at bind time — it catches list-to-bind drift), not *attestation* (a client that refetches the hash at bind time reduces the gate to self-comparison; the shown flow correctly anchors the hash at list time — preserve that invariant). Two real thin spots: (a) the gate validates the *recorded* hash, never the bytes in R2 — if the object were replaced without a provenance update, "approval binds bytes" is actually "approval binds provenance"; (b) Blocker 4 — nothing shown binds "approved" to anything but the error message. Also: no idempotency on bind — if animating consumes credits, double-submit double-charges (future-conditional); the lowercase-hex-only regex will hard-fail against any uppercase-stored hash — normalize both sides.
- **Data-truth / schema drift.** `bindTarget = selectedStill ?? adopted` requires *both* producers to satisfy `MotionTarget {assetId, sha256}` flat. `adopted` comes from `assetView` (flat, verified). `selectedStill` comes from `c.result.stills` — the generation response shape is not shown; if batch stills carry `sha256` nested (e.g., under `provenance`) the batch path sends `undefined` and dies at `E_BIND_NO_HASH` while the adopted path works — classic response-shape drift between the two halves of the `??`. Separately, `assetView` derives `brandKit`/`workspaceId`/`lane`/`seed` from string tags: a tag-prefix rename upstream yields silent `null`s, not errors. No PascalCase/snake_case or FK-target drift visible; the `sha256` field name matches the gate's parameter name exactly.

## HIGHEST RISK
Blocker 1 + 2 as one compound: the slice's entire user-visible promise — "arrive in Compose with the frame already bound" — silently no-ops in its most natural flow (had a batch, browsed the library, came back with a frame) and then actively misbehaves on the next tab return. Cheapest de-risk before ship: (1) retire only on a genuine `c.result` *transition* (a `useRef` of the previous result identity, not a mount-time truthiness check); (2) have Compose call an `onConsumed()` callback the moment it adopts, clearing hub `reused`; (3) one test that mounts Compose with **both** `incoming` and a pre-existing `c.result` set — the exact matrix cell the suite never covered, which is also why the bug survived eleven rounds.
