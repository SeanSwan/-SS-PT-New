## VERDICT
REVISE — the core replay/retention design holds, but the terminal-disposition `catch` can destroy a money-safety stub after it was correctly written, and the claim/estimate ordering (as documented) lets estimate responses poison the replay namespace for real requests.

## BLOCKERS

1. **P1 — Terminal `catch` deletes a successfully-retained stub, reopening the double-charge window the retention rule exists to close.** In `localBatchRunner`, the `try` wraps `batches.getBatch(...)`, `store.set(key, ...)` (the retention write), **and** `rememberKey(...)` — three operations with completely different failure semantics — and the `catch` unconditionally does `store.delete(key)`. Failure scenario: a local batch finishes **partial** — 3 of 5 frames delivered and billed — `store.set` succeeds, then `rememberKey` throws (eviction-bookkeeping error, class pressure, anything). The catch deletes the stub that was just correctly written. Client retries with the same key → `store.has(key)` is false → full re-render → second charge for 3 frames of already-delivered work. The catch's own comment ("a failed cleanup must not leave the 202 stub answering forever") is only true for a *failed `store.set`*, where the pending 202 stub is indeed stale. A failed `rememberKey` or a throwing `getBatch` after delivery is the opposite case, and the code picks the money-unsafe default. Evidence: the terminal-disposition block, `store.set(key, Promise.resolve(slimForReplay({...})))` followed by `rememberKey(...)` inside the same `try` whose `catch` runs `store.delete(key)`.

2. **P1 (conditional on the documented order) — estimate-only requests claim the idempotency key before the estimate early-return, creating an immortal, eviction-classless stub that real requests replay.** The flow comment reads: "synchronous claim: `store.set(key, pending)` → chooseLane → **estimate early-return** → commit()". If claim precedes the estimate return, then: client sends `estimateOnly:true` with key K → pending promise resolves to an estimate-shaped response (no `batchId`, no `statusUrl`, no `replayExpiresAt`) → stored under K. No terminal runner ever touches it (estimates don't run batches), so it is never deleted and never `rememberKey`ed. Client then sends the *real* compose with the same key K (natural SDK behavior — one key per logical operation): guard fires (`!req.estimateOnly && store.has(K)`), `prior` = estimate response, `prior?.replayExpiresAt > 0` is false → `{...estimateResponse, replayed: true}` returned to a compose request. Client gets no `batchId`, no `statusUrl`, wrong shape — UI hangs or crashes on the follow-up poll. Note the guard's `!req.estimateOnly` exclusion only makes sense if estimates *write* — you don't exclude reads from a namespace nothing writes to — which corroborates that the claim on the estimate path is real. Evidence: the composeStills flow comment ordering; the guard line `if (!req.estimateOnly && store.has(key))`. This is also the cleanest **eleventh pair-defect**: *the replay guard excludes estimate reads, but the claim does not exclude estimate writes.*

3. **P2 — Guard compares a stored absolute deadline against request-start `now`, erring permissive.** `now = deps.now ?? Date.now()` is captured at the top of the call; the guard evaluates `prior.replayExpiresAt > now` possibly after awaits and queue time. A stub that died at T+50min is served as alive if the request started at T. Bounded consequence (the statusUrl "refuses itself" per the comment, so it costs one wasted round-trip before the client retries with a new key), but the fix is a one-liner: sample `deps.now()` at guard time. The reverse direction (an injected late `now` in tests) expires stubs early → fresh re-run → double-charge *in test only*. Evidence: "`now` is `deps.now`, defaulting to `Date.now()` at the top of the call" + the guard line.

4. **P2 — `prior === undefined` falls through the guard as "replay".** Between `store.has(key)` and the resolved value of `await store.get(key)`, a terminal `.finally` can delete the key (the settled-list's "no await between has and set" protects claim-vs-claim, not has-vs-get-vs-terminal-delete). If `get` returns `undefined`, `!(undefined > 0)` is true → `return {...undefined, replayed: true}` → the client receives literally `{replayed: true}` with no fields. Window is ~zero for a synchronous in-memory store whose async `get` reads the map before its first await; real if the store does I/O. Defensive one-liner: `if (!prior) /* fall through to fresh run */`. Evidence: the guard block; the settled note's scope ("between the idempotency `has` and `set`").

5. **P2 — Response-shape drift between first response and replay, plus internal-field leakage.** First caller: `{accepted:true, status:'queued', count: <requested>}`. Replayer: `{accepted:false, status:'done'|'partial', count: <delivered>, requested, failed}` — `count` silently changes meaning, and `accepted:false` on a *successfully completed* batch will misrender in any frontend that branches on `accepted` before `status`. Additionally `{...prior, replayed:true}` spreads `replayExpiresAt`, `key` (the internal hashed key), and `admission` straight into the HTTP response. Not cross-tenant (the key is user-scoped — settled), but it's internal surface for free. Evidence: the 202-stub definition vs. the `slimForReplay({...accepted, accepted:false, count: snap.stills.length, ...})` terminal write.

## ATTACKS
- **Correctness:** The in-flight join (Attack 2's question) works **by accident**: caller 2 hits `store.has(key)` → true, `await store.get(key)` awaits the pending promise → resolved 202 stub → the *missing-field* clause (`!(prior?.replayExpiresAt > 0)`) is what lets it through, returning `{...202stub, replayed:true}`. So "missing = replay" is **load-bearing for concurrency dedup**, not a legacy-deploy courtesy — the doc's framing ("stub written by an older deploy") misdiagnoses its own policy. This matters: anyone who "fixes" the missing-field default to `expired` silently breaks in-flight join, and anyone who keeps it inherits Blocker 2's estimate pollution. The policy needs a discriminator (`kind: 'pending' | 'settled' | 'estimate'`, or stamp `replayExpiresAt` at claim time), not a blanket default. Also: `snap.finishedAt || Date.now()` in the terminal write bypasses `deps.now`, so injected-clock tests can't control stub expiry — determinism drift between test and prod.
- **Security:** No new authn/authz surface — keys are user-scoped and settled. The one item worth naming: `{...prior}` returns the internal `key` and `admission` fields (Blocker 5) — hygiene, not privilege. SWA-165 stays filed, not re-raised. No injection/SSRF surface in this path; the OpenRouter call's payload hygiene (PII in user briefs) is out of this round's scope and no violation is evidenced in the document.
- **Data-truth / schema drift:** (a) First-response vs. replay-response drift: `count` = requested vs. delivered, `accepted` true vs. false, extra `requested`/`failed` fields — the frontend contract must branch on `batchId`/`status` presence, never `accepted` alone. (b) `replayExpiresAt` written with wall-clock `Date.now()` but *read* against `deps.now` — same logical field, two clocks. (c) The pending stub and the settled stub share a store slot with **different shapes** and no type tag — every consumer currently distinguishes them by the absence of one field.

## HIGHEST RISK
Blocker 1 — the over-broad terminal `catch`. It is unconditionally present in the shown code (unlike Blocker 2, which depends on the ordering comment being literal), and its failure mode is *silent double billing* — the exact catastrophe the retain-on-delivery rule was built to prevent, undone by a bookkeeping throw. Cheapest de-risk: split the `try` — keep the delete-on-failure `catch` around **only** the `store.set`; give `getBatch` and `rememberKey` their own log-only handlers. On unknown terminal state (throwing `getBatch`), write a short-TTL stub rather than deleting, so the failure is bounded in both directions. ~6 lines.
