## BLOCKERS

1. **P1 — Default kit semantics are unstated; omission may silently re-create the original bug.** Scenario: a new caller (or an old one that never heard of kits) invokes compose without a `brandKitId`. The document never says whether omission maps to `swanstudios`, `universal`, or a refusal. If it maps to `swanstudios` (today's de facto behaviour), then every future integration that forgets the parameter gets Swan's palette and law profile applied to someone else's site — precisely the failure §1 declares fixed, reintroduced through the default. The strict-refuse philosophy is applied to *unknown* ids but not to *absent* ones. No file:line available — the resolution call site (`composeStills.mjs:102`) is described but its fallback branch is not quoted. This must be pinned by a test like the refusal tests were.

2. **P1 — Taste path applies Swan taste to non-Swan renders with no marker, refusal, or disclosure (author's own open question 1).** Scenario: Sean composes for another site using `taste` mode; output is dressed by his rated corpus (Swan taste) while the brief path would have applied `universal`. Two sites, two code paths, two different brand outcomes — and nothing in the result says which regime ran. Option (c) — refuse `taste` + non-default kit until measured — is the cheap correct answer; shipping (a) silently is not acceptable for a feature whose entire purpose is "renders are judged by the right brand's laws."

3. **P1 — Kit/provenance is not persisted on the asset row.** The packet lists "showing which kit rendered an asset" as a *missing nice-to-have* (§3.5), and `lawProfileOverridden` is described as recorded on "the result." If the result is ephemeral and the asset row stores only the free-text `workspace` label, then after the fact nobody can answer "which brand laws produced this published image?" — for a system whose laws exist to protect a real person's named brand, that is an audit hole, not a polish item. Persist `brandKitId` + `lawProfileEffective` + `lawProfileOverridden` on the asset row in this slice, not the next one.

4. **P2 — No authz model for kit selection or lawProfile override.** Any authenticated caller able to reach compose can apparently pass any allowlisted kit id *and* override its `lawProfile` with nothing stronger than a boolean flag (§3.3). Scenario: a compromised or merely careless client token renders under `swanstudios` with `lawProfile: 'none'`; the only trace is a flag on an unpersisted result (see #3). At minimum: override requires an explicit operator-scoped permission, and the refusal/override decision points need named checks in the packet.

**Security**

If it flows into R2 keys, filenames, DB queries, or log lines unsanitized, that is injection/log-forgery surface.
