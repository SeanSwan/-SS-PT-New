## BLOCKERS
1. **P1** — Desktop drag dies the moment the pointer leaves the photo: `onPointerDown` sets `isDragging`, then `containerProps` binds `onPointerLeave: onPointerUp`, which clears the flag. `setPointerCapture` is supposed to allow overshoot; this handler undoes it. Input: pointerdown on the comparison, drag past the image edge → output: handle freezes at the last in-bounds `clientX` while the button is still down. Evidence: `src/hooks/useBeforeAfterSlider.ts` (`onPointerUp` / `onPointerLeave: onPointerUp` in the `containerProps` `useMemo`). Same path has no `onPointerCancel` / `onLostPointerCapture`, so a cancelled touch leaves `isDragging.current === true` until a later pointer cycle.

2. **P1** — Capture is taken on `e.target`, not the track. A down on `TransformationSlider`, an edge label, or a photo (unless `pointer-events: none` is actually in the CSS — not shown) captures the child. Move/up are registered on the container. That works only while those events bubble and the child stays mounted; it is the opposite of the “track is the pointer surface” model you asked about. Input: pointerdown on the 44px handle, handle re-renders or the clipped image is the target → output: lost capture / missed moves. Evidence: `onPointerDown` → `(e.target as HTMLElement).setPointerCapture?.(e.pointerId)` in `useBeforeAfterSlider.ts`.

3. **P1** — `shouldShowProfileSidebar` contradicts the written failure-mode policy. Prose: new/unconsidered tabs must render full width (crush is the bug). Code: only `home` and `nutrition` opt out; any other string, including a future tab id, returns **true** (sidebar on, 300px rail). Input: `activeTab === 'progress' | 'analytics' | 'NewTab'` → output: crushed main column, the exact Home bug you just removed. `null`/`undefined` return **false**, so first paint and unknown-string also disagree and will CLS. Evidence: `TABS_WITHOUT_PROFILE_SIDEBAR` + `shouldShowProfileSidebar` as pasted; this is opt-out, not the claimed opt-in.

## ATTACKS
- Correctness: `useBeforeAfterSlider` “full source” returns `setPosition` but only declares `setPositionState` — if that listing is literal, `tsc --noEmit` could not have been 0; if tsc was 0, the packet is not full source. Treat every “verified” claim as untrusted until the real file is shown. `onPointerDown` calls `updateFromClientX` immediately: a vertical scroll that begins on the photo jumps the handle to that `clientX` even with `touch-action: pan-y` (horizontal drag itself is the correct `touch-action`; the jump-on-contact is the mobile break). No drag threshold, no `onPointerCancel`. `Home`/`End` → 5/95 is consistent with `aria-valuemin/max` (not a lie to AT) but is surprising to sighted keyboard users; defensible only if you say “keeps both frames visible” in `aria-valuetext`. `role="slider"` on the whole track is acceptable when the track *is* the input (single tab stop, keyboard on the same node). It is not acceptable while unlabeled images remain in the tree: hide them (`aria-hidden` on both photos + edge labels) or you get “slider, Before transformation, After transformation”. CSS var scoping **does** hold — inline `--swan-slider-pos` on each track does not leak to a sibling slider; do not “fix” that. `isFilteredView` is computed from **pre-filter** `activities.length`, so a brand-new account that can still click `Workouts` gets the unfiltered empty string (`Start a workout or create a post!`) — and that CTA is itself happy-path-only if a logged workout does not create a profile post. `shouldShowProfileSidebar(null) === false` vs unknown string `true` is a latent first-paint / typo-tab bug, not a style nit. Bypassing `useAuth()` in a modal that **builds role-specific hrefs** is not a leaf-display pattern; it is an untyped auth read that will rot the first time someone assumes the modal is provider-guaranteed.

- Security: 2c is the authz hole in this packet. Client-side `user?.role` with a default client URL is a multi-tenant footgun: staff with a missing role land in the member logger (`?loadPlan=today`). That is not an open redirect, but it is a wrong-workspace action. 2b’s `POST /api/photos/:userId` is out of scope for the UI delete, but the quoted handler takes `userId`/`clientId` and a caller-supplied `storageKey` — if that path is not bound to the session’s client prefix, it is an IDOR sitting under the thing you just decided members cannot use; removing the button does not close it. No new injection/SSRF/secret issues in the pasted TS. 20 `framer-motion` rows is not a DoS.

- Data-truth / schema drift: Filter chips `Workouts` / `Progress` / `Achievements` still name **event types** while the feed is `ProfileActivityPost[]`. That is caller-field vs model drift; copy cannot repair it. `loadPlan=today` and `intent=log_workout` are query-shape claims with no consumer shown — frontend URL vs logger/searchParams drift. Wiring the removed upload to `createPost` / `PhotoGallery` would have been a worse drift (`photoType` / `storageKey` never set, comparison still empty); **deleting the button was the correct call**. Remaining 2b lie is the copy: “will appear here” names no actor, while the only writer is admin `PhotoManager.tsx` typing URL + `photos/{category}/{clientId}/...` by hand. `#A0A0B0 → --text-muted` / `#E0E0E0 → --text-secondary` is palette drift unless those tokens are bit-identical in `crystalline-dark`; the raw `#fff` scrim also violates `var(--token, #fallback)` even with `swan-guard-allow-hex`. No PascalCase table issues in this packet.
