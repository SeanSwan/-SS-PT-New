## BLOCKERS

1. **P1 — Retained replay stubs outlive their batch rows; replay answers with a dead `statusUrl`.**
   Interleaving: batch settles at T → fix A retains the client-keyed stub (`store.set(key, Promise.resolve(slimForReplay(...)))`). Row TTLs out at T+1h (`BATCH_TTL_MS`, batchStore.mjs `prune()`). Nothing deletes the stub at that moment: the only stub eviction is the opportunistic loop in `startLocalBatch`, and `getBatch()`'s internal prune **discards** its return. Worse, the client's own status polling is what triggers the internal prune — the poller kills the row the retained stub advertises. At T+2h (a perfectly legitimate delayed retry — this is exactly what retention exists for), replay returns `{status:'succeeded', replayed:true, statusUrl:'/api/atelier/compose/stills/<id>'}` → client GETs → 404. Failure scenario: mobile client retries a lost response after a network flap hours later → confident success payload → 404 → user believes render succeeded and vanished. Consequence: the replay contract is only honest inside a 1-hour bubble that nothing enforces. The retained-key eviction class does **not** rescue this: its triggers are global memory pressure (the SWA-165 class) and new-batch creation — neither is time-bounded to row TTL. And `getBatch()` discarding prune's return is not harmless; it is the *mechanism* of this leak.

2. **P2 — The eleventh pair-defect: `failed` drops but `partial` retains, and the retained partial carries drifted fields.**
   Failure scenario: 10-frame batch, 3 frames fail → `snap.status === 'partial'` → key retained → a client retrying the *same compose request* (the natural "finish what I asked for" retry) replays the partial corpse forever, while the all-failed client gets a fresh render. Retaining partial is *defensible* (something was delivered; same-key re-render is nondeterministic and wasteful) — but then the failed-drop rationale ("retaining makes failure permanent") applies with reduced force to partial and the document never states the principle. Compounding it: `slimForReplay({ ...accepted, status: snap.status })` spreads the **202 stub**, so `count` and `cost` are the *accepted* values, not terminal ones — an 8/10 partial replays as `count: 10`. That's response-shape drift between the replay payload and ledger truth. Evidence: fix A retain branch; the `accepted` stub definition.

3. **P2 — `.finally(cleanup).catch(() => {})` swallows cleanup failures, stranding a success-path corpse; and telemetry was added to release errors (C) but not cleanup errors (A).**
   Failure scenario: runner settles → `.finally` callback throws inside `slimForReplay` or `store.set` (e.g., serialization of `accepted.brandKit`) → the `.catch` placed *after* `.finally` eats it → the store still holds the long-resolved 202 promise → every future replay for that key returns `{accepted:true, status:'queued', replayed:true}` forever. This is the exact corpse class round T killed, surviving on the success path. Fix C deliberately added `onReleaseError` telemetry; fix A's catch is a silent black hole — that asymmetry is itself a member of the pair-defect family (telemetry-on-release-but-not-on-cleanup).

Invalid input gets *two different* silent repairs: `NaN`/negative → default 90s; small-positive → 50ms. That is precisely the original bug shape (wrong quantity silently accepted). ## ATTACKS

- **Correctness:** Blockers 1 and 3 are lifecycle/ordering defects: unlinked TTLs (row vs stub) and a promise-chain shape (`.finally` before `.catch`) that converts cleanup exceptions into permanent stale state. Also unverifiable-but-suspicious: fix A assumes `runLocalBatch`'s promise settles *after* the terminal status write — if any path resolves the promise before marking the row, the retained stub says `status:'running'` forever. That assumption needs a test, not a comment.
- **Security:** No new authn/authz surface; replay key construction remains tenant-scoped (settled). One rules-watch item, not a finding: `openrouterImage.mjs` sends compose prompts (which include `brandKit` free-text) to a third-party model gateway. The house rule says IDs-only to LLMs. Verify no client PII rides in brandKit text — I cannot check payload contents from this document.
- **Data-truth / schema drift:** Blocker 2's `count`/`cost` drift (accepted-stub values replayed as terminal truth). Blocker 1 is drift of a liveness kind: the stub asserts a URL whose backing row no longer exists. Both are the replay payload desyncing from batch-store truth.

**Recommendations (attack 6):**
1. Make row death and stub death one event: route *every* `prune()` caller through the same `store.delete(goneKey)` loop (a 5-line helper), including `getBatch()`'s internal call — or stamp retained stubs with `expiresAt = finishedAt + BATCH_TTL_MS + margin` checked on read. This kills blocker 1 structurally instead of opportunistically.
2. Belt-and-braces: on replay, if the batch row is gone, return an honest `410 result expired, re-compose` rather than a 200 with a dead URL.
3. Write down the retention principle — "nothing delivered → key drops (retryable); anything delivered → key retains (stable)" — make the test name carry it, and rebuild `count`/`cost` in `slimForReplay` from `snap`, not from `accepted`.
4. Restructure to `.catch(swallow).finally(cleanup)` with cleanup's own try/catch piped to the same telemetry sink as `onReleaseError`.
5. Replace the clamp with a startup assertion (`grace ≥ measured frame time`, `grace < watchdog`) plus a WARN log on any runtime clamping; derive the ceiling from measured frame time, not a 5090 constant.
6. On tests (attack 5): the wrong-reason pass that survives a neutering check is any test asserting an observable with **two producers**. Concretely: a test for fix A's failed-drop can survive neutering *the drop line itself* if its fixture advances the clock or starts another batch first — fix B's prune-eviction deletes the same key via a second path, so the test stays green with A's fix dead. Likewise, assertions on echo fields (`batchId`, `key`, `lane`) pass identically fixed and neutered. Neutering checks must pin the discriminating fields (`accepted`, `status`, and URL *liveness*, not URL *presence*) and must neuter with the row deliberately kept alive.

## HIGHEST RISK
Blocker 1. It is the only finding that inverts the product promise — replay exists so late retries get truth, and instead late retries get a confident lie — and its trigger (any quiet period > 1h, then any retry) is the common case, not the tail. Cheapest de-risk: make `prune()` own store eviction for every caller (wire `getBatch()`'s internal prune through the same delete loop — roughly five lines, testable in one fixture: settle → advance past TTL → poll status (kills row) → replay → assert 410-or-rerender, never 200-with-dead-URL).
