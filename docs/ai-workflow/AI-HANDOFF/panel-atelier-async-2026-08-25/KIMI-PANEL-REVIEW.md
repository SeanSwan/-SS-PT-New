## VERDICT
REVISE — the contract core (202+poll, per-frame persistence, owner-scoped absence-404) is sound, but the background job has no timeout/no wedging protection while the GPU reservation is unbounded and never pruned, and the idempotency layer can hand back 202s for batches that no longer exist; six small predicates and their tests close this.

## BLOCKERS

1. **P0 — No stall/timeout on the background job ⇒ permanent reservation wedge.** Inputs/state: ComfyUI hangs, connection drops mid-frame, or any async throw escapes the runner's catch (e.g., inside `persist`) at frame 2 of 4 → `finishBatch` never runs, reservation never released, batch stuck `running`, and per the document "running never pruned" (§2 Expiry row) with "no cancel endpoint" (§3) → every subsequent `POST lane:local` returns `E_LOCAL_BUSY`/409 **forever**, and the UI "disables Generate while a batch is in flight" (§1) so the operator is locked out until a manual restart. The gates only pin release for *known* failure shapes ("crash … FAILED", "a crash before rendering … releases the GPU" in `atelierAsyncStills.test.mjs`); nothing pins a hang. Fix: per-frame deadline + absolute batch watchdog (see HIGHEST RISK).

2. **P1 — Idempotency entries can outlive the batch they point to ⇒ 202 for a dead batch.** Inputs/state: batch finishes, `prune()` drops it after 1h (§2 Expiry row), client re-submits with the same key → `store.has(key)` → `202 {replayed:true, batchId, statusUrl}` (§2 "Idempotency coalesces to one batch") where every poll now 404s; the 202 contract ("accepted") is violated and the client can never recover while the key is reused. §4 Q2 only examines replay-during-`queued`; the post-expiry case is unexamined. Fix: tie idempotency-entry TTL to batch TTL and, on replay, re-validate batch liveness — if gone, either mint a fresh batch or return a terminal code, never `replayed:true` for absence.

3. **P1 — Idempotency key user-scope unspecified ⇒ cross-tenant existence leak.** Inputs/state: two owners present the same client key (client-generated keys collide in the real world; shared team machines share headers) → `store.has(key)` on a global map returns owner A's `batchId` + `statusUrl` to owner B with `replayed:true`; the owner-scoped poll gate (`getBatch(id, userId)` → 404, §2 "Owner scope on poll") then hides the body, but the *existence* and id shape already leaked, and B's request is silently coalesced into A's GPU spend. Owner-scoping is specified only on the poll side. Fix: key must be `(userId, idempotencyKey)`; pin with "two owners, same key, two batches."

4. **P1 — 404 has no terminal semantics on the client; the snapshot schema's `terminal` flag cannot be read when absence is the answer.** §1 assigns 404 to four distinct causes: not-your-batch, finished>1h, server restart, malformed id (`E_BATCH_NOT_FOUND`). The in-body `terminal` and `error` fields are unreadable in exactly the states where the operator most needs a decision. Unspecified, a poll loop (3s) against a post-restart id runs forever — directly contradicting "this page can be left" (§1). Fix: specify client predicate: *404 for a batchId we hold ⇒ terminal failure state + offer re-generate*; pin with an e2e test across a restart.

5. **P2 — Gate/pipeline ordering between "Reservation before VRAM read" and "Idempotency coalesces" is unpinned.** If `reserveGpu()`/`admission()` run before the idempotency lookup, a double-click *during* an in-flight batch gets 409 (`E_LOCAL_BUSY`) instead of `replayed:true` — a direct contradiction of gate 6. §4 Q2 admits the uncertainty ("`store.set(key, Promise.resolve(accepted))` before the batch starts"). Fix: declare idempotency-lookup-first, and `store.has`/`store.set` must be synchronous (no await between) so `set` is atomic with `has`; pin with "two parallel same-key requests → one 202, one replayed, zero 409s."

6. **P2 — Two gates are UNTESTED by the packet's own rule ("If a gate has no test it says UNTESTED"): batch-id route shape and expiry.** `/^[0-9a-f-]{36}$/` (§2) also accepts 36 hyphens and any hex/hyphen soup; harmless but sloppy, and if any id generator ever emits uppercase, POST would mint ids its own GET route rejects. `prune()` timing/race (batch finishing exactly as prune runs) is unpinned. (Document supplies no line numbers; evidence is the §2 gate table and named test titles.)

## ATTACKS

- **Correctness:** (a) The <25ms acceptance assertion with 30ms/frame stubs is wall-clock-bound → flaky under CI load; assert the render pipeline was *not awaited* (e.g., spy on `renderStill` call count at response time), not a duration. (b) `rendered` vs `stills[]` can diverge under partial failure: persist→pushStill ordering means a throw after a successful `renderStill` but mid-`persist`/`pushStill` leaves the single source of truth ambiguous — derive `rendered` from `stills.length`, never a separate counter. (c) `estimateOnly` reservation semantics contradict the accept predicate: `!estimateOnly` gates the 202, yet "release on every path" lists estimateOnly — does an estimate acquire the reservation and return 409 while a render runs? Unspecified. (d) "disables Generate while in flight" is per-tab client state; tab N+1 bypasses it, so the 409 path is load-bearing — the client *must* honor Retry-After (present on 409, good) and surface it honestly. (e) `Promise.resolve(accepted)` stored as the replay value should be the *batch record*, not an HTTP-shaped object; anything response-shaped risks replaying a body the batch state has since invalidated.

- **Security:** Owner-scoped 404-on-absence is correct anti-enumeration (accept). Real exposures: (a) cross-user idempotency scope (Blocker 3). (b) Hosted lane is synchronous with no stated per-owner concurrency cap — `adminOnly` blunts this, but one operator can still stack N sync hosted requests; add a per-user semaphore or state why it's unnecessary. (c) SSRF/workflow-injection: nothing in the packet says ComfyUI's base URL and graph construction are static server-side config; if any client field ever reaches the prompt graph or URL, that's SSRF plus ComfyUI workflow injection — pin "prompt text is data, never graph." (d) `statusUrl` bearer-ness: fine while poll relies on ambient auth + owner scope; forbid token-in-URL variants in any follow-up. (e) Polling cost at N tabs is trivially fine for one operator (N×20 req/min); not a blocker — answer to §4 Q3 is "fine, add nothing."

- **Data-truth / schema drift:** The snapshot shape `{status, stills[], failures[], rendered, count, persistence, error, terminal}` is asserted as a list, not a schema: `persistence` semantics are undefined (per-still? batch-level? enum?), `failures[]` item shape is unpinned despite only `error.code` being promised, and `stills[]` item shape (assetId, url?) isn't pinned against the library's asset record. One schema definition + a contract test kills all three. The loose id regex vs the actual UUID generator is a live drift candidate (Blocker 6). No SQL here, so PascalCase/snake_case drift is N/A. **House-rule scan of this document:** no UI code ⇒ styled-components/Victory/token/44px rules not implicated; no banned language; no credential claims. One forward flag: the §4 Q5 "render while I'm away" Hermes/Telegram idea must obey the zero-PII-to-LLMs binding — **batch/asset IDs only, never prompt text or client names** — write that into whatever packet picks it up.

## HIGHEST RISK
Blocker 1 — the wedged reservation. It is the only failure that converts an ordinary external hang (ComfyUI, network, OOM-killed child) into a *permanent, silent, operator-locking DoS* on a single-GPU solo deployment, and the design currently has no wedge-escape by construction ("running never pruned" + no cancel + no timeout). Cheapest concrete de-risk before ship: in the background runner, race each `renderStill` against a deadline (~90s ≈ 3× the 27s/frame budget), and on trip call `finishBatch(failed, E_FRAME_STALL)` + `release()`; add a batchStore sweeper that force-fails any batch older than a hard absolute cap (e.g., 15 min). That's ~40 lines and two predicates — "a stalled frame fails the batch and frees the GPU", "watchdog fails a wedged batch" — each pinned by one test, with a best-effort ComfyUI queue purge as cleanup. This also makes the "running never pruned" policy safe.

## CONFIDENCE
What I could **not** verify from the document alone, and what would settle it:

1. **Catch scope of the background runner.** Whether an async throw *inside* `persist` (after `renderStill` succeeds) still reaches the catch that calls `finishBatch`/`release`, or escapes as unhandled rejection — the gates prove known failure shapes, not the escape path. Settle with: source of the runner in `backend/services/atelier/*.mjs` plus a test that rejects asynchronously in `persist` at frame 2.
2. **Atomicity and order of `store.has`→`store.set` vs `reserveGpu()`/`admission()`.** §4 Q2 shows the author is unsure too. Settle with `batchStore.mjs` source or a two-parallel-same-key concurrency test.
3. **Idempotency key composition and TTL.** The doc never defines the key's namespace or lifetime. Settle with `batchStore.mjs` source.
4. **Deployment is truly one process.** A PM2 cluster-mode or 2-replica k8s deploy silently breaks both the process-local Map *and* the in-process reservation (two GPU "owners" simultaneously). Settle with the pm2/docker/k8s manifest.
5. **UI behavior on 404** (Blocker 4) — frontend poll code is not in the packet; settle with the poll hook/component source.
6. **VRAM TOCTOU window vs the Motion agent process.** `admission()` sampling lag (nvidia-smi cadence) and the collision window between admission and first-frame allocation are unquantified; settle with a chaos test that launches a Motion job mid-batch, and confirm OOM is classified into `failures[]` with a code, not a hang.
7. **ComfyUI behavior on kill mid-frame** (orphan queue entries, partial files on disk) — vendor behavior, needs an integration test.
8. The two UNTESTED gates are self-declared; everything else hangs on (1)–(4). My REVISE assumes single-process is real and the runner catch is total; if either assumption fails, the verdict degrades toward REJECT on Blocker 1 alone.
