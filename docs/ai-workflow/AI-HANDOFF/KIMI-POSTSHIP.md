## PROSE

**On the severity question you asked directly.** A gate that runs only where the owner merges delivers perhaps 70% of the value *today* and decays. The number isn't the point; the architecture is. This corpus exists because a documentation system failed *silently* — every file read correct while the structure rotted. You have now shipped an enforcement mechanism that fails silently on every surface except one, and written into canon that it is "wired … verified." The mechanism is real (unlike the nine you deleted), so this is not a full recurrence of the fictional-mechanism class — but it is the same genus: a claim about the repository that is only true of an environment. Grade: HIGH, not CRITICAL, because the gate does run at the current merge chokepoint and the corpus is genuinely cleaner than before. It becomes CRITICAL the day a second machine or a cloud agent touches the brain.

**The correct fix is CI-first, hook-second.** A `prepare` script alone repeats the mistake in miniature: it covers local clones but not CI itself, and it still makes enforcement depend on each environment's cooperation. The CI job makes the gate a property of the repository — the thing canon claims it is. The hook then becomes what it should have been described as all along: optional local fast feedback.

**Is the canon wording false or incomplete?** False. "Incomplete" would be a true statement missing detail; "wired into `.githooks/pre-commit` … verified" asserts a repository fact that holds nowhere the repository is cloned fresh. The kindest reading is that "verified" was scoped to the author's machine — but canon is read by agents who cannot see that scope. The sentence must be rewritten to make the enforcement surface explicit, and it should be rewritten in the same PR that makes it true.

**On `design.html` — my earlier position holds, and the hole is real but smaller than the alternative.** I argued a drifting visual mirror is worse than none because a wrong visual gets copied while a wrong textual claim gets argued with. Nothing about shipping has weakened that: the mirror had already drifted (that drift was part of the rot), and an agent copying stale hex swatches would have done more damage than an agent with no swatches at all. But I want to be honest about the cost now that it's concrete: the corpus lost its only *human*-facing surface. Agents read tokens fine; humans reviewing a design decision need to see it. The correct replacement is not a hand-maintained HTML mirror — that's the same trap — but a **generated** one: a build step that renders token swatches and type specimens *from the canon token source*, so the visual cannot drift because it has no independent existence. Until that exists, the hole is acceptable; the pre-ship state was not. Retiring it was right. Leaving the hole permanently would be wrong.

**What shipping revealed that pre-ship review could not:** four rounds of hostile review — including mine — all verified the gate *from inside the environment where it was installed*. Every one of us ran the tests, confirmed CLEAN, and never once cloned fresh. That is the durable lesson: for any enforcement mechanism, the verification surface must include an environment that did not participate in building it. Add "fresh-clone verification" to the review checklist; it would have caught F1 in round one.
