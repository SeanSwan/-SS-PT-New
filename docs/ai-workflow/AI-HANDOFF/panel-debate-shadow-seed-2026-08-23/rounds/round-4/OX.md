# Ox Alpha — round 4, fresh-eyes adversarial

The consensus candidate is sound on all four points and I adopt it. But every prior seat is staring at the FK graph, the composite-PK tuple, and the YAML password. Applying the fresh-eyes lens, three defect classes are structurally visible in the packet that none of those addresses:

**Class 1 — the test suite is verified nowhere.** The builder header admits `vitest run` is *blocked locally* ("missing @rollup Linux native binary"). The only workflow in the packet (migration-shadow-check.yml, full step list: Checkout → Setup Node → npm ci → Export URL → Pre-migrate guard → Migrate ×2 → Seed → Assert → Import → Upload) contains **no step that runs vitest**. So the suite — including what the test file itself calls "the most important test in this file" (the safety gate) — is executed neither locally nor in CI. Acceptance criterion §7 "The test suite passes" is asserted by nobody. This is precisely the packet's own §9 trap: an instrument that has never been observed to distinguish anything.

**Class 2 — explicit PKs poison identity sequences.** `generateRowValues`'s PK branch emits `out[col] = rowIndex + 1` for integer PKs with no regard for `autoIncrement`, and `normalizeModel` doesn't even capture the flag. On Postgres serial/identity columns, inserting explicit low integers leaves the backing sequence at 1. The entire purpose of this job is Migration Run 2 exercising **data migrations against populated tables** — a data migration that `INSERT`s into any seeded table will collide with the unwritten sequence and fail. The gate either burns down on legitimate migrations or trains people to ignore it.

**Class 3 — the shadow token is checked against the whole URL, not the database.** `validateShadowUrl` runs `/shadow/i.test(url)` over the full URL string. `postgres://shadow:something@localhost:5432/appdb` passes the gate while the target database is `appdb`. Loopback bounds the blast radius, so MINOR — but the check as written certifies the wrong surface, which is the packet's own "gate inspecting the wrong surface" trap in miniature.

Smaller items: the PII-guard `throw` inside `generateRowValues` fires *outside* the per-table try/catch in `main()`'s row loop, aborting the whole run instead of reporting per-table; the backfill `UPDATE … WHERE col IS NULL` blanket-overwrites every NULL in the column, not just the cycle-broken rows; and the workflow assert relies on `tail -1` over a prefix (`^SHADOW-SEED `) that also matches the `SHADOW-SEED OK …` progress lines — currently correct only because the report line happens to print last.

Rulings on the running state: step order satisfies §5.3 (pre-migrate-guard is `--check`-only and correctly precedes Run 1); the seed step sits correctly between the two migrates; `retry: 1` is inert for these pure-function tests but should go for hygiene; `POSTGRES_PASSWORD: "***"` is the confirmed MAJOR — the quoted form is valid YAML (so the builder's linter claim stands) but the container password is the literal `***` while `DATABASE_URL` authenticates as `shadow`, so the very first connect fails.
