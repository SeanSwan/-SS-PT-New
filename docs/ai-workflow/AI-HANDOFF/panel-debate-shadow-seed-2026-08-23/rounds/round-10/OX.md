**The missed class — sequence/PK desync across the gate's own phases:**
- `seed-shadow-db.mjs`, `generateRowValues` pk branch: `out[col] = rowIndex + 1` for non-UUID PKs; these explicit values go straight into `m.bulkCreate(values, ...)`.
- Nowhere in the file is there a `setval`/`pg_get_serial_sequence` call (verified: zero occurrences).
- Consequence: every seeded table with a `serial`/identity integer PK now has rows 1–5 occupied while its sequence still sits at 1. The workflow's own "Migrate (second run — WITH DATA)" step (`.github/workflows/migration-shadow-check.yml`, that step) is *designed* to run data migrations against this data. Any data migration that does `INSERT INTO <seeded serial-PK table>` without an explicit id gets duplicate-key on sequence value 1 → the gate goes red on a perfectly valid migration. The job exists to validate data migrations; this defect makes it false-fail on a subset of them. MAJOR.
- Fix: after section 4b, per seeded table: `SELECT setval(pg_get_serial_sequence('"T"', '<pkCol>'), GREATEST((SELECT MAX("<pkCol>") FROM "T"), 1))` wrapped in try/catch (tables without a sequence no-op). One green CI run proves it.

Job still fails (correct outcome, wrong surface). MINOR.
- `validateShadowUrl` tests `/shadow/i` against the *whole* URL, so `postgres://u:shadow@localhost/production-named-db` passes the token check. Loopback-only containment makes this unexploitable today; NOTE-level hardening (match against pathname/database segment).
