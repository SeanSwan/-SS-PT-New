The migrate→seed→migrate order in `.github/workflows/migration-shadow-check.yml` matches brief §5.3. The live gate in `validateShadowUrl` still runs before any model import. Those two surfaces are not the break. The break is that this job can go green while inspecting the wrong password, the wrong report line, and a dependency graph that does not contain every FK the generator will try to satisfy.

**F1 — workflow password is not `shadow` (MAJOR).** YAML L20–22 claims user/password/database are the literal word `shadow`. L25 is `POSTGRES_PASSWORD: "***"`. Brief §4 says the same contract. Builder header frames this as “YAML `***` alias bug caught and quoted” — that is a quoting fix that left the wrong secret in place. If `DATABASE_URL` uses password `shadow`, migrate/seed cannot auth and the job is dead. If `DATABASE_URL` was also pointed at `***`, the job can go green on a password the brief and the comment both forbid. Fix: L25 `POSTGRES_PASSWORD: "shadow"`; Export step password must be `shadow` so the URL the seeder and `npm run migrate` use matches the service.

**F2 — deps graph is association-only; `tableNameToModel` is built after topo (MAJOR).** `seed-shadow-db.mjs` L355–366 walks `m.associations` only, then L368 `topoSort`s that graph. `normalizeModel` L261–274 already records attribute-level `references` as `foreignKeyTarget`. Those FKs drive `generateRowValues` L176–186 and the §4 insert, but they do not constrain order. Child-before-parent → insert fail → table in `failed` or empty → migrate-2 still runs against a void table. `tableNameToModel` is created at L377–378, after topo, so it cannot be used to resolve attr-level parents today. Fix: hoist `tableNameToModel` before the §3 loop; after the associations walk, add parents from `foreignKeyTarget` via that map, keep only `registry.has(parentNm)`.

**F3 — single `pkCol` (MAJOR).** L422 `Object.keys(attrs).find(...)` + L440 `updateOnDuplicate: [pkCol]` + L448 `v[pkCol]`. Composite PK: conflict target is one column; second seed run duplicates or throws. Acceptance criterion “run twice, no duplicate PKs” is false for those tables. Fix: `pkCols = Object.keys(attrs).filter(c => attrs[c].pk)`; pass `pkCols` to `updateOnDuplicate`.

**F4 — scalar `insertedIds` / whole-slot FK assign / unused `tPk` (MAJOR).** L448–449 stores scalars. L180 assigns `parents[i]` wholesale to the FK column. L463–467 computes `tPk` and never uses it; backfill reads `insertedIds.get(...)?.[0]`. Internally consistent only while PKs are one column. The moment F3 stores maps, L180 writes an object into the FK and L467 writes a map into `update`. Fix: store `values.map(v => Object.fromEntries(pkCols.map(c => [c, v[c]])))`; `out[col] = parentRow[a.foreignKeyTarget.pk]`; backfill `insertedIds.get(bf.targetLower)?.[0]?.[attrs[bf.col].foreignKeyTarget.pk]`; delete `tPk`. Update `seed-shadow-db.test.mjs` and `seed-shadow-db.selftest.mjs` `parentIds` fixtures from scalar arrays to PK maps or those suites go red for the wrong reason.

**F5 — Assert greps the wrong surface (MAJOR).** Seed step stdout includes `SHADOW-SEED OK …` (L450), `SHADOW-SEED cycle-backfill …` (L474), then the report (L490). Assert is `grep '^SHADOW-SEED ' | tail -1`. Brief §9: a gate that inspects the wrong surface is worse than no gate. Today `tail -1` happens to be the JSON line; one extra `console.log` after L490 and Assert either fail-closes or parses the wrong text. Fix: `grep '^SHADOW-SEED {'`.

**F6 — `retry: 1` (MINOR).** `backend/vitest.config.mjs` L34–L35. The new suite is in this config’s `include`. A flake that fails then passes is a green check that certified nothing. Delete those two lines.

**F7 — backfill not deduped (MINOR).** L430 pushes one `{table,col}` per row. L463–474 `update`s `where: { [bf.col]: null }` — first pass writes every null, the next four are no-ops. Dedupe on `(table,col)` before UPDATE.

**F8 is a panel miscount, not a code defect.** I count 32 `ok()` calls in `seed-shadow-db.selftest.mjs` (8 URL + 4 topo + 4 uuid + 5 report + 6 generate + 5 type/name). That matches the builder’s “32/32” claim. Do not change the claim to 31 and do not add a dummy 32nd check.

Verified non-findings under this lens: step order is migrate → seed → assert → migrate-2 → import; `validateShadowUrl` is first in `main` with no override; `countRows` re-quotes `"${table}"` (the `"Users"` trap is handled on the count path); PII guard / determinism / synthetic-over-snapshot stay accepted intentional.
