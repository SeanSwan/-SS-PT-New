## ATTACKS

**Correctness**
- **Q1 (lock/transaction): No deadlock from this code alone** — a plain SELECT under MVCC takes no row locks, so session-row lock + unlocked package read cannot form a wait cycle. The real risks are: (a) if `getClientPackagePricing` is *not* passed the transaction, Sequelize v6 (no built-in CLS) pulls a **second pooled connection** inside the transaction — pool max N with N concurrent cancels = connection-pool livelock, everyone holding one connection waiting for a free second; (b) if `restoreCredit` later *writes* the package row inside this transaction, any flow that locks package→session (purchase, credit adjustment) inverts the order → real 40P01 deadlock. Verify transaction propagation and lock ordering; the doc shows neither.
- **Q2 (in-place mutation): Yes, trap.** Admin submits full $175 on a $110 package → derived $110 overwrites `billingOptions.chargeAmount` → any audit log, response echo, or retry path now records $110 as what the admin *requested*. Dispute evidence is destroyed and a retry-after-exception re-validates the already-clamped value as if operator-entered. Fix is one line: build and return `{...billingOptions, chargeAmount: derived}`.
- **Q3 (silent clamp): Wrong call.** This workstream's whole thesis is "never silently substitute a money number," and the clamp silently substitutes one. Today no legitimate >rate charge exists, but a configured no-show policy (build-next item) collides with it immediately, and a 90-min/multi-hour booking would be silently undercharged. Reject-with-error above the rate (or require an explicit `allowOverage`), and always return derived-vs-submitted delta so the UI can show "charged $X (adjusted from $Y)."
- **Q5 (re-arm vs `chargeTouched`):** Three defeating sequences: (1) **stale response ordering** — switch client A→B in the modal; A's slower response lands last and re-arms B's panel with A's price unless the hook has last-request-wins/AbortController; (2) **`pricingUnavailable` not reset to true at refetch start** — "cleared only on successful fetch" implies B's panel shows A's armed defaults during B's in-flight fetch, the original bug in new clothes; (3) **`chargeTouched` persisting across modal close/reopen or client switch** (if state lives in a parent) — re-arm never runs, or worse, arms from the previous client's snapshot.
- **Q6:** Honest floor, unfinished feature. A numberless "See cancellation policy" on a *decision* screen is a dead end (is the policy even reachable in the client app? Unverified). It should state the deterministic part the server knows: "Cancelling now (within 24h) incurs a fee of 50% of your session rate — [View policy]." Full fix = server-computed quote at warning time (see build-next #3).

**Security**
- **IDOR / scope leak (unverified):** `canSetBilling` checks *role*, not *ownership*. Can trainer A cancel/bill trainer B's client? The doc shows no `session.trainerId === req.user.id` check in the cancel path. One integration test as trainer-off-the-session settles it.
- **Authz gap = Blocker 1:** client cancel + null billing is an authorization question as much as a pricing one — the server must enforce policy *for* unprivileged cancellers, not just ignore their input.
- Idempotency (Blocker 2) is also the replay defense: no idempotency key on a money-mutating PATCH.
- No injection surface found in the described validation (`parseCancellationAmount` correctly rejects non-finite/negative; string inputs coerce to 0 → throw for non-`none` types). `-0 >= 0` passes the guard but `-0 <= 0` throws downstream — covered.

**Data-truth / schema drift**
- **Q4 (`isFallback`):** If `isFallback` is a boolean *returned by the helper* on lookup failure, a real package at exactly the fallback rate is fine — nothing breaks. The hazard is the future refactor that "simplifies" it to `rate === 175` value-sniffing, which would mis-flag every standard 60-min package. Lock it with a test: real package priced exactly 175 must be treated as real. The sharper adjacent issue is Blocker 4 (which package), not the rate coincidence.
- **`??` fixes JS-zero only.** If `lateFeeAmount` is a Postgres DECIMAL, node-postgres returns it as a **string** (`"0.00"`, `"88.00"`): truthy, so `??` passes it through into number-expecting render code (`.toFixed` crash or mangled display). And if any serialization path emits `late_fee_amount` (snake) while the frontend reads `lateFeeAmount`, `??` yields null and the client sees "See cancellation policy" even when the server stated a fee. Verify column type and the exact response shape of the endpoint feeding `mapLateCancelWarning`.
- `packageInfo.pricePerSession` assumes the helper's camelCase mapping matches the model; if `getClientPackagePricing` ever goes through a raw query, snake_case leaks silently.

**House rules:** No violations *evidenced* by the document — no MUI/Recharts introduced, no LLM paths (so zero-PII rule untouched), no yoga/meditation language, no "NASM-certified." But I cannot verify ≤300-line compliance for `UniversalMasterSchedule/*` after the added fail-closed branches + re-arm effect, nor palette-token/WCAG compliance of the new "Pricing unavailable" states. The printable pricing sheet needs a print-media light theme without breaking dark-first app tokens — check it.
