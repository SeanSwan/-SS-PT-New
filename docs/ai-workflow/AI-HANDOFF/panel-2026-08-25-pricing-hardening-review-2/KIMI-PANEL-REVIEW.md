## VERDICT
REVISE — the server-derived-charge architecture is the right fix, but it overrides the price without knowing whether the cancelled session was 30 or 60 minutes, so it can still record the wrong money, and the client panel now shows a dead-end instead of a number.

## BLOCKERS

1. **P1 — Rate override is duration-blind, so it corrects one wrong number with another.** `applyServerDerivedChargeAmount` receives the whole `session` object but passes only `session.userId` into `getClientPackagePricing` (session.service.mjs, new function added at the +133 hunk; the lookup call passes `session.userId` with no duration/sessionType argument). The business runs two rates — $175/60-min, $110/30-min (document's Product context). Concrete failure: a client whose package is the 30-min rate ($110/session) cancels a 60-min session, operator picks "Full Session Charge" → server overrides to $110, undercharging $65. Inverse: client with a 60-min package cancels a 30-min session → overridden to $175, overcharging $65. The old placeholder bug is preserved, just relocated to the server. The guard must select the package/rate matching the session's duration, and the seed gives no evidence it does.

2. **P2 (binding house-rule violation) — session.service.mjs exceeds the 300-line file cap by ~6x.** The hunk header `@@ -1675,6 +1728,7 @@` on session.service.mjs proves the file runs past line ~1729 post-change. The cap is non-negotiable per house rules; the new `applyServerDerivedChargeAmount` was added to the monolith instead of a `session-cancellation-billing.mjs` helper. Easy extraction; flagging because it's mandatory, not because it's a runtime risk.

3. **P2 — Client cancel panel is now a dead-end, and may be one permanently.** `SessionDetailClientCancelWarningPanel.tsx` (~line 129) renders the literal string `See cancellation policy` when `lateFeeAmount === null` — no link, no destination, and the client cannot evaluate whether to cancel. Worse, `mapLateCancelWarning` (SessionDetailModal.actions.ts, ~line 80) now depends on `result.cancellationPolicy?.lateFeeAmount`; if the warning endpoint doesn't actually populate a `cancellationPolicy` object on the client path (nothing in the diff shows the endpoint changed), then *every* client sees the dead-end string 100% of the time. That trades "invented $88" for "no information ever," and the owner just moved the placeholder problem rather than solving it.

4. **P2 — Client is told their credit was restored when the server said nothing.** Same file (~line 82): `creditRestored: result.cancellationPolicy?.creditRestored ?? true`. A missing policy object — exactly the case that now produces the null fee — defaults to `true`, i.e., the UI asserts a money/credit fact to the client on server silence. Same defect class as the $88 placeholder, untouched by this round. Should default to `null`/unknown and render neutrally.

5. **P2 — Clamping silently rewrites the operator's decision with no audit or feedback.** `billingOptions.chargeAmount = ... Math.min(billingOptions.chargeAmount, sessionRate)` mutates in place (session.service.mjs new fn). Two problems: (a) a legitimate charge above one session (no-show fee, multi-hour booking) is silently reduced — the document itself asks whether that's right, and the answer is it's wrong *as implemented* because there's no `logger.info` when the clamp changes the amount; (b) the in-place mutation erases the operator-submitted amount before any audit write, so "what the trainer asked for vs. what was charged" is unrecoverable. Log the override when it fires; consider clamp only for `late_fee` semantics.

6. **P2 — pricing.ts is a second, manually-synced source of pricing truth.** The file's own header admits it: "If pricing changes, it changes here AND in the storefront seeder." That's guaranteed drift — it's verbatim the process failure this whole workstream exists to fix ($200 tier, $160/session pack). The handoff sheet should read from a public pricing endpoint backed by the same DB/seeder the server now trusts, not a frontend constant.

No security blockers found: the new path adds no caller-controlled input (userId comes from the session row), preserves the admin/trainer-only billing gate, and introduces no injection, IDOR, replay, or tenant-scope surface.

## ATTACKS

- **Correctness:** (1) Duration-blind override — Blocker 1; this is the same defect class as the original 175/88 placeholder, moved server-side, so the shipped fix is incomplete at its own standard. (2) Edge leak: `Number.isFinite(sessionRate) && sessionRate > 0` guard means a legitimately $0 package (comped/promo session) returns early and *keeps the caller's validated amount* — the exact placeholder passthrough the guard exists to kill, for any free/intro session. (3) `isFallback` as the honesty signal is fragile: if the helper derives `isFallback` by comparing the found price to its hardcoded 175 (rather than "no package found"), a real client priced at exactly $175 gets classified as fallback and is ignored — the server then trusts the caller's number again. I cannot verify the helper's derivation from the diff (see CONFIDENCE). (4) Possible ordering bug: the pre-existing validator throws on `chargeType !== 'none' && chargeAmount <= 0`, and the override runs *after* `normalizeCancellationBillingOptions`; if any frontend path can submit `full` with a 0/blank amount, the request dies before the server-derived value can rescue it — only safe if the frontend always seeds a positive full amount, which the radio-gating suggests but the seed doesn't prove. (5) Rendering `` `$${lateCancelWarning.lateFeeAmount}` `` with no `toFixed(2)` — a 55.5 fee renders "$55.5". (6) Lock question the doc raises: a three-table read (Order/OrderItem/StorefrontItem) inside a transaction holding `LOCK.UPDATE` extends lock hold time and invites contention under concurrent cancels; it's not provably a **deadlock** from this document (no lock-order inversion is visible — reads here don't re-acquire the session row), but the lookup has no business being inside the lock and should be hoisted above the transaction boundary.

- **Security:** Clean by inspection. The override consumes only server-side state; the role gate (`canSetBilling`) is preserved before normalization; no new endpoint, no PII-to-LLM surface, no idempotency regression (cancellation was already non-idempotent and unchanged). One note, not a blocker: a failed pricing lookup logs `session.id` and `error.message` — if that logger ships anywhere client-visible, `error.message` can carry SQL detail; keep it server-side.

- **Data-truth / schema drift:** (a) `pricing.ts` duplicates backend seeders by hand — Blocker 6. (b) Frontend now expects `cancellationPolicy.lateFeeAmount` in the warning response, while no endpoint change is shown — if the server emits `{ lateFeeAmount }` flat or omits the policy object, the frontend renders the dead-end string forever (Blocker 3, response-shape drift candidate). (c) `LateCancelWarningModel` compiles `result: any` — the drift-prone typing style is untouched; a narrow interface for the warning response would have caught (b) at compile time.

- **Build-next, ranked by value/hour for a trainer-led business whose #1 gap is acquisition:**
  1. **Wire the cancel-warning endpoint to `getClientPackagePricing`** so clients see their real fee. The helper already exists; this finishes Blockers 1/3/4 properly instead of shipping "See cancellation policy." Cheapest high-value fix in the document.
  2. **Admin cancellations report:** one read-only tab — cancellations by trainer/client, late-cancel rate, fees assessed vs. waived vs. clamped, credits restored, revenue recovered. Trainers/admins currently have zero cross-client visibility into the thing that directly touches revenue.
  3. **Referral-attributed milestone shares:** the core loop already says "make milestones shareable"; give each share a referral link and attribute inbound signups. This is the only build-next item aimed at the owner's stated #1 gap (acquisition) rather than internal tooling, and beats everything above strategically.
  4. **Configurable cancellation policy** (late window hours, fee as % or fixed, credit behavior) in a settings table instead of the hardcoded 50% — small table, removes a hardcoded business rule from code.
  5. **Public pricing endpoint consumed by the handoff sheet and any public page** — kills Blocker 6 and gives the acquisition surface a single truth.
  6. **Money-path reconciliation:** charges are recorded — is anything collected? An "assessed-but-unpaid fees" ledger plus a payment link is the missing end of the cancellation money path.

## HIGHEST RISK
Blocker 1 — the server now has the *authority* to decide what a full session costs and uses it without knowing the session's duration, in a business with exactly two durations. Every property the original fix was built on (server is the truth, never trust the caller) is undermined the first time a mixed client cancels. Cheapest de-risk before ship: pass the session's duration/type into `getClientPackagePricing` and select the matching package item rate (or return null and leave the validated amount alone when ambiguous), plus one unit test — a $110/session client cancelling a 60-min session with `chargeType: 'full'` must not record more/less than the correct rate, and vice versa. Two-ish hours, closes the hole this entire workstream was opened to close.
