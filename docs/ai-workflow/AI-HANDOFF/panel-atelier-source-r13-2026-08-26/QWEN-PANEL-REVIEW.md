## VERDICT
REVISE — The `estimateOnly` path bypasses the authoritative `commit` gate and the idempotency store, creating a race condition where concurrent preview requests can double-reserve GPU resources or bypass spend ceilings if the ledger is degraded.

## BLOCKERS
1. **P0**: **Race Condition in `estimateOnly` GPU Reservation**: In `composeLaneChoice.mjs`, `admitLocal` returns `{ reservation: null }` for `estimateOnly`. However, in `composeStills.mjs`, the `estimateOnly` path returns *before* the `commit` gate. If two concurrent `estimateOnly` requests hit the local lane, they both pass `chooseLane` (which does not reserve for estimates) and both return successfully. This is safe for *spend* (since estimates don't spend), but if the local lane's `admit` function has side effects (e.g., updating a "busy" flag or VRAM allocation counter) that are *not* wrapped in the `reserve()` call (which is skipped for estimates), the state may be corrupted. More critically, if `admit` *does* allocate resources (even temporarily) and the code assumes `reservation` is the only handle to release, the `estimateOnly` path never calls `reservation?.release()` because `reservation` is `null`. If `admit` has any side effects beyond pure checking, they are leaked. **Evidence**: `composeLaneChoice.mjs:42-45` (`admitLocal` returns `null` reservation for estimates) vs `composeStills.mjs:155-158` (estimate path returns without releasing anything, assuming no reservation was made).
2. **P1**: **Bypass of Authoritative Commit Gate for Estimates**: `composeStills.mjs:155-158` returns the estimate result *before* the `commit` call at line 170. The `commit` gate is described as "THE AUTHORITATIVE MONEY GATE" that checks *both* ceilings atomically. While `gateHosted` checks the spend ceiling for estimates, it does so *before* the atomic commit. If the ledger is degraded (`usage.degraded` is true), `gateHosted` throws `E_LEDGER_DEGRADED` for non-estimates but *allows* estimates (line 68 in `composeLaneChoice.mjs`). This means an estimate can succeed even when the system is in a state where no *actual* spend is allowed. This is logically consistent (estimates don't spend), but it creates a **state divergence**: the UI shows a valid price, but the user cannot execute it. The error message for `E_LEDGER_DEGRADED` says "a billed model cannot be charged safely," but the estimate path silently succeeds, potentially misleading the user into thinking the system is operational. **Evidence**: `composeLaneChoice.mjs:68-71` (degraded check skipped for estimates) vs `composeStills.mjs:170-180` (commit gate skipped for estimates).
3. **P2**: **Idempotency Store Not Updated for Estimates**: `composeStills.mjs:128` only sets the store key if `!req.estimateOnly`. This means concurrent `estimateOnly` requests with the same key will *not* coalesce. If the local lane's `admit` function is not idempotent (e.g., it increments a counter), multiple estimates will cause multiple side effects. **Evidence**: `composeStills.mjs:128` (store.set skipped for estimates).

## ATTACKS
- **Correctness**: The `estimateOnly` path bypasses the `commit` gate, which is the only place where the *atomic* check of both run and spend ceilings occurs. While `gateHosted` checks the spend ceiling, it does so in a non-atomic manner (read `usage.spendUsd`, then check). If two estimates are processed concurrently, they both read the same `usage.spendUsd` and both pass. This is safe for *estimates* (since they don't spend), but if the `usage` object is mutated by other processes (e.g., a background job), the estimate may be based on stale data.
- **Security**: The `estimateOnly` path does not require an owner (`assertKeyHasOwner` is called, but it only throws if `req.idempotencyKey` is present and `userId` is missing; estimates typically don't have an `idempotencyKey`). This means anonymous users can generate unlimited estimates, potentially DoS-ing the local lane if `admit` has side effects.
- **Data-truth / schema drift**: The `estimateOnly` response includes `cost: { ...cost, chargedUsd: 0 }`. The `cost` object is built from `gateHosted` (for hosted) or a hardcoded object (for local). If `gateHosted` throws `E_LEDGER_DEGRADED` for non-estimates but allows estimates, the `cost` object is still returned. This is consistent, but the `chargedUsd: 0` field may be misleading if the system is in a degraded state.

## HIGHEST RISK
The **race condition in `estimateOnly` GPU reservation** (Blocker 1) is the most dangerous. The cheapest way to de-risk is to **make `admitLocal` idempotent for estimates** by ensuring that `admit` has no side effects when called with `estimateOnly: true`, or by **wrapping the estimate path in a try-finally that releases any resources acquired by `admit`**.
