# 2. Attack on S3a

**The three-valued outcome is right and is the best thing in the slice.** `blocked_by_policy` ≠ `dead` is exactly the distinction that prevents the "fix the 403 by spoofing a browser" failure. Keep it. But it's incomplete: there's no fourth value for **content-changed** — a feed that returns 200 with a parked-domain page, a redirect to a homepage, or a CAPTCHA wall is `live` under any liveness rule keyed on status + parseability of *something*. The manifest will record these as live and the merge decision downstream will trust them. Add `degraded`/`content_anomaly` or the liveness rule must include a content-shape check (item count > 0, GUIDs present). As specified, "liveness rule" is pinned but its definition isn't shown — if it's status-code-only, the spec is certifying garbage as live. **LIKELY** this gap exists, since the doc lists "UA, timeout, redirects, concurrency, delay, retries, liveness rule" without stating the rule.

**Cross-version diff refusal is too strict, and the stated reason proves it.** "Differences would be attributable to the tool" — yes, and sometimes that's the *point*: when you bump the spec (say, timeout 5s→10s), the first question everyone asks is "what flips?" Refusing to answer forces operators to hand-diff two manifests with no tool support, or worse, to never bump the spec because the migration cost is unbounded. The spec is versioned precisely so versions change; a differ that refuses across versions makes version bumps operationally frozen. The right behavior: cross-version diff runs but every hunk is labelled `spec_changed: vN→vM` and excluded from any "publisher-side change" count. Refusal should be reserved for diffing manifests with *missing* `specVersion` — which, since the field is required, can't happen. **CERTAIN** this will be worked around within a month of the first spec bump.

**What the manifest fails to capture that a merge decision needs:**

1. **Per-outlet history, not a snapshot.** A dated manifest answers "what was true on 2026-08-21." A merge decision needs "has this feed been live for 30 consecutive days" — one probe proves reachability, not reliability. No retention of prior manifests is described; "diffs against the previous" implies exactly one previous is kept. **LIKELY** single-generation retention.
2. **Fetch cost.** A feed that takes 9s of a 10s timeout is "live" and will be the first thing to blow the sync budget at 107 outlets. Latency per host belongs in the manifest; it's free to record at probe time and expensive to discover later. **CERTAIN** it's absent (not in the listed spec fields).
3. **The probe's own identity is pinned but its *network position* isn't.** UA and timeout are in the spec; egress IP/ASN isn't. A probe run from a datacenter ASN gets different 403s than one from residential. If probes ever run from CI vs. a worker, results differ with `specVersion` identical — the exact failure the versioning was built to catch, surviving it. **LIKELY** unhandled.
4. **`blocked_by_policy` has no reason code.** robots-disallow vs. 403-vs-our-UA vs. paywall are three different merge decisions (respect, renegotiate, drop). One bucket forces someone to re-probe manually to decide. **CERTAIN** as specified.

Also: the `test:scripts` glob fix is the most important line in §3 and it's buried. The suite was structurally blind to `scripts/lib/**` — meaning *every* prior claim about scripts tests passing (153 pass) was made by a runner that couldn't see some of the tests. Audit what else the globs miss before trusting any suite count in this document. **CERTAIN** the blindness existed; **SPECULATIVE** that other globs have the same shape — check `*.test.*` patterns repo-wide.

Doing S7 before S8–S10 builds the integration surface before the thing being integrated exists, guaranteeing the mapping is designed against guesses. **Missing slice: there is no syndication *ground truth* step between S3b and S9.** S9's fixture trio is synthetic. The entire product thesis — "restated text hides corroboration, source-side evidence reveals it" — has never been tested against real wire content (AP/Reuters stories carried by multiple outlets in the 107). **S4 is secretly three slices.** (a) Provenance columns — additive, reversible, cheap. (b) Retention/volume budget + enforcement job — a *data-deletion* system with its own failure modes (what does the job do on partial failure? does it log what it pruned? is pruning itself provenance-recorded?). (c) The lifecycle decision — a product/policy call with zero code relationship to (a) or (b). Bundling a destructive job with a schema migration means the migration's review gets the deletion job's scrutiny budget or vice versa. Split it.

**S5 is secretly two.** "Seed 107 dormant" and "first cohort of 10 live" have different blast radii and different rollback stories. Seeding dormant rows is reversible (delete rows). Enabling 10 live connectors starts *spending quota and fetching external content* — that's the first moment the system touches the outside world at scale, and it shares a row in the table with a data load.

**Where it becomes irreversible — precisely: S4's retention enforcement job, first run, against items ingested before the provenance columns were populated.** The doc says "items ingested without provenance can never support syndication detection" — correct — but the irreversibility is sharper than stated: the moment the enforcement job prunes an unprovenanced item, the *evidence that the item ever existed* is gone, so you can't even measure how much of your corpus is unprovenanced after the fact. The 10 existing `official_connector_items` are the test case: if any predate provenance columns, S4 as written either prunes them (data loss, unmeasurable) or exempts them (the job ships with a carve-out on day one). The irreversible line is not "S4" — it's the first execution of the enforcement job, and the doc never says what happens to pre-existing rows. **That decision is currently unmade and will get made by default, by the job.**

Secondary irreversibility: S5's live cohort begins accumulating `quota_spent` and external fetch receipts against contract approvals that are family-scoped (§4.2). If `feed_set_hash` isn't bound before S5, every receipt written under the loose attestation is evidence signed against the wrong scope, permanently.

**§4.2 — Bind `feed_set_hash` into contract approvals before S5, not as part of S3b.** It's a small change: add the column, compute the hash at approval time from the sorted feed-set, recompute and compare at enable and at `sync()`. The terms gate narrowed exposure; it did not close the hole, and S5 is the first slice that writes receipts under attestation. Doing it after S5 means receipts exist that no attestation covers. Do it now, family-scoped approvals become feed-set-scoped, the 2 existing rows get re-approved (there are only 2 — the migration cost is a conversation).

**§4.3 — Do not gate on `terms_acknowledged_at`. Delete the column or repurpose it.** Gating blocks 39/39 including the one live outlet — that's not a gate, it's a shutdown. The honest model: `termsUrl` presence + a recorded *review* (who read the terms, when, outcome: crawl-ok / link-only / blocked) is the gate; "acknowledged" implies a counterparty action that will never happen for RSS. Replace `terms_acknowledged_at` with `terms_reviewed_by/at/outcome` in S3b, which is already supplying ownership data. This folds §4.3 into S3b at zero extra cost.

**§4.4 — Make `lifecycle` a real gate or delete the column; do not leave it as display metadata.** A column named `lifecycle` that nothing enforces is a trap: the next engineer will write `WHERE lifecycle = 'active'` assuming it means something, and it will silently include/exclude the wrong rows. Given `owner_enabled` is the real gate, the minimal correct move is a CHECK constraint or trigger making `lifecycle` a *derived function* of `owner_enabled` + probe state (dormant = never enabled; active = enabled; dead = blocked_by_policy/dead per manifest), so it can never disagree with the gate. That kills the "born dormant describes a control that does not exist" problem by making the description true.

# 6. The endgame

**The single biggest reason this lane never reaches a working disagreement map: the independence model gets built on self-declared registry data, so syndication and common ownership are undercounted from day one, and the map reads coordinated content as independent corroboration — the exact failure the product exists to prevent.** Everything in S3b's identity story — registrable domain, publisher identity, `independence_group_id`, ownership — comes from the registry, i.e., from what outlets say about themselves. Wire content (AP, Reuters, syndicated columns) doesn't announce itself per-feed; ownership (the same company owning 40 local outlets under 40 domains) isn't in any RSS field. If S9's clustering runs on independence groups derived from declared data, the fixture trio passes, the suite is green, and the shipped map systematically overstates independence — silently, because there's no ground-truth check against reality. A disagreement map that inflates corroboration is worse than no map: it manufactures consensus.

**The build step that prevents it: the missing ground-truth slice from §3 — before S9, run the deterministic syndication detector and the independence grouping against a hand-labelled sample of real content from the live 107 (known wire stories, known same-owner outlet clusters), and require measured precision/recall on syndication edges and independence groups as the gate for S9, not the fixture trio.** The fixture proves the code does what the code says. Only labelled real data proves the model of the world is right — and the labelling is cheap now (107 outlets, a few dozen stories) and effectively impossible to retrofit after S10's map is being shown to users as evidence.
