## HIGHEST RISK
The entire settled-defect edifice — identity-checked deletes, synchronous misses, conditional writes — is true **only in one process against one synchronous Map**. The hosted lane re-runs for money; the moment it runs behind a second replica (or the store is swapped for anything async), every invariant becomes probabilistic and the failure is *silent double charges*, no crash, no log line. Cheapest de-risk before ship, ~an afternoon: (a) a "REPLAY STORE CONTRACT" header stating single-process/synchronous/reference-identity as checked invariants, not folklore; (b) a dev-mode assertion that store methods never return thenables (turns blocker #4 into a loud failure); (c) a deploy-gate: claim keys live in exactly one process — CI fails any multi-replica config; (d) write the Redis mapping *now* (`SETNX`≈`claimIfAbsent`, Lua compare-and-delete≈`dropIfStillOurs`, key TTL≈`replayExpiresAt`) so the eventual port is translation, not reinvention.

## RECOMMENDATIONS
*(per the brief's item 4 — Sean's standing ask)*

1. **Observability before launch.** Every decision in this module is silent except contention. Emit counters at each branch: `replay.hit{lane, ageMs}`, `replay.miss{reason: absent|expired|rejected}`, `claim.win`, `coalesce.join`, `contention.exhaust`. Alert when hit-age approaches `BATCH_TTL_MS` — the dishonest-200 failure mode becomes a dashboard line instead of a support ticket.
2. **Deterministic concurrency harness.** All fifteen prior defects were interleavings; stop testing them with sleeps. Build a scripted microtask scheduler (fake clock + manual drain, tests author interleavings as ordered op lists) and a property test over random op sequences (claim / resolve / reject / advance-clock / replay / release) asserting three invariants: ≤1 owner per key; no replay body served past its row's TTL; every delete's token matched at delete time (instrumented store). This is the docstring made executable — given how load-bearing the comments are here, that's the highest-leverage test investment in the codebase.
3. **Give the deliberate-untested list an owner and a trigger.** `chargedUsd` parity and the retention predicate are fine to defer pre-revenue, but "parity test passes" should be a hard launch gate on the hosted lane's billing switch, written down now while it's cheap.
4. **Shrink the exemption surface.** Stamp `acceptedAt + BATCH_TTL` on the 202 stub so every stored value carries a deadline; `fromClaim`'s absence-exemption becomes near-dead code and the starved-continuation window closes for free. Fail-closed direction is already safe.
5. **Rejection taxonomy.** Owner rejects with a domain sentinel (`E_RENDER_FAILED`) vs. internal errors; retry the former, count and surface the latter. Retry-on-bug is how one crashed render becomes N.
6. **Contention semantics at the edge.** Verify `E_REPLAY_CONTENTION` maps to 409/429 + `Retry-After` — "retry in a moment; nothing was spent" is exactly right copy for a retryable status and exactly wrong for a 500.
7. **Eviction (SWA-165 class, not re-raised, but the cheap version is one afternoon):** per-user live-key count cap plus per-user LRU. That bounds the client-keyed memory amplifier without touching the watchdog design — and I agree with the filed reasoning that the never-settling claim wants an owner-side watchdog, not a waiter-side timeout.
8. **Atelier-wide:** this guard's shape is generic — reuse it at **publish/assets**, where a re-publish of the same key should replay the prior asset handle rather than re-render; a second bespoke guard there would be the seventeenth pair-defect waiting to happen. Derive the client key **once at the API edge** and consume it in every stage (brief→still→motion→publish→assets) rather than re-deriving per stage. Add an append-only replay audit log (key, decision, deadline, batchId — IDs only): on a paid lane, "why was I charged twice" needs an answer trail, and a daily reconciliation job (ledger vs. batch rows vs. replay decisions) catches drift cheaper than debugging it. Last: a per-user spend cap on the hosted lane so the replay guard's failure mode is bounded by policy, not only by correctness.
