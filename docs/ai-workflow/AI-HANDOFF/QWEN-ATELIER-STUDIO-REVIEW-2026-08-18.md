### 3. A2 is the crux — attack it. Will the diversity contract produce different variants?
**No. It will produce 7 flavors of the same layout. This is a known failure mode of LLMs.**

**The Attack:**
You propose: *"Each variant is seeded with a distinct `(archetype × style-taxonomy axis × motion budget)` triple... generated by parallel subagents that cannot see each other's output."*

**Why this fails:**
1.  **Semantic Collapse:** Even with different seeds, LLMs converge on "safe" design patterns. If you ask for "Construction Business, Modern, High Motion," 7 models will all produce a hero section with a left-aligned headline, a right-aligned image, and a blue CTA button. The *structure* is determined by the *intent* (Construction), not the *style* (Modern).
2.  **Parallelism is a Lie:** "Parallel subagents" in a single context window or even separate API calls often share the same underlying latent space biases. They are not truly independent creative entities; they are stochastic samplers from the same distribution.
3.  **The "Similarity Check" is Too Late:** Regenerating a pair above a threshold is a reactive patch. It wastes tokens and time.

**The Cheapest Reliable Mechanism for Genuine Divergence:**
**Constraint Inversion, not Parameter Variation.**
Instead of varying *style*, vary *structure* and *negative constraints*.
*   **Variant 1:** "Hero must be text-only. No images."
*   **Variant 2:** "Hero must be a full-bleed video. No text overlay."
*   **Variant 3:** "Layout must be asymmetric grid. Left column 70%, Right 30%."
*   **Variant 4:** "Dark mode only. High contrast."
*   **Variant 5:** "Minimalist. Single font. No icons."

**Cite:** This is how human designers diverge. They don't just change colors; they change the *grammar* of the page. The "Diversity Contract" must mandate **structural opposites**, not stylistic nuances. If two variants have the same DOM structure (e.g., `<header><h1><p><button>`), they are the same variant.

### 4. A4 merge: Is merge-by-instruction a fantasy?
**Yes. It is a fantasy. It will always degrade into regeneration.**

**The Attack:**
You claim: *"Requires each variant to expose a structured token/section manifest... otherwise merge is a re-generation."*

**Reality:**
1.  **Semantic Mismatch:** "Take 3's layout with 5's palette" is not a mechanical operation. Layout 3 might rely on a specific aspect ratio for its hero image that conflicts with Palette 5's color blocking. The "manifest" does not capture *why* the layout works.
2.  **LLM Hallucination in Merge:** If you feed two HTML files and a prompt "Merge A and B," the LLM will not perform a diff-and-merge. It will *read* both, form a mental model of "what a good construction site looks like," and *generate a new third site* that resembles both. This is not a merge; it is a new generation.
3.  **Cost:** A "merge" prompt is often longer and more complex than a "generate" prompt, making it *more* expensive, not less.

**The Blunt Truth:**
Stop selling "Merge." Sell **"Iteration."**
*   Sean picks Variant 3.
*   Sean says: "I like the layout, but make it look like Variant 5's color scheme."
*   The system takes Variant 3's HTML, injects Variant 5's CSS tokens, and regenerates.
*   **This is not a merge engine. This is a targeted edit engine.** Do not build a "Merge Engine" (A4). Build a "Token Injection" step in the Convergence Loop (A5).

### 5. N-number: Is 5/7 right?
**No. 5 is too many for judgment; 7 is too many for cost.**

**Reasoning:**
*   **Judging Capacity:** Sean is a human. Comparing 7 distinct HTML layouts side-by-side on a canvas is cognitively overwhelming. He will not notice the subtle differences in spacing or typography. He will pick the one that "feels right" in 5 seconds, which is usually the most visually loud one, not the best one.
*   **Cost:** 7 variants = 7x the token cost for generation + 7x the token cost for the "similarity check" (if you keep it) + 7x the token cost for the final "pick" prompt.
*   **Recommendation:** **N=3.**
    *   **Variant A:** The "Safe" option (Standard industry layout).
    *   **Variant B:** The "Bold" option (High contrast, unusual grid).
    *   **Variant C:** The "Minimal" option (Text-heavy, whitespace).
    *   **Why 3?** It forces a clear choice. It is easy to compare. It is 60% cheaper than 5. It aligns with the "Batch-and-select law" (T4) which says "2-3 rounds then stop."

### 6. R4 / recall: How to make a 61KB file reliably reachable?
**Do not load the file. Load the *Index*.**

**The Problem:**
A 61KB file is too large for context. If you load it, you waste 15k-20k tokens on data you might not need. If you don't load it, the agent guesses.

**The Concrete Solution:**
1.  **Create a `design-brain/index.json` (or `.md`)** that is < 2KB.
2.  **Structure:**
    ```json
    {
      "archetypes": {
        "construction": {
          "file": "website-archetypes.md",
          "section": "# Construction",
          "key_traits": ["Trust", "Safety", "Project Gallery"],
          "recommended_styles": ["Industrial", "Clean Corporate"]
        },
        "fashion": { ... }
      }
    }
    ```
3.  **Workflow:**
    *   Agent receives brief: "Construction business."
    *   Agent reads `index.json` (cheap).
    *   Agent sees `key_traits` and `recommended_styles`.
    *   Agent *only* loads the specific section of `website-archetypes.md` if it needs deep detail.
    *   **Crucially:** The `index.json` contains the *decision logic*, not the *data*. The agent uses the index to make the choice, not to read the whole library.

**This solves R4 without bulk loading.**

### 7. The Sean-serialized bottleneck: Does N-up make it worse?
**Yes. N-up makes the bottleneck 5x worse.**

**The Attack:**
You assume Sean will "judge side-by-side." He won't. He will get overwhelmed.
*   **Current State:** Sean sees 1 site. He says "Good" or "Change X."
*   **N-up State:** Sean sees 5 sites. He says "I like 3, but 5 has better colors." Now you have to explain *why* 3 is better than 5, or re-generate 3 with 5's colors. This is a **negotiation**, not a judgment.

**The Solution: Proxy Rubric + Automated Scoring.**
1.  **Automated Scoring:** Before Sean sees the variants, the system runs a "Taste Check" script.
    *   Check: "Does the hero have a CTA?" (Yes/No)
    *   Check: "Is the contrast ratio > 4.5?" (Yes/No)
    *   Check: "Is the font size > 16px?" (Yes/No)
    *   **Score:** 0-100.
2.  **Filtering:** Only show Sean the **top 2** variants by score.
3.  **Reasoning:** "Variant 3 scored 95/100. Variant 5 scored 80/100 (failed contrast check)."
4.  **Result:** Sean judges 2 options, not 5. The "bottleneck" is reduced by 60%.

**This is not a "proxy rubric" in the abstract sense. It is a **Quality Gate** that filters out bad options before they hit Sean's eyes.**
