**F14 (new MAJOR) — AiConversation cannot CAS and is denormalized.**
`AiConversation.mjs:24-83` is labeled authoritative and enumerates `userId, role, context, targetUserId, messages, status, metadata, messageCount, lastMessageAt`. There is no `version` / etag / revision. `messages` + `messageCount` are two representations of one fact with no evidenced CHECK, generated column, or trigger. Writers exist at `useAIChat.ts:217,425,448` (create + POST messages). Under any read-modify-write of the JSON blob, a second device or double-submit silently drops appends; under a split update, `messageCount` drifts from `messages`. Constraint 3 says memory is not domain truth; it does not license lost conversation continuity (owner outcome + Q3). Residual (f) calling this “unproven pending write-SQL” understates a model-level integrity hole: the table *as specified* cannot express a safe multi-writer append. Default-deny until the write path is a single `UPDATE … SET messages = messages || $new, messageCount = messageCount + 1, version = version + 1 WHERE id = $id AND version = $seen`.

**REJECT F4 HOW (Postgres UNIQUE / CAS / undo), not F4 the finding.**
`AiCommandAuditLog.mjs:24-91` still has no `action_id` and no unique idempotency key; `useCoachCommand.ts:96,170,207` are three uncoupled endpoints; `dispatchAIWorkoutEvent` at `aiWorkoutEvents.ts:121-128` is a boolean. Receipt + CAS is required. The candidate’s `UNIQUE(idempotency_key)` is not Postgres-true: UNIQUE allows multiple NULLs, so an omitted key bypasses the constraint; a client-minted global key collides across actors. Packet has zero schema — that does not license a wrong one.

Required contract: `idempotency_key TEXT NOT NULL`, `UNIQUE(actor_id, idempotency_key)` (not a bare global unique), `CHECK(status IN ('draft','pending_confirm','applied','denied','cancelled','failed','reversed'))`, and every execute/confirm/cancel/undo is `UPDATE receipts SET status = $next WHERE action_id = $id AND status = $expected RETURNING *` — 0 rows is a conflict, never a second success. Q5 demands undo; the three-endpoint surface has none, so `applied → reversed` must exist or undo is a lie. Do not reuse `AiCommandAuditLog.mjs:24-91` as that row.

**REJECT F6 HOW (effect over-reset), not F6 the finding.**
`CoachCommandCenterPage.tsx:38-42` initializes `activeTab` once via `useState(() => coerceCoachTabForRole(initialTab, userRole))`. Role hydrate, impersonation, and `?tab=` deep-links leave a stale tab — real. An effect on `[userRole, searchParams]` is wrong: any unrelated query change reclobbers an in-session tab click. Correct machine: depend on `[userRole, routeForcedTab]`; if `routeForcedTab` is set, `setActiveTab(coerce(routeForcedTab, userRole))`; else re-coerce the *current* tab so a now-illegal role tab falls back and a legal user selection is left alone.
