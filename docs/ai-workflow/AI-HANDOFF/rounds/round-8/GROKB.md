**REJECT F4 HOW (incomplete, not optional).**  
`AiCommandAuditLog.mjs:24-91` records actor, role, resolved target, operation, outcome, error, hash, duration. It has no `action_id`, no unique idempotency key, and no reversal pointer. `aiWorkoutEvents.ts:121-128` returns a dispatcher boolean. Constraint 2 requires wrong-client mutation to be recoverable. Constraint 4 forbids success copy before an authoritative verified write. The candidate correctly refuses to reuse the audit row as a receipt and correctly adds `UNIQUE(idempotency_key)` plus CAS so execute/confirm/cancel cannot all succeed. That only stops double-success. It does not make an `applied` mutation recoverable. The machine `draft→pending_confirm→applied|denied|cancelled|failed` has no `applied→reversed` edge and no `reverses_action_id` / `compensating_action_id`. After a catastrophic-class apply, operators have an outcome bit and nothing to invert. That is the still-open running-state defect. Shipping F4 as written ships unrecoverable mutations.

F4 provenance is also wrong-scoped. Receipt provenance is listed as `chat|command|workout-bridge`. Competing write lanes `/api/coach/intake` and `/api/coach/proposals` mount at `routes.mjs:378-379` (gate table). F2 only blocks ungated routers; a gated proposal/intake apply can still mutate domain state outside the receipt authority. Parallel write authority is a data-truth break of constraint 3.

Confirm and cancel cannot both succeed; reverse cannot succeed twice. If the audit log is kept as forensics, add `action_id` FK + `reverses_action_id` — it is still not the receipt.
