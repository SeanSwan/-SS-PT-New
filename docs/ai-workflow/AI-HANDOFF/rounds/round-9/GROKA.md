Two stores, two inserts, one fact.

**REJECT F4 machine completeness.** `draft→pending_confirm→applied|denied|cancelled|failed` has no `queued` state and no reconcile transition. execute/confirm/cancel CAS does not cover replay of an offline row. Confirm+cancel cannot both succeed is necessary and insufficient.

**F15 MAJOR — bind C6 to F4 in one uniqueness domain.**

WHAT: one `ActionReceipt` relation is the uniqueness and CAS domain for online and offline-originated actions. The offline queue is a buffer that inserts/gets that row as `queued`; it is not a second fact store.

WHERE: new relation (not `AiConversation.mjs:24-83`, not `AiCommandAuditLog.mjs:24-91`); writers are `/api/ai-command` execute|confirm|cancel (`useCoachCommand.ts:96,170,207`), chat-originated actions from `AITerminalPanel.tsx:116-139` / `useAIChat.ts:217,425,448`, and the gym-floor offline enqueue that does not exist in packet today. `dispatchAIWorkoutEvent` (`aiWorkoutEvents.ts:121-128`) must not be treated as enqueue or success.

HOW:
1. Columns: `action_id` PK, `idempotency_key TEXT NOT NULL UNIQUE`, `capability`, `client_id` (server-resolved, immutable after insert), `actor_id`, `provenance CHECK (chat|command|workout-bridge|offline-queue)`, `status CHECK (queued|draft|pending_confirm|applied|denied|cancelled|failed)`, `version INT NOT NULL DEFAULT 0`, `payload_hash`, timestamps.
2. Postgres: `UNIQUE(idempotency_key)` on a `NOT NULL` column (nullable UNIQUE allows multiple NULLs and bypasses F4). No DELETE of receipts. Terminal rows stay. Do not reuse `AiCommandAuditLog.mjs:24-91`.
3. Enqueue: `INSERT … status='queued' ON CONFLICT (idempotency_key) DO NOTHING RETURNING *`; conflict returns the existing row; never insert a second domain fact.
4. CAS only: `UPDATE action_receipts SET status=$next, version=version+1 WHERE idempotency_key=$k AND status=$expected AND version=$v RETURNING *`. Zero rows = conflict; return existing receipt; do not apply the domain write. Legal edges: `queued→pending_confirm|applied|failed`, `draft→pending_confirm|denied|cancelled|failed`, `pending_confirm→applied|denied|cancelled|failed`. Illegal: confirm or cancel of `applied`; apply of `cancelled`; any client_id rewrite.
5. Reconcile is that CAS, not “replay the handler.” Domain mutation runs iff CAS returns a row.
6. Core workout fact keys are deterministic: `hash(server-resolved client_id + workout_session_id + movement_id + set_index + local_logged_at_bucket)`. Client random UUIDs do not stop two gym-floor devices from double-applying one set; `UNIQUE` cannot help if the keys differ.
7. Constraint #4: UI success only on a receipt in `applied` (or an explicit `queued`/`pending_confirm` unsynced state). `dispatchAIWorkoutEvent` boolean never maps to saved.
