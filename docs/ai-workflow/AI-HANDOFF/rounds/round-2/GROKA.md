**F3 / dual-path client identity is a split state machine, not a UX nit.**  
`AITerminalPanel.tsx:119` and `:133` send `clientId || null`. `aiChatRoutes.mjs:308-344` accepts caller `targetUserId` on create. `aiCommandRoutes.mjs:111-145` accepts caller `selectedClientId`. `clientResolver.mjs:110-166` scopes trainers and stops at role for admins. `commandExecutor.mjs:309-343` only “resolves” those IDs. Three independent client keys can be live in one session. Constraint 2 (wrong-client mutation is catastrophic) is already violated at the type level: there is no single server-issued context token, so chat memory and command apply can name different clients and both “succeed.” Fix is not “validate the client’s clientId.” Kill the caller field. Bind receipts to the server-resolved `client_id` only.

**F4 / missing unique idempotency is a retry race, not a docs gap.**  
`AiCommandAuditLog.mjs:24-91` records actor, role, resolved target, operation ID, outcome, error, hash, duration. It does **not** have `action_id` or a UNIQUE `idempotency_key`. `aiWorkoutEvents.ts:121-128` returns a dispatcher boolean. Constraint 4 forbids painting success before an authoritative write; constraint 6 requires retry without duplicates. A confirm/cancel/retry pair against that audit table can apply twice or apply+cancel with two success rows. Required command state machine: `draft → pending_confirm → applied | denied | cancelled | failed`, CAS on a version/status column, UNIQUE(`idempotency_key`) at storage. `dispatchAIWorkoutEvent` boolean never maps to UI success. `AITerminalPanel` paints success only on a receipt row.

**N2/N3 / `'both'` vs omitted default is two persistence machines in one panel.**  
`AITerminalPanel.tsx:116-122` calls `sendMessageWithConversation(..., clientId || null, 'both', null, requestContext)`. `:133-136` omits mode, 6th, and 7th args. Partial failure of `'both'` has no defined status. Conversation `status` (`AiConversation.mjs:24-83`) is not an action receipt and must not become one. One explicit mode. Every failure state named. C6 stands: offline queue is a **separate durable store**, never `AiConversation.messages` / `status`.

**F6 / `activeTab` is a one-shot coerce — stale after role hydrate or searchParams change.**  
`CoachCommandCenterPage.tsx:38-42` (`useState(() => coerceCoachTabForRole(initialTab, userRole))`). `userRole` comes from `authUser?.role` (`:34-35`); first paint is often undefined. No effect on `[userRole, searchParams]`. Stale tab keeps the wrong capability surface mounted. Re-coerce in an effect; do not trust the initializer.
