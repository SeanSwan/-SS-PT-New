## VERDICT
REVISE — the wired cancel path is fail-closed, but unknown prices are still a `number`, both new APIs fail-open by default, empty `partial` still becomes a real 50% charge on the server, and defaults never re-arm, so the original defect class is gated in one place and live everywhere else.

## BLOCKERS
1. **P1 — empty Custom Amount + server `||` fallback = surprise 50% charge.** Inputs: package fetch fails/empty → `pricingUnavailable: true` → `buildCancelPanelDefaults` returns `{chargeType:'none', chargeAmount:''}` → admin clicks Custom Amount (still enabled) → `selectChargeType('partial', '', false)` → submit with `chargeType:'partial', chargeAmount:''`. Server: `parseFloat('') || (sessionRate * 0.5)` → client is billed half the real session rate even though the UI never showed a dollar amount and the labeled 50% control was disabled. Evidence: `SessionDetailCancelOptionsPanel.tsx` (partial `onChange` seeds `''` when unavailable); `backend/routes/sessionRoutes.mjs:2235-2248` (`partial` and `late_fee` both honor the client number and substitute on any falsy parse).

2. **P1 — new APIs are fail-open, which is the bypass.** Inputs: any new/forgotten call site omits the flag (Storybook, a second modal, a test that still matches the old signature). `pricingUnavailable` defaults to `false` → radios enabled → caption asserts "based on client's package" → `$175.00` / `$88.00` render → `late_fee` submit sends `88`. For a $110 package that is an overcharge (`88` vs `55`); `full` is display-only but `late_fee`/`partial` are not. Evidence: `SessionDetailCancelOptionsPanel.tsx` (`pricingUnavailable?: boolean` + `= false`); `SessionDetailModal.actions.ts` `buildCancelPanelDefaults(..., pricingUnavailable = false)`. Parent required, children optional: the unsafe default is on the leaf that actually paints money.

3. **P1 — defaults captured while `pricingUnavailable` is true never re-arm.** Inputs: modal opens (`createDefaultPricingState` has `pricingUnavailable: true`) → `buildCancelPanelDefaults` runs in that window → `{chargeType:'none', restoreCredit:false}` → fetch succeeds, flag flips false, radios enable, real `$` appear, selection stays `none`. Admin confirms the historical default (full) without noticing. Outputs: $0 cash charge **and** credit not restored (prepaid session burned) because fail-closed set `restoreCredit: false`. If `useSessionCancellation` builds defaults once on mount, this is every cancellation, not a race. Evidence: `useSessionPackagePricing.ts` `createDefaultPricingState` (`pricingUnavailable: true`); `SessionDetailModal.actions.ts` fail-closed branch; author states it does not re-arm.

4. **P1 — client-facing late-cancel warning still invents `$88`.** Inputs: client (`canManage === false`) → hook early-returns → `pricingUnavailable` is always true and unused → `mapLateCancelWarning` does `result.cancellationPolicy?.lateFeeAmount || defaultLateFee`. Missing/0 policy amount → UI shows `$88` as if it were their fee. `||` also treats a real `0` as missing. Evidence: `SessionDetailModal.actions.ts:79`; known residual, still ships.

## ATTACKS
- **Correctness:** The original bug was "unknown is unrepresentable." This commit adds a parallel boolean and leaves `defaultFullCharge: number` / `DEFAULT_FULL_CHARGE` / `DEFAULT_LATE_FEE` (175/88) in state. Every future consumer that reads the numbers and not the flag re-opens the lie; TypeScript cannot stop them. Error/empty paths are only safe if they never set `pricingUnavailable: false` — the provided success snippet sets it false whenever there is "data," with no proof `fullCharge` wasn't coerced from a missing field back to 175. Partial stays enabled during outage (intentional escape hatch) but confirm is not shown to be disabled on non-finite `chargeAmount`, so the hatch is also a trapdoor into server-side 50%. `parseFloat(chargeAmount) || fallback` cannot charge `0` (becomes fallback) and accepts negatives. Label still says "Full Session Charge (Default)" when the actual default is `none`. Stale-fetch race is unaddressed in the diff: no abort/request-id visible; a slow response for client A can land on client B with `pricingUnavailable: false` and a *real wrong* package price under a caption that claims provenance. "0 assertions rewritten" plus the still-green test *"falls back to full and late charge defaults when pricing fails"* encodes the dangerous contract; `tsconfig` excludes `**/*.test.tsx`, so the new flag was never typechecked at the call sites that matter. No browser run, no throttled-fetch observation.

- **Security:** `late_fee` and `partial` are client-supplied money. Admin/trainer is privileged, but the original incident was not an attacker — it was the app sending a placeholder the server believed. A frontend-only gate does not close that. No finite/range/sign check, no idempotency key on cancel+charge, no proof the package-price fetch is scoped to the session's client (IDOR / cross-client price). Disabled radios are DOM-only; `buildCancelPayload` is not in the patch, so a stale `chargeType:'late_fee'` with leftover `88` may still submit. Multi-tenant leak surface is the price fetch, not the boolean.

- **Data-truth / schema drift:** Policy is `$175` / `$110`, no volume discounts. `frontend/src/config/pricing.ts` still has a `$200` tier and a 10-pack at `$160` ("Save $200"). `backend/fix-storefront-packages.mjs` (no `DISABLED_` prefix, zero callers, hand-runnable) writes the retired 175→140 ladder onto the storefront. `dashboard-tabs.ts:186` advertises `/dashboard/admin/pricing-sheet` as `status:'real', isNew:true` for a route that does not exist and a viewer with zero importers. Frontend `defaultFullCharge` vs server `packageInfo.pricePerSession`; placeholder `88` vs 50% of `$110` (`55`). Prices hardcoded in ~8 places, so this panel can be honest while the PDF, seeder, and storefront disagree. House rules not evidenced in the patch: 44px targets on the radio rows, `var(--token,#fallback)` on `ChargeAmount`, Dual-Button Glow on confirm, WCAG on disabled+danger text, ≤300 lines/file.

## HIGHEST RISK
Server `parseFloat(chargeAmount) || fallback` on `late_fee`/`partial` (`sessionRoutes.mjs:2235-2248`). The whole frontend boolean is bypassable (devtools, stale state, empty partial, next caller that forgets the optional prop) and the server *invents a charge* from missing input — the same failure class as the AI-pricing video that started this. Cheapest de-risk before ship: make `late_fee` mirror `full` (ignore client amount, use `chargeCalc.lateFeeAmount` / `sessionRate * 0.5`); for `partial`, `400` if `Number.isFinite(n)` is false (do not substitute); reject negatives. ~10 lines, no nullable cascade, actually closes the overcharge class. Then flip both new defaults to `pricingUnavailable = true` and rebuild panel defaults when the flag falls.

## CONFIDENCE
Could not verify from this document: `useSessionCancellation` (when `buildCancelPanelDefaults` runs, whether session switches reset state, whether confirm is blocked on empty amount); the rest of `useSessionPackagePricing` (error path, `canManage` early-return, how `fullCharge`/`lateFee` are derived, abort/stale-response handling); `buildCancelPayload`; whether the cancel panel is visible on modal open or only after a click; live `packageInfo.pricePerSession` for 30min clients; file lengths and visual house rules. A throttled-network recording of open → immediate confirm and open → wait → confirm, plus those three files and a server test that `partial`+`''` is `400` not `0.5 * rate`, would settle it. I am confident the fail-open defaults and the `parseFloat ||` substitution are real; I am not confident whether non-rearm is a rare race or the new steady-state default.
