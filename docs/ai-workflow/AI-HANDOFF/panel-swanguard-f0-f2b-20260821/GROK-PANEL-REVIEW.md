## VERDICT
REVISE — the enabled-law fences in F0 actually hold, but the production ingest constructor never sets the cap the comments claim is “fixed,” the upsert NULLs refreshable columns, and `POST /api/creators/ingest` is an unserialized quota cannon.

## BLOCKERS
1. **P1 — null-refresh clobber on re-import.** Seed field omitted/unparseable → mapper yields `undefined` → `toValues` sends SQL `NULL` → `DO UPDATE SET col = excluded.col` overwrites owner-visible metadata with NULL (or, for `title`, with the raw channel id). Concrete: a YouTube seed entry with `channelId` but no `handle`/`uploadsPlaylistId`/`subscriberCount` wipes those columns on an existing row; a title-less entry sets `title = channelId` and destroys a display name. Evidence: `packages/domain/src/creatorSeed.ts` (`str`/`num` + youtube/twitch loops), `apps/api/src/creatorSeedImport.ts` `toValues` (`handle ?? null`, `uploadsPlaylistId ?? null`, counts `?? null`, `discoveryReason ?? null`) and `REFRESHABLE_COLUMNS` interpolated into `DO UPDATE SET`.

2. **P1 — production ingest cap is not actually fixed; endpoint has no lock.** `createCreatorIngestRunnerFromEnv` builds the real runner with no `itemsPerCreator`. `run()` forwards `undefined`. Combined with no rate limit and no concurrency guard on `POST /api/creators/ingest`, one owner POST (or a retry pair) can fan out across every enabled creator, including the two ~24k-video channels the comments themselves name, and a second overlapping POST doubles it. Evidence: `apps/api/src/creatorIngestRunner.ts` `createCreatorIngestRunnerFromEnv` (clients/catalog/items only), `createCreatorIngestRunner` (`itemsPerCreator: options.itemsPerCreator`), `apps/api/src/creatorCatalogRoutes.ts` ingest branch (`await ingest.run(...)` with only `onlyCreatorIds`).

3. **P2 — enabled-count invariant false-positives under READ COMMITTED.** `before` and `after` are separate statements, no table lock. Concurrent `enable_creator` / disable that commits between them changes the global count; this import then throws and **rolls back a legitimate metadata refresh**. The import itself cannot flip `enabled`, so the check is the wrong grain. Evidence: `apps/api/src/creatorSeedImport.ts` `readCounts` + `if (after.enabled !== before.enabled)` inside `db.withTransaction`.

No P0 on Q1: nothing in this packet writes `creator.enabled = true` without the 0028 owner-event gate.

## ATTACKS
- Correctness: Q1 is closed in this diff — mapper never reads inbound `enabled` (`creatorsFromSeed` `base.enabled = false` only), INSERT column list omits `enabled` (default false), `DO UPDATE` omits it, INSERT trigger rejects `enabled=true`, UPDATE trigger requires same-txn `creator_event(action='enabled', actor='owner')`, ingest writes `creator_item` not `creator.enabled`, HTTP actor is not taken from the body. Remaining correctness holes: happy-path seed (duplicate `platform`+`platform_channel_id` counts as insert+update and still passes `inserted+updated === rows.length`); `onlyCreatorIds` that are all typos/disabled can yield a 200 zero-item receipt (law 5 adjacent — “fetched nothing” vs “none of those ids were runnable”); ingest∥disable can still fetch a creator that was enabled at list-time (harmless only if every feed join derives visibility from `creator.enabled`, law 4); two concurrent `ingest.run` calls are unsynchronized; Q4 count is racy as above; `xmax = 0` insert detection is a Postgres-ism that silently lies if anyone “simplifies” to `DO NOTHING` (they at least fail loud if RETURNING is empty). `itemsPerCreator` was kept off the HTTP body (good) and then not set at the one construction site that matters (bad). Unhandled: no timeout around `await ingest.run()`.
- Security: `requireRole(user, 'owner')` wraps all `/api/creators*` including GET (members cannot IDOR the watch list). `onlyCreatorIds` cannot widen the enabled set *if* `runCreatorIngest` really intersects — that function is not in the packet. No injection in the upsert (bound params; `REFRESHABLE_COLUMNS` is a const). No SSRF: ids, not URLs. Secrets stay in env and never enter the route. Gaps: **no rate limit, no idempotency key, no advisory lock** → stolen owner session or a double-submit burns YouTube/Twitch quota (Q3 is real). `readJsonBody` is unbounded `request.text()`. `const actor = 'owner' as const` is role-check-implied, not session-value-derived — ingest does not write actor today, but this is the exact pattern law 2 forbids if a later edit reuses it for enable. CSRF not assessable from this packet (cookie vs bearer).
- Data-truth / schema drift: camelCase row ↔ snake_case columns is positional (`$1`–`$19` vs `toValues` 19 entries) — a single inserted column without a matching `toValues` push silently misaligns. `CreatorSeedRow` carries `avatarUrl`, `dailyCap`, `minDurationSec`, `maxDurationSec`, `snoozeUntil`, `enabled*` that the INSERT never writes (defaults / drop). Re-import **does** write `subscriber_count` / `video_count` / `uploads_playlist_id` / `discovery_reason` / `handle` / `title` from a static JSON snapshot, so any live API-updated stats or owner-edited display names get reverted; nulls clobber as in blocker 1. Conflict target is `(platform, platform_channel_id)` while INSERT also supplies `id` — if those unique keys ever diverge, PK collision vs ON CONFLICT take different paths. `muted_keywords` is a JS array with no evidence here of `text[]` vs `jsonb`. Receipt shape `{ receipt }` is unverified against the frontend.

## HIGHEST RISK
Unbounded, unserialized `POST /api/creators/ingest` against real platform quotas (missing FromEnv cap + no lock + no cooldown). Cheapest de-risk before ship: hardcode `itemsPerCreator` to the already-proven F2 value in `createCreatorIngestRunnerFromEnv`, and take a Postgres `pg_try_advisory_lock` at the start of `run()` so a second call returns 409/429 instead of starting another fetch.
