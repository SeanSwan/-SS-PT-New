## BLOCKERS

1. **P2 — GATE 2 (stateful run-cap pre-check) executes before the idempotency replay check, so a retry is judged against a total that already includes its own committed batch.**
   Scenario: cap 100, ledger at 96. Original hosted request with client key K, count 4 → `commit` records 4 runs *before* generation (laneLedger `tryCommit` records pre-provider, by design), ledger now 100. Client's connection drops before receiving the response. Client retries with the same key. Flow: GATE 2 evaluates `usage.runs (100) + count (4) > 100` → throws `E_RUN_CAP` — *before* `assertKeyHasOwner` / `store.has(key)` can return the settled result. On the hosted lane the response is documented as "the only handle," so the paid output becomes unreachable through the API while the ledger keeps the money. No double charge — this is denial of a paid result plus a false error message.
   Evidence: `composeStills.mjs` — the `// GATE 2 — volume cap applies to BOTH lanes` block (`runs + count > limits.maxRunsDaily` → throw) precedes `// GATE 3a — idempotency FIRST` and `if (!req.estimateOnly && store.has(key)) return ...`. The commit that makes the double-count real is the `tryCommit`-shaped `commit({ runs: count, ... })` call earlier in the same function. The GATE 3a comment claims "idempotency FIRST" — it is first only relative to the lane gate, not to GATE 2, and GATE 2 is the only gate above it that is *stateful* (GATE 1 and the kit gates are deterministic functions of the request and re-pass identically on retry).
   Honest caveat: deps default `usage = { runs: 0, spendUsd: 0 }`. If the live route does not inject live ledger usage, GATE 2 never fires in prod and this becomes latent — but then GATE 2 is dead code and its "better error earlier" claim is false. Both branches of that conditional are defects; only the route wiring can tell you which one you have. Fix is a three-line reorder (derive key + replay check above GATE 2; neither depends on it) or exempting `store.has(key)` requests from the pre-check. Note the retry only reaches the replay path with the *same* key if the client supplied one — for derived keys this intersects Blocker-adjacent uncertainty about `deriveKey` (see CONFIDENCE).
