Round-2 attack is correctness only: state machines, races, FK/cycles, Postgres truth, injection surface. Consensus F1/F2/F4–F11 are adopted. F3 as written is not a closed identity contract. Two new MAJORs are missing from the candidate and will double-apply or orphan under the packet as it stands.

**F3 is necessary and insufficient.** Packet shows three different caller-supplied identity names and a null path: `AITerminalPanel.tsx:116-139` sends `clientId || null`; `aiCommandRoutes.mjs:111-145` accepts `selectedClientId`; `AiConversation.mjs:24-83` stores `targetUserId`; `clientResolver.mjs:110-166` scopes trainers and explicitly does not bound admins; `CoachCommandCenterPage.tsx:34-43` has `isClientMode` with no packet-visible “target MUST equal auth PK” check on the command lane. Rejecting only null (`TARGET_REQUIRED`) still allows (a) a client posting another user’s PK, (b) a trainer/admin executing against a different PK than the bound conversation’s `targetUserId`, (c) a stale tab racing a client switch. Constraint 2 is a write-safety contract, not a naming convention.

**F12 (new MAJOR) — FK / ON DELETE / intake↔proposal identity are unstated.** `AiConversation.mjs:24-83` enumerates `userId` and `targetUserId` with no association, unique, CHECK, or ON DELETE in the excerpt. `AiCommandAuditLog.mjs:24-91` records resolved target and operation id with no `action_id` unique and no FK to users or commands. Intake handlers start at `coachIntakeRoutes.mjs:23-33`; proposal apply is `coachProposalRoutes.mjs:30-54`; no join key, no shared PK, no delete rule. Postgres consequences that the candidate does not close:
- no FK ⇒ conversation/command/proposal can target a non-row (ghost client); constraint 2 fails before any resolver runs
- `ON DELETE CASCADE` on `targetUserId` silently destroys trainer history when a client is removed
- `ON DELETE SET NULL` re-creates the null-target state F3 just banned
- `ON DELETE CASCADE` on audit wipes the only recoverability log
- intake deleted under an in-flight proposal, or two proposals minted from one intake, is an orphan/cycle; packet has zero SQL to disprove it

Absence of SQL in the packet is not proof the constraints exist. Sequelize field lists are not constraints. This stays MAJOR until a schema probe shows the FKs.

**F13 (new MAJOR) — unique `actionId` ≠ linear state machine.** F1’s unique key stops duplicate inserts. It does not stop illegal transitions. `useCoachCommand.ts:96,170,207` exposes execute/confirm/cancel as three HTTP verbs with no packet-visible expected-status predicate. Two tabs can confirm+cancel the same row; confirm can fire after cancel; execute can mint a success receipt with no prior pending state. Same hole on proposals: packet says the approval service “claims pending rows” (`coachProposalRoutes.mjs:30-54`) but shows no `UPDATE … WHERE status='pending' RETURNING *`. Check-then-act under READ COMMITTED is a lost-update. F6’s fix is the right shape; it is not yet specified for confirm/cancel, reject, or expire, and it is not verified against live SQL.

SQL injection: no query text in packet, so no injection finding. Residual only — live probe must show bind/replacements, not string concat of `selectedClientId` / `targetUserId`.

Mount order at `routes.mjs:630-634` is correct Express specificity. Not a defect. Admin unbounded scope stays pending policy IFF every write is tagged in audit with actor+resolved PK and F3’s existing-PK check holds; untagged admin writes are not acceptable.

Fixes (apply, do not re-derive):

- **F1** WHAT: durable idempotency + receipt. WHERE: `AiCommandAuditLog.mjs:24-91` add `action_id TEXT NOT NULL` + `UNIQUE(action_id)`; `aiCommandRoutes.mjs:111-145` require `actionId`, return the audit row as receipt; `useCoachCommand.ts:96,170,207` send the same `actionId` on execute/confirm/cancel. HOW: executor is `INSERT … ON CONFLICT (action_id) DO NOTHING RETURNING *` then return stored receipt; never re-dispatch on conflict.
- **F3 (replacement)** WHAT: one user-PK identity, role-closed. WHERE: `clientResolver.mjs:110-166`, `aiCommandRoutes.mjs:111-145`, `AITerminalPanel.tsx:116-139`, `AiConversation.mjs:24-83`. HOW: resolve alias → `users.id`; `400 TARGET_REQUIRED` if missing; `403 TARGET_FORBIDDEN` if role=client and target≠`auth.userId`, or role=trainer and target∉resolver set; admin may target any existing PK only; if `conversationId` bound, refuse when `conversation.targetUserId ≠` resolved PK; receipt echoes `{alias, targetUserId}`.
- **F12** WHAT: real Postgres constraints. WHERE: `AiConversation.mjs:24-83`, `AiCommandAuditLog.mjs:24-91`, intake `:23-33` + proposal `:30-54`. HOW: `userId`/`targetUserId`/`actorId` FK → `users(id)`; conversation `targetUserId` `ON DELETE RESTRICT` while status∈active; audit FKs `ON DELETE SET NULL` plus denormalized actor/target snapshots (never CASCADE); intake↔proposal share one `intake_id` FK, proposal `UNIQUE(intake_id)` or explicit revision key; `CHECK` on status enums; block `users` delete while pending commands/proposals exist.
- **F13** WHAT: CAS transitions, not just unique keys. WHERE: confirm/cancel behind `useCoachCommand.ts:170,207`; apply/reject behind `coachProposalRoutes.mjs:30-54`. HOW: single-statement `UPDATE … SET status=$next WHERE action_id=$id AND status=$expected RETURNING *` inside a transaction; 0 rows → `409 CONFLICT` with current status + last receipt; legal map: execute:∅→pending_confirm; confirm:pending_confirm→confirmed; cancel:pending_confirm→cancelled; proposal approve:pending→applying→applied|failed; reject:pending→rejected. Terminal states are absorbing.
- **F6** keep as written; implement with the F13 UPDATE shape, not SELECT-then-UPDATE. **F2/F4/F5/F7/F8/F9/F10/F11** keep as written.
