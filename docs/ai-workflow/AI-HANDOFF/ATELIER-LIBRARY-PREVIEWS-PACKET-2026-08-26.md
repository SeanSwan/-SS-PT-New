# Review packet — library previews · 2026-08-26 (loop iteration 6)

**Branch** `feat/atelier-v2-compose` · not deployed. A small follow-up slice, so **free seats only** — this implements what the previous panel asked for rather than proposing something new.

> All restated-code claims generated by command at write time.

## 1. What this answers

Last round's sharpest product criticism (Grok): *"you have shipped the index without retrieval."* The card showed `1920x1080`, so finding your work meant **reading** rather than **recognising** it — which is not how anyone looks for a picture.

## 2. What landed

`listAssets` now signs one short-lived URL per **image** row, using the same `generatePlaybackUrl` signer the published-reference endpoint already uses. Files: `assetLibrary.mjs` 234, `AtelierLibrary.tsx` 178, `AtelierLibrary.styles.ts` 67, tests 31 backend + 11 frontend.

**Signing is parallel and per-row isolated.** Presigning is a local HMAC, not a network call, so a page of two dozen costs nothing. Each is wrapped so that one object which will not sign yields `previewUrl: null` — a card that falls back to its dimensions. **A page that 500s because of a thumbnail is a worse library than one with a missing thumbnail.**

The wrap uses `Promise.resolve().then(() => readUrl(...)).catch(...)` rather than `readUrl(...).catch(...)`, because a signer that throws *synchronously* never produces a promise for `.catch` to attach to. There is a test for exactly that.

**The client degrades twice.** No `previewUrl` → the dimensions placeholder. A `previewUrl` that has since **expired** → `onError` hides the image, because a broken-image icon reads as "your asset is gone", which is never true.

Non-image rows are not signed at all: there is no still to preview.

## 3. What I want attacked

1. **Is a signed URL in a list response the right trade?** The previous packet said "the storage key never leaves the server". A signed URL is time-limited and opaque, which is the trade the reference endpoint already makes — but it is a trade, and it is now made 24 times per page instead of once per asset.
2. **Expiry vs. paging.** A URL signed when page 1 loaded may expire while the operator scrolls. The client hides the broken image; it does not re-sign. Is silent degradation right, or should it refetch?
3. **`object-fit: contain` with a `max-height`.** A cropped hero is unrecognisable, so previews are letterboxed rather than filled. Right call for a *studio* library, or does it make the grid look weak?
4. **What is still missing** for this to be retrieval rather than an index — select-into-Compose, delete, sort, date filters?
5. **Anything about this that looks wrong from outside it.**

## 4. Verification

Backend **405/405 across 20 suites** (5 new), frontend **119/119 across 14** (2 new). `tsc` exit 0 over the glob-generated 15-file include. `vite build` exit 0; the chunk hash changed from `Bme8TQc7` to `ByBXSWpy`, so the new code is in the bundle. Token-registry guard CLEAN, secret scan CLEAN, every file ≤300.

**Not proven:** a real signed URL against real R2. The signer is injected and the tests assert the plumbing, the isolation and the fallbacks — not that R2 returns an image.

| **Silent isolation hides systemic failure.** A rotated key makes all 24 fail, and the page renders grey boxes with a 200 and no telemetry — the operator concludes their renders are gone | GLM (P2), Qwen (P2) | Per-row `console.warn` with the asset id; and `previewsUnavailable` when **every** image on a page fails, surfaced as a notice saying it is the signer and not their assets. One bad object and a broken signer are different facts and must not look identical |

## Disproven

- **"No lazy-loading anywhere in the packet"** (GLM) — `loading="lazy"` was in the component and pinned by a test from the start. The *packet* failed to mention it, which is a packet defect, not a code one.

## Accepted, not fixed here

- **No derivative thumbnails** (GLM P1). Previews sign the *original*, so a page of 24 at 1920×1080 is tens of megabytes; `loading="lazy"` bounds what is fetched, not what a fetched one costs. Real thumbnails need a resize pipeline at write time. **Trigger: the first page that feels heavy on a real connection** — which, unlike "when the list feels slow", an operator will notice immediately.
- **`mime` may be null on back-catalogue rows** (GLM P2), so `kind === 'image'` is the only classifier. Correct; the kind column is populated by the atelier writer, and older rows predate it.
- **A stalled signer would block the page** (GLM P2) — true if `generateThumbnailUrl` ever became a remote call. It is a local HMAC today; the invariant is now written down here rather than assumed.

## The claim I had to correct

The previous packet said **"the storage key never leaves the server."** A SigV4 presigned GET puts the object key in the URL path, so that is no longer true in full, and repeating it would be exactly the confident-copy-outliving-the-code failure this lane keeps writing up. What a preview actually grants is a **time-limited read of one object** — the same trade the published-reference endpoint already makes, now made per row instead of per request. The docblock says so.
