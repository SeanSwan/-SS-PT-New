The actual controls are the ones GPT listed in the same breath and then buried: minimization, short retention, purge on logout/account-switch/role-switch, server-synced drafts. ## WHAT EVERYONE STILL MISSED

1. **Route-shadowing is a class, and nobody audited it.** A guarded block-time handler sitting on a shadowed dead router was found by luck. Nobody — four review rounds plus GPT — proposed the obvious execution: boot the app, enumerate the mounted route table, and assert that every guarded handler is the one actually serving its path. If one dead router exists, the prior probability of others is not low [INFERENCE from the verified dead-router fact]. This is a test, not a review finding, which is why static review keeps missing it.
2. **Nobody verified which master-prompt builder is reachable.** V6 proves v3.0 and v5.0 *coexist*. Coexistence is not reachability. The v5 "fallback" may serve live traffic or may be dead code — the entire C6 migration plan is sized differently depending on the answer, and nobody traced the call sites [INFERENCE].
3. **The dictation utterance has no failure story.** Everyone flagged ack-before-save. Nobody asked: when the save fails, where does the transcript go? For a dictation-first product, the utterance must be durably captured (an intake item — the very tables GPT wants to generalize) *before* processing, so a failed save is retryable instead of evaporating. GPT's Stage 1 "await-before-success" fix turns silent loss into a loud failure that still loses the user's spoken words. The owner's core loop deserves better than either [INFERENCE].
4. **The de-identification denylist has no regression test and will rot.** It's a verified denylist preserving health context by design. Every new intake field is a chance to silently bypass it. Nobody proposed a test corpus asserting denylist output contains no direct identifiers, nor a check that new intake fields route through it. The privacy posture GPT's C4 correctly demands is unenforceable without this [INFERENCE].
5. **The parallel safety loaders have no retirement plan.** The generation controller separately loads pain entries, waivers, movement analyses — that's why "AI never sees injuries" was an overstatement. GPT's C5/C6 canonical `ClientTrainingContext` adds a *third* safety-context source. Nobody specified which loader wins during the transition or when the parallel paths get deleted. Two drifting safety sources is worse than one broken one: each looks authoritative, neither is.
6. **The approval-authorization gap is real and unaddressed by everyone** (probe confirmed): `coach_action_proposals` scopes claim/approval to `created_by_user_id`. Under GPT's C2 generalization, a client's voice-originated `plan_edit` proposal could be claimed and applied by the client — self-approval of an AI-originated mutation, which is precisely the failure the "explicit Apply" vision exists to prevent. A per-role approval matrix (who may apply which proposal type for which subject) must precede generalization, not follow it.
7. **Nothing has been executed, and the two most embarrassing errors in this chain were execution-shaped.** V1's false-absence came from grep; the dead router is invisible to static reading. The minimum execution harness, specifiable today with no new dependencies: docker-compose Postgres → clean migrate → boot → (a) replay onboarding submit through prompt-build and assert safety fields in output, (b) replay voice submit with the DB killed mid-save and assert no success ack + recoverable transcript, (c) replay signed Stripe events, (d) dump the mounted route table. Every prior miss in this chain would have been caught by one of those four. Nobody specified the harness. That is the meta-finding.
