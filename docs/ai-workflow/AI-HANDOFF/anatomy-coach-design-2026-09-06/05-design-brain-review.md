## Proposed Brain vNext procedure

1. Classify the surface: marketing, client reporting, trainer/operator, analytical, or functional 3D; record mixed surfaces and precedence. Identify the one user action that should be fastest.
2. Establish route/mount/API/model receipt, entitlement and state truth. No design claim based only on an attractive screenshot or inactive component.
3. Write the data/action contract: what is observed, inferred, pending, unavailable, private and irreversible. Define draft/selection/server authority separately.
4. Produce 2–3 original directions with names, four-phase usage arc, emotional job, signature, motion and tradeoffs. Cite references for principles; do not copy layout wholesale or conceal provenance.
5. Create actual desktop/mobile wireframes and one adverse-state sheet before high-fidelity polish. Select by task correctness first, then hierarchy, brand, access, motion and performance.
6. Hostile pass tries wrong target, duplicate confirm, stale data, unknown outcome, role change, inaccessible canvas, mobile keyboard and reduced motion. A clean pass may remain clean.
7. Record a decision with retained/rejected elements and evidence. Freeze a versioned design contract for builders. New scope updates the same packet with supersession links.
8. Verify mounted behavior on real fixture-backed UI before promoting doctrine. Update design.md first, generate design.html and adapters with existing tooling, run parity tests and maintain rollback snapshot.

## Fair comparison, without pretending it already happened

Use the same synthetic client set, same capability map, same viewport matrix and the same six tasks for A/B/C. Randomize order and conceal direction authorship from evaluators where practical. Tasks: first pain report; update the same episode; reveal patella and return without losing draft; explain recovery uncertainty; coach reviews a conflicting-client proposal; recover a saved action after response loss.

For each, record correct target/outcome, unintended effect count, completion rate/time, navigation steps, ability to explain data freshness, keyboard success and confidence in what saved. Collect distinctiveness/readability preference separately. Match feature completeness before comparison; a stripped-down concept cannot win only because it omitted hard workflows. Include client, trainer/admin and assistive-use perspectives; a single designer's preference is not a usability study.

Select the version with zero unintended writes, no critical accessibility or data-truth failure, and best task completion. When differences are inconclusive, choose the simpler implementation with preserved capability. Combine compatible pieces only; never combine three navigation systems. Log evaluator count, limitations and raw aggregate results without private user records.
