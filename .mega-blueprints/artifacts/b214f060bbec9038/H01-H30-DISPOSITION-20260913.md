# DECISION REQUIRED — R-H27's bounded grace (raised by the round-179 hostile review)

**The fact, measured rather than argued.** With an adapter that ignores the abort, the round-172 fix releases the occupancy slot 1500 ms after the deadline. The reviewer executed that sequence and measured **`maxLive = 2` concurrent provider operations** (`bootcampBrain.mjs`, grace release path). R-H27 says, in its own words: *"if an adapter cannot cancel, retain that occupancy until settlement"* and *"at most one unsettled optional Brain provider operation per server process."* So the code now deviates from the requirement's text while implementing the register summary's description of the same row - *"unsupported cancellation is disclosed with bounded concurrency"*.

**Why it cannot simply be fixed.** Unbounded retention and "never wedge permanently" are mutually exclusive when an adapter may never settle: retaining the slot until settlement IS the wedge the round-171 review found and the round-172 fix removed. Something has to give, and which thing gives is a product decision, not a coding one.

**Option A — amend the requirement text (code unchanged).** Add to R-H27: an occupancy slot is released on settlement, OR after a bounded grace period following the deadline, whichever comes first, and state the grace value. Cheapest, makes the packet self-consistent, and changes nothing a trainer experiences. Cost: the requirement becomes whatever the code does, which is only legitimate because the register summary already describes bounded concurrency.

**Option B — accept the deviation as implemented and record it as accepted.** No text change; the row carries a named, measured, deliberate deviation. Cost: a reader comparing code to `13-server-repair-contract.md:279` finds a contradiction with no pointer explaining it, which is the stale-claim pattern this packet has corrected four times.

**Option C — change the fix's shape (biggest, arguably correct long-term).** Make the provider contract mandate `signal` handling - `async (prompt, { signal }) => string` - and hard-fail an adapter that ignores the abort, so there is nothing left to bound. Cost: the documented provider contract changes (`bootcampGenerator.mjs:813-817`), every existing adapter must be updated, and today NONE of them receive a signal at all because R-H27's second-argument form is brand new in this packet.

**VERIFIED IN ROUND 207, AND IT SHARPENS ALL THREE OPTIONS: no brain adapter accepts a second argument.** A search across `backend/services` for a provider signature taking `(prompt, options)` or `(prompt, { signal })` returns exactly one hit - `appendSwanCoachPlanningGuidance(prompt, { placement })` in `swanCoachPlanningContextService.mjs`, an unrelated function - and the documented contract remains `async (prompt) => string`. **So the `AbortSignal` this packet added is currently DECORATIVE: nothing consumes it, and the abort cancels nothing.** Two consequences follow. First, the bounded GRACE PERIOD is not a convenience layered on top of a working abort - it is the ONLY containment that functions today, because "abort where supported" is not supported anywhere yet. That makes option A the honest description of what the code can do rather than a weakening of the requirement. Second, option C is not a tidy-up: it requires changing the provider contract AND updating adapters that do not exist in this worktree at all, so it is genuinely a separate integration slice rather than part of this repair.

**My recommendation: A now, C as a separate slice.** A closes the contradiction this packet created without pretending the tradeoff away. C is the right end state, but it is a provider-integration change rather than a repair, and bundling it here would mean shipping an unexercised contract change against adapters that do not yet exist.

**Nothing has been changed for this decision.** The code is exactly as round 172 landed it, the deviation is recorded in the H26/H27 row, and this block exists so the choice is one line rather than a re-derivation.
